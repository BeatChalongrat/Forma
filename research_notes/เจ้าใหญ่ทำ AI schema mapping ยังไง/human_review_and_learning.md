# How mature AI-plus-human-review products route work by confidence and learn from corrections (IDP, MDM, data-quality) — transferable patterns for an AI schema-mapping tool with an ops review team

Research date: 2026-11-02. Scope: IDP vendors (Rossum, Hyperscience, ABBYY Vantage, UiPath DU, Google Document AI, AWS Textract+A2I, Microsoft Document Intelligence / Content Understanding, Nanonets, Instabase, Klippa), MDM/entity resolution (Tamr, Reltio, Informatica, IBM MDM, Senzing), deterministic data-quality gates (Great Expectations, Deequ, Soda, dbt, Monte Carlo), review-UX research, metrics, and per-sender memory/drift/versioning. Vendor terminology is kept exact and quoted where it matters. Secondary sources are flagged as such.

---

## KQ1. How is confidence calibrated and thresholded in practice (per field, per document type, per sender)? Published STP / accuracy numbers?

### Takeaway
Every mature vendor thresholds at the **field** level, nests it under a **queue/flow/document-type** default, and layers deterministic rules on top; the mature ones (Hyperscience, Microsoft) stop exposing raw confidence at all and instead let the operator set an **accuracy target** or **error-coverage target** from which thresholds are derived against human-verified samples. Vendors openly warn that raw confidence is not accuracy, and published STP numbers are mostly marketing; the credible independent baseline for invoice "touchless" rate is around one third.

### Cited Findings

**Rossum (score 0–1, per-queue default, per-field override, three automation levels)**
- Confidence scores range 0–1 and are described as "the extent to which the AI engine is confident that it got the text and the location of the field correctly"; Rossum says scores are calibrated to the probability a value is correct, so a threshold of 0.975 means a 2.5% maximum error rate — [Rossum Knowledge Base: Using AI confidence thresholds for automation](https://knowledge-base.rossum.ai/docs/using-ai-confidence-thresholds-for-automation-in-rossum)
- With "Confident" automation enabled, all captured fields default to 0.975 ("Field automation - Score threshold" on the queue's Automation tab); per-field thresholds are set in the extraction schema and Rossum recommends per-field; the "Automation data" table is used to adjust thresholds "based on insights"; when a field clears its threshold the datapoint carries `validation_sources: ["score"]` — [Rossum Knowledge Base](https://knowledge-base.rossum.ai/docs/using-ai-confidence-thresholds-for-automation-in-rossum)
- Rossum's own caveats: accuracy estimation remains "an unsolved problem", the engine "may be a little pessimistic" (real accuracy higher than score hints, varying field by field), and customers should test on their own data; high-automation customers are pointed to a "Dedicated AI Engine" with threshold analysis by the Rossum AI team — [Rossum Knowledge Base](https://knowledge-base.rossum.ai/docs/using-ai-confidence-thresholds-for-automation-in-rossum)
- The API guide names the three levels "No automation" (default; review all), "Confidence automation" (review only low-confidence or validation-error documents), "Full automation" (export anything without validation errors), says `score_threshold` defaults to **0.8**, can be set on the queue or per datapoint in the schema, and warns: "Note that the threshold does not correspond to the accuracy of the fields passing the threshold!" — [Rossum API guide: Automation](https://rossum.app/api/docs/openapi/guides/automation/). *Conflict:* knowledge base says 0.975 default under "Confident"; the API guide says 0.8 default for `score_threshold`. Likely UI vs API defaults or doc drift; treat 0.8 as the API default and 0.975 as the UI "Confident" preset.
- Rossum shipped "a new confidence score calibration model that enables better automation rates for custom model training users" in a 2019 release — [Rossum blog: Under the Hood](https://rossum.ai/blog/under-the-hood-rossum-product-improvement-news/)

**Hyperscience (accuracy target → auto-thresholding; confidence is internal)**
- Accuracy is scored per field (an SSN with one digit missing counts as 0% for that field); "automation" is the share of fields the machine handles without human review (at 90% automation humans see 10% of fields); raising the accuracy target sends more fields to humans — [Hyperscience: Transcription Accuracy and Automation (v42)](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)
- "Accuracy targets enable both fine-tuning and auto-thresholding." Targets can be set for document transcription as a whole, for individual Structured fields, and for Semi-structured fields and table columns; targets are per flow; "Field Dictionary" targets apply wherever a field appears and a flow-level target overrides them — [Hyperscience v42](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)
- Minimum QA records before auto-thresholding: Structured text 5,000 fields; Semi-structured text 2,000; Checkboxes 2,000; Signatures 2,000; Table text 2,000 cells; "Period of records to use" bounds the look-back window — [Hyperscience v42](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)
- Machine confidence is "an internal, non-configurable value that is meaningful only inside its model", explicitly "not the same as accuracy or probability"; the operator sets the accuracy requirement and the system adjusts thresholds; a chart example maps 0.96 confidence to ~99.74% accuracy; a 99.5% target picks the threshold where errors are 0.5% of all fields — [Hyperscience v42](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)
- An entry-level 99% target does not guarantee 99% on that entry "because thresholds are set for the whole fine-tuning model, not per entry"; it just gives that entry a higher threshold; entry-level targets generate no extra QA tasks — [Hyperscience v42](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)
- Example trade-off: a 99.5% target may start at 75% automation and rise to 94% at the same accuracy as QA results train the model — [Hyperscience v42](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)
- Third-party listing repeats Hyperscience marketing of "up to 99.5% accuracy and 98% automation" and notes independent reviews report lower handwriting accuracy — [ERP Research (secondary)](https://www.erpresearch.com/erp-add-ons/ocr/hyperscience)

**AWS Textract + Amazon A2I (declarative activation conditions; now closed to new customers)**
- "Amazon SageMaker A2I is no longer open to new customers"; existing customers continue, no new features planned — [AWS docs: Human Loop Activation Conditions with Textract](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-json-humantaskactivationconditions-textract-example.html)
- Three `ConditionType`s: `ImportantFormKeyConfidenceCheck` (with `ImportantFormKey`, `ImportantFormKeyAliases`, and `KeyValueBlockConfidence{Equals,LessThan,LessThanEquals,GreaterThan,GreaterThanEquals}` plus the same five `WordBlockConfidence*` comparators; `"*"` matches any key), `MissingImportantFormKey` (triggers when the key or its aliases are absent — the whole form goes to humans with no predicted pairs), and `Sampling` (`RandomSamplingPercentage` 0.01–100); conditions compose with `And`/`Or`; "only one condition needs to evaluate to true to initiate a human loop" but all are evaluated — [AWS docs](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-json-humantaskactivationconditions-textract-example.html)
- Worked thresholds in AWS's own examples: `Employee Name` key-value block confidence < 60 and word blocks < 85; `Pay Date` < 65 / < 85; a pattern that "always send[s] low confidence inferences... and sample[s] high confidence inference... at a specified rate" (e.g., < 60 always; > 90 sampled at 5%) — [AWS docs](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-json-humantaskactivationconditions-textract-example.html)
- `Sampling` is deterministic per input: repeated identical `AnalyzeDocument` requests give the same sampling outcome — [AWS docs](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-json-humantaskactivationconditions-textract-example.html)
- Console walkthrough: trigger review when key "Mail Address" has confidence < 99 or is missing; also randomly send a percentage of pages for model monitoring — [AWS ML blog: Textract + A2I for critical documents](https://aws.amazon.com/blogs/machine-learning/using-amazon-textract-with-amazon-augmented-ai-for-processing-critical-documents/)

**Microsoft Content Understanding / Document Intelligence (separate confidence model; calibration recipe; published numbers)**
- A confidence score is "a learned estimate of how reliable a specific field result is" (0–1); it is *not* the LLM's self-reported certainty but comes from a separate service-level confidence model whose inputs include the document and evidence, the field and result, labeled examples where available, and the model's own behaviour (e.g., ambiguity signals); trained on Microsoft-curated data, not customer data; the latest refresh improved AUROC "by up to 14%"; confidence is "a ranking signal for risk" — [Microsoft Foundry blog, Oct 2026: Content Understanding confidence, grounding, HITL](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)
- Calibration recipe: segment by document type (form family, version, source); set thresholds per document type **and** per field; give **empty fields their own policy** because confidence on empty results "did not reliably separate 'no value' from 'missed value'"; keep fields in review when confidence does not separate errors from correct values; steps: collect human-verified representative production documents → measure accuracy and separability per field/type → set a business target (e.g., catch ≥ 80% of known errors) → choose the cutoff that meets it with the fewest reviews, else keep the field in review → validate on held-out → monitor with an "outer loop" of human-checked samples of *unflagged* results — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)
- Results: evaluation of >22,000 field values across >1,000 production documents; on held-out data "41% fewer field values were selected for targeted review" while still covering "more than 80% of known extraction errors"; insurance customer: "nearly a 50% reduction in human review burden", "75% faster form onboarding", "97%+ page-level classification accuracy"; a public calibration lab on 1,000 CORD v2 receipts (800/200 split) at an 80% error-coverage target auto-approves only ~14% of filled values and 13% of blank values, leaving 73% for review — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)
- Stated limits: calibration "is not a portable guarantee" — it applies only to the evaluated document types, analyzer configuration, field schema and LLM; high overall accuracy does not justify a looser threshold; a stricter threshold cannot fix a non-separating signal; synthetic data is no substitute; revalidate when documents, config, schema or LLM change or monitoring shows drift — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)
- Microsoft Q&A notes custom classifiers can assign high confidence to a wrong label, so high confidence alone does not justify skipping review — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2285322/why-is-azure-ai-document-intelligence-custom-class)

**UiPath Document Understanding (two confidences, per-field thresholds, per-doc-type OCR threshold)**
- Besides a customizable OCR confidence threshold per document type, an "Extraction confidence threshold" is set per field in the Taxonomy Manager under "Validation settings" — [UiPath IntelligentOCR activities release notes](https://cloud.uipath.com/mukesha/docs_/activities/docs/release-notes-uipath-intelligent-ocr-activities)
- Official guidance: set thresholds per field and "always check both Extraction Confidence as well as OCR Confidence for a given value before making your decision"; validation is recommended when 100% accuracy is needed, there is no other source to cross-check, or no "synthetic consistency checks" exist (e.g., line items sum to a total, ID checksum) — [UiPath DU 2022.10: Data Extraction Validation overview](https://docs.uipath.com/document-understanding/automation-suite/2022.10/classic-user-guide/data-extraction-validation-overview)
- UiPath forum (official staff tone) warns confidence "should be used for guidance only and not treated as 100% accurate" — [UiPath Forum](https://forum.uipath.com/t/validation-station-showing-depending-on-confidence/226394)

**Nanonets, Google Document AI, Instabase, Klippa**
- Nanonets: `score` 0–1 per prediction; recommends ~0.8, which in their experience gives roughly 0.9 precision and 0.9 recall; "scores usually need calibration per model" by testing thresholds and inspecting what gets flagged; field scores can be combined into a document-level score; example Total_Amount 0.985 vs Net_Amount 0.541 — [Nanonets docs: Confidence scores](https://docs.nanonets.com/docs/confidence-scores)
- Google Document AI HITL exposed "confidence threshold filters to limit the number of documents going through HITL"; quickstart sets the threshold to 100% to send everything; HITL is **deprecated** (deprecation table lists January 16, 2024; a localized quickstart says unavailable after January 16, 2025 — sources differ on the date) — [Google Document AI HITL overview](https://docs.cloud.google.com/document-ai/docs/hitl); [Document AI HITL quickstart](https://docs.cloud.google.com/document-ai/docs/hitl/quickstart)
- Instabase: "Confidence scores help trigger human review when AI results fall below a certain threshold", combined with validation logic and external-system validation — [Instabase blog](https://instabase.com/blog/overcoming-the-limitations-of-llms-data-validation-and-human-review)
- Super.AI (generic guidance): review at least 30 data points per field to pick a threshold, revisit when data distribution changes — [Super.AI docs](https://docs.super.ai/docs/confidence-score)

**MDM match bands**
- IBM MDM: two thresholds — an "autolink threshold" for automatic matches and a "clerical review threshold" for the minimum potential match; "Scores that fall in the range between the clerical review threshold and the autolink threshold can be sent through the potential matches workflow to be remediated by a data steward" — [IBM MDM docs](https://www.ibm.com/docs/en/DSXDOC/wsj/mdm/config-workflow-potential-match.html)
- Partner (Mastech, not vendor) examples: Reltio zones ≥ 0.95 auto-merge, between review and merge thresholds → steward task, < 0.60 distinct — [Mastech Reltio guide (partner)](https://digihub.mastechdigital.com/assets/Reltio/Reltio%20Asset%20Library/04_Match_Merge/RELTIO_Match_Rule_Development.docx); Informatica 95–100% auto-merge, 80–94% manual review steward task — [Mastech Informatica patterns (partner draft)](https://digihub.mastechdigital.com/assets/Informatica/Informatica_Platform_Library/08_MDM/INFA_Match_Merge_Patterns.docx)
- Tamr: confidence is "a loose measure of how many of Tamr Core's internal classifiers agree on a label" (High/Medium/Low) — [Tamr docs: Reviewing Pairs](https://docs.tamr.com/new/docs/record-pairs-reviewer)
- Senzing: no tunable match thresholds; "principle-based" resolution derives behaviour from attribute frequency, exclusivity and stability; internal thresholds exist only for when keys "go generic" — [Senzing: Entity Exploration tutorial](https://senzing.com/docs/tutorials/eda/eda_basic_exploration/); [Senzing: Principle-based ER](https://senzing.com/principle-based-ER/)

**Published STP numbers**
- Industry-average touchless rate 32.6% (Ardent Partners 2025 AP benchmark, n=212) — cited secondhand by [Hypatos](https://www.hypatos.ai/knowledge-base/what-is-touchless-rate-ap-automation); not verified against Ardent's report.
- Vendor rules of thumb: touchless best-in-class "roughly 50% to 80%", STP best-in-class "above 60%" — [Kognitos (vendor)](https://www.kognitos.com/blog/accounts-payable-kpis-metrics-that-matter-2026/); top-quartile "80%+" — [ChatFin (vendor)](https://chatfin.ai/blog/touchless-ap-straight-through-processing-finance-2026); "95 percent field accuracy does not translate directly to a 95 percent straight-through rate" — [invoicedataextraction.com](https://invoicedataextraction.com/blog/touchless-invoice-processing)

### Inferences
- The field is converging on **"set the error budget, not the threshold"**: Hyperscience (accuracy target → auto-threshold), Microsoft (error-coverage target → cutoff per field/type) and Rossum's "threshold = desired accuracy" framing all put a business number in front of the operator and derive the score cutoff from verified samples. For a schema-mapping tool this means `policies/approval.yaml` should express *target accuracy per field criticality* and the system should derive/report the implied score cutoff from the review history, rather than hard-coding 0.8.
- Everyone keeps a **three-band** outcome (auto / review / block-or-distinct). The middle band is where the human lives; the top band is still **sampled** (A2I `Sampling`, Microsoft "outer loop", Hyperscience QA) so that silent errors in auto-approved work are measured.
- **Empty/missing gets its own policy** (Microsoft, A2I `MissingImportantFormKey`): "no value" vs "missed value" is a different question than "is this value right", and confidence does not separate them. A mapping tool should treat an *unmapped* target field as a distinct review item type from a *low-confidence* mapping.
- Vendors who sell "calibrated" scores (Rossum) still publish disclaimers; the ones who do not expose raw scores at all (Hyperscience) avoid the trap of operators reading 0.8 as 80% correct. Showing a *band* or an *implied error rate from your own history* is safer UX than a raw probability.
- Nothing credible exists for STP in schema mapping specifically; the analogous metric is "rounds exported without a human touching the mapping" and should be baselined internally before setting targets.

### Gaps
- No vendor publishes the actual calibration method (temperature scaling, isotonic, etc.); Rossum and Microsoft describe outcomes only. Hyperscience describes the mechanism (fine-tuning with QA consensus) but not the model.
- Klippa: no documentation surfaced on confidence or review routing in any search.
- No independent (non-vendor) STP benchmark for IDP beyond the secondhand Ardent 32.6% figure.
- Google Document AI's replacement for HITL after deprecation was not found.

## KQ2. What does the human see when reviewing, and how are corrections captured so the same mistake does not recur?

### Takeaway
The review surface is always **value + evidence side by side** (highlighted source region, "grounding", matching attributes highlighted), with only the uncertain items demanding attention; corrections are captured as *labelled ground truth* (region re-selection, type reassignment, pair label) and re-validated by the deterministic rules immediately, while model learning happens in a separate, gated batch step.

### Cited Findings
- **UiPath Validation Station** groups extraction results into two categories relative to a minimum confidence so reviewers focus on low-confidence fields; when a user edits a value "its score [is] set to 100% so that the 'requires attention' group of fields will not contain it anymore" — [UiPath Forum: DU 2022.5 Community Preview](https://forum.uipath.com/t/document-understanding-2022-5-community-preview/442187). Validation can be attended ("Present Validation Station") or asynchronous via Action Center ("Create Document Validation Action" / "Wait for Document Validation Action and Resume") — [UiPath DU 2022.10 docs](https://docs.uipath.com/document-understanding/automation-suite/2022.10/classic-user-guide/data-extraction-validation-overview)
- **ABBYY Vantage Manual Review**: documents with any field failing a rule go to review; if an operator changes a value "it will be checked again using any applicable rules"; a data-catalog lookup rule reruns and a matching record makes the field read-only; verification modes include "Only verify documents that have rule errors, fields with low-confidence characters, or unknown document types" and "No documents are sent to review"; multi-stage review lets a senior operator re-review junior work — [ABBYY Vantage: Manual Review activity](https://docs.abbyy.com/vantage/documentation/skill-designer/process/manual-review); [ABBYY Vantage: Rule verification](https://docs.abbyy.com/vantage/documentation/skill-designer/document/rule-verification/rule-verification)
- ABBYY correction capture: if extracted data does not match, the reviewer "select[s] the correct region on the document image" and the system re-reads from that region; reassigning document type makes the system "more accurate at assigning this document type to similar documents" once results are saved; if training is disabled "corrections made in the Manual Review Client do not improve future processing" — [ABBYY Vantage: Online learning in Manual Review](https://docs.abbyy.com/vantage/documentation/runtime/manual-review/online-learning)
- **Microsoft grounding**: grounding "links an extracted value back to the document content that supports it"; merging grounding into the extraction flow "cut average inference token usage by up to 28% and improved accuracy"; it supports evidence display for reviewers, validation of value+evidence together, and an audit trail; in the insurance case field-level confidence rules populated **priority labels** in the HITL tool and "the labels directed attention and did not authorize automatic processing" because the data was sensitive — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)
- **A2I**: default worker template renders the Textract key-value and block inferences for the flagged keys only (`{{ task.input.selectedAiServiceResponse.blocks }}`); for `MissingImportantFormKey` the worker is asked to *locate* the key and value — [AWS docs](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-json-humantaskactivationconditions-textract-example.html)
- **Tamr Pairs page**: Tamr's suggestion (Match/No match) with High/Medium/Low confidence; "high-impact pairs" marked with a lightning bolt are the pairs Tamr is least sure about and "have the biggest effect on what Tamr Core learns", sorted to the top by default; reviewers should prioritise cases where Tamr is confident but wrong ("the feedback you provide by labeling these pairs is the most valuable"), label about a dozen No matches and a dozen Matches via similarity filters, "don't guess" — skip and leave a comment; curators and verifiers resolve conflicting responses; a confusion matrix under "Show details" is clickable to filter pairs — [Tamr docs: Reviewing Pairs](https://docs.tamr.com/new/docs/record-pairs-reviewer)
- Tamr Curator Hub (System of Record): each suggested duplicate carries High/Medium/Low match confidence and curators "click the label to see which fields match or partially match"; a 2026 "Feedback" section consolidates curation items and lets curators dismiss suggestions — [Tamr Cloud docs: Curating records](https://cloud.docs.tamr.com/docs/curating-records-in-the-system-of-record); [Tamr product updates July 2026](https://www.tamr.com/blog/tamr-product-updates-july-2026)
- **Reltio Potential Match Review page**: "Attributes that meet the match rules are highlighted automatically"; stewards compare up to 5 profiles side by side and decide "a match or not a match"; perfect matches merge automatically, similar-but-incomplete records become "Potential Matches" — [Reltio docs: Review potential matches](https://docs.reltio.com/model/consolidate-data/configure-match-rules-overview/review-potential-matches-overview)
- **Senzing explanations**: the `why` command "explains why two entities did not resolve"; output shows `MATCH_KEY` ("the list of features that contributed to the match, both positively and negatively") and the principle, which "is the actual reason for the match"; `how` shows "the step-by-step resolution path and ... exactly where the scoring fell short of the merge threshold" — [Senzing Entity Exploration tutorial](https://senzing.com/docs/tutorials/eda/eda_basic_exploration/). A competitor characterises this as "explanation without control" because rules and thresholds cannot be tuned — [Data Ladder whitepaper (competitor)](https://dataladder.com/whitepapers/best-senzing-alternative-for-entity-resolution/)
- **Rossum**: a field below threshold is not validated and has an empty `validation_sources`; "Validation error will always stop a document from being automated" at both confident and full levels; a field evaluated with a negative built-in check is not automated "even when its confidence score meets the threshold"; required fields must have a value — [Rossum Knowledge Base: Automation rules overview](https://knowledge-base.rossum.ai/docs/automation-rules-overview); [Rossum API guide](https://rossum.app/api/docs/openapi/guides/automation/)
- **Instabase Human Review Suite**: reviewers "compare extracted information with the original documents, correct results and manage review queues"; reviewer groups, assignment, escalation paths by document type, review-performance monitoring — [Instabase blog](https://instabase.com/blog/overcoming-the-limitations-of-llms-data-validation-and-human-review)
- **Hyperscience Supervision**: fields below threshold generate "Transcription Supervision" tasks; a Supervision entry is not scored as machine output but can establish consensus and measure human accuracy — [Hyperscience v43: Scoring Transcription Accuracy](https://help.hyperscience.ai/v43/docs/scoring-transcription-accuracy)

### Inferences
- The universal correction primitive is **"point at the right evidence, not just type the right answer"** (ABBYY region re-select, A2I locate-the-key, Tamr pair label with field highlight). For schema mapping the analogue is: the reviewer picks the *source column* (or sample cell) that should feed the target, not merely types a corrected value — that produces a reusable mapping rule, whereas a typed value produces only a one-row override.
- Corrections are **immediately re-validated by deterministic rules** (ABBYY re-runs rules and lookups; Rossum re-validates cleared fields) before being accepted. The human's edit is not trusted blindly either.
- Tamr's "label where the model is confident but wrong" and "high-impact pairs first" are explicit **active-learning queue ordering** — the review queue is sorted by expected learning value, not by document arrival. A mapping tool can rank review questions by (criticality × uncertainty × how many future rounds the answer would settle).
- Microsoft's insurance case shows confidence can be used purely as **triage/priority labels** without authorising auto-processing — a good first deployment mode for a review team that does not yet trust the model.

### Gaps
- No vendor documents the exact screen layout of its review client beyond prose; no screenshots or UX studies of Rossum/Hyperscience review clients were found in official docs.
- How UiPath corrections flow from Validation Station into Data Manager retraining was not covered by the fetched page (it defers to a separate "validation-station" page).

## KQ3. Which products retrain per customer vs globally, and how fast does a correction take effect?

### Takeaway
Nobody mature retrains a model on a single correction. The fast path is a **deterministic memory** (rules, templates, data-catalog lookups, UiPath's score→100% on edit) that takes effect immediately; model learning is **batched and gated** (ABBYY: retrain at +10% new documents, accept only if ≥ 1% accuracy gain; Hyperscience: nightly auto-thresholding on thousands of QA records; Tamr: explicit "Apply feedback and update results" job). Learning is per customer/skill/flow on top of shared foundation models.

### Cited Findings
- **ABBYY Vantage Online Learning** (Document and Classification skills only, not structured-document skills): collection starts at the first corrected document from a Manual Review Operator (a field region corrected, or a type changed); non-reviewed documents may be at most 33% of train+test; training set max 10,000, test set max 1,000 (oldest replaced when full); first 30 documents all go to training, then 80/20 split; once full, 80% of new documents are discarded and the rest split 80/20; the first learning session after a skill version is published starts when the set gains **10% new documents**, same after a successful session, dropping to **5%** after an unsuccessful one; "the skill is updated only if Online Learning yields at least a 1% accuracy increase"; testing uses the test set when ≥ 20 docs (else both sets / cross-validation); Online Learning **does not create a new skill version** — versions change only on publish — [ABBYY Vantage: Online Learning](https://docs.abbyy.com/vantage/documentation/runtime/online-learning/online-learning)
- **Hyperscience**: "Fine-tuning" (Transcription Automation Training) uses verified QA tasks to produce "fine-tuned confidence", lowering confidence on "high-confidence errors" and raising it on "low-confidence correct extractions"; "Auto-thresholding" uses the fine-tuned confidence to set thresholds meeting the target and "runs nightly and whenever a flow's ... Document Transcription settings change"; minimum thousands of QA records per field type before it engages (see KQ1) — [Hyperscience v42](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)
- Hyperscience consensus: "two entries for a given field must have matching normalized transcriptions"; a QA field is abandoned after 3 human entries without consensus or when two keyers mark it illegible; abandoned entries are excluded from accuracy metrics — [Hyperscience v43](https://help.hyperscience.ai/v43/docs/scoring-transcription-accuracy)
- **Tamr**: the "Apply Feedback and Update Results" job "trains the model using the latest verified pair feedback", applies it to all candidate pairs replacing system suggestions, clusters, assigns persistent IDs on first publish, and "generates new high-impact pairs"; "Update Results" only re-applies without training; recommend labelling "at least 50 pairs" (matches and non-matches) before the first training run; metrics (Accuracy, Precision, Recall, F score) are recomputed vs expert feedback each run and "do not indicate how accurate the model is for all pairs" — [Tamr docs: Curating Project Jobs and Viewing Metrics](https://docs.tamr.com/new/docs/record-pairs)
- **Rossum**: per an unofficial mirror of Rossum University, Aurora models "learn continuously from each document that is processed (user-confirmed) in the queue"; "depending on your version of the AI engine, changes may affect predictions either immediately or after an agreed-upon period"; the T-LLM foundation model and Aurora Engine "are shared across all of the customers" with customer- or use-case-specific Aurora models on top — [rossum.university mirror (unofficial)](https://mrtnzlml.github.io/rossum.university/docs/learn/ai-learning); Rossum's Aurora 1.5 launch markets "instant learning — our AI automatically gets better just from seeing your documents" — [Product Hunt: Rossum Aurora 1.5 & Copilot (marketing)](https://producthunt.com/products/rossum-aurora-1-5-copilot)
- **Nanonets Instant Learning Model**: "AI Confidence" starts at 0% and rises as files are approved, unlocking auto-approval at 90% — from search summary of [Nanonets docs: Models](https://docs.nanonets.com/docs/models) (direct fetch returned only front matter; treat as partially verified)
- **Microsoft**: customers do not retrain the confidence model; "they calibrate their workflow against their own checked examples" — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)
- **Google Document AI uptraining**: requires a minimum of 10 documents in both training and test sets and 10 instances of each label in each set; reviewed HITL output can be used as labelled data — [Google codelab: Document AI Workbench Uptraining](https://codelabs.developers.google.com/codelabs/docai-uptraining); [Google docs: Uptrain a pretrained processor](https://docs.cloud.google.com/document-ai/docs/workbench/uptrain-processor)
- **Reltio guidance**: "You should only switch to automatic merging after a lot of investigation and with a high confidence rating that all your matches are correct" — [Reltio Community (Daniel Gage)](https://community.reltio.com/blogs/daniel-gage/2021/09/26/data-governance-recognizing-and-consolidating); "Match tuning is the iterative process of developing match rules while minimizing bad matches, maximizing automation, and preserving system performance" — [Reltio Community (Joel Snipes)](https://community.reltio.com/blogs/joel-snipes1/2021/09/19/effective-match-tuning-design-and-implementation); Informatica frames match tuning as "iterative and repeatable depending on changes to match requirements" — [Informatica Velocity: MDM Match Tuning](https://success.informatica.com/velocity/stages/360-engagement/plan/best-practices/mdm-match-tuning.html)
- Contrast from a non-IDP product: Norman Finance's categorisation memory only auto-books a remembered pattern "once it has been confirmed at least twice" — one correction is not enough to act on automatically — [Norman Finance blog](https://norman.finance/de/en/blog/categorization-learns-from-corrections)
- Google patent on "human-augmented AI configuration and optimization insights" (HITL config/analytics) exists but is a patent, not product doc — [US12223015B2](https://patents.google.com/patent/US12223015)

### Inferences
- The mature pattern is **two loops with different latencies**: (a) a deterministic, per-sender memory that applies on the next document (template/rule/lookup/UiPath 100%), and (b) a gated statistical loop that only promotes a new model/threshold after enough verified evidence and a measured improvement (ABBYY ≥ 1%, Hyperscience thousands of QA records, Tamr explicit job). FORMA's "memory reuse → heuristics → agents" pipeline already matches loop (a); loop (b) is the place for calibrating `policies/approval.yaml` thresholds from review history, gated by `make eval-gate`-style non-regression.
- ABBYY's "online learning does not create a new skill version" is a deliberate split between *learned parameters* and *versioned configuration*; the published skill version is the rollback unit. For an append-only `MappingVersion` design, learned synonyms/weights should likewise live beside, not inside, the immutable version — or produce a new version with `parent_id` when they change behaviour.
- The "one correction, immediate effect" marketing (Rossum "instant learning") is deliberately hedged in their own docs ("depending on your version of the AI engine"). Honest UX: show the reviewer *what will change next time* (a remembered rule) rather than claiming the model learned.
- Tamr's "at least 50 pairs before first training" and Super.AI's "30 data points per field" give rough **minimum-evidence** numbers for turning on any automatic behaviour; Norman Finance's "confirmed twice" is the smallest defensible rule for per-sender memory.

### Gaps
- How quickly a Rossum Aurora correction affects the next document is engine-version dependent and not published with numbers.
- Nanonets' per-vendor behaviour and how corrections modify the instant-learning model were not retrievable from the docs fetch.
- No vendor publishes retrain-latency SLAs.

## KQ4. What deterministic plausibility checks are standard, and how are they layered with model confidence?

### Takeaway
Deterministic rules are **always senior to confidence**: a rule failure blocks automation regardless of score (Rossum, ABBYY, UiPath). The data-quality world supplies the standard check vocabulary — completeness/null share, uniqueness, allowed set, range/quantile, referential integrity, row count, and history-based anomaly detection on those same metrics — with a **warn vs fail** severity split and a tolerance ("mostly"/ratio) parameter.

### Cited Findings
**Layering in IDP**
- Rossum: "Rossum never exports a document that contains validation errors"; schema/connector validation errors block even at full automation; non-required fields with errors are cleared and re-validated, and if the error persists manual review is required; hidden fields "are not validated and do not affect document automation"; a negative built-in check blocks a field even above threshold; batch files blocked by default — [Rossum API guide](https://rossum.app/api/docs/openapi/guides/automation/); [Rossum Automation rules overview](https://knowledge-base.rossum.ai/docs/automation-rules-overview)
- ABBYY: rules "set up conditions that specific fields will need to satisfy"; any failing field sends the document to review; confidence (0–100 per field, below threshold flagged) is the second trigger; verification mode selects which trigger classes go to review — [ABBYY Manual Review](https://docs.abbyy.com/vantage/documentation/skill-designer/process/manual-review)
- UiPath lists "synthetic consistency checks (for example, confirming line items sum to a total or that an ID checksum is valid)" as the thing that lets you skip human validation — [UiPath DU 2022.10 docs](https://docs.uipath.com/document-understanding/automation-suite/2022.10/classic-user-guide/data-extraction-validation-overview)
- Microsoft: validate "value plus evidence together"; keep a field in review when confidence does not separate — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)

**Check vocabularies**
- Deequ (`Check(CheckLevel.Error, ...)` in a `VerificationSuite`): `hasSize`, `isComplete`, `isUnique`, `isContainedIn`, `isNonNegative`, `containsURL(col, _ >= 0.5)` (ratio tolerance), `hasApproxQuantile`; plus "Automatic suggestion of constraints" from profiling, "Anomaly detection" on metrics over time, a `MetricsRepository` for persisting metrics, and incremental metric computation on growing/partitioned data — [awslabs/deequ README](https://github.com/awslabs/deequ)
- dbt: four built-in generic tests `unique`, `not_null`, `accepted_values` (`values`), `relationships` (`to`, `field`); `severity` is `warn` or `error`; `error_if` / `warn_if` set custom failure-count thresholds; `store_failures` writes failing rows to `dbt_test__audit` so they can be inspected; results surface as `PASS/WARN/ERROR/SKIP` — [dbt docs: Data tests](https://docs.getdbt.com/docs/build/data-tests)
- Soda anomaly detection: `anomaly detection for row_count` / `avg(order_price)` / `freshness(start_date)` / `missing_count(id)` / `invalid_count(user_email)`; uses Facebook Prophet to learn trend and seasonality; needs **at least four measurements at a regular cadence** (result `[NOT EVALUATED]` until then; back-to-back scans do not count); users can mark an anomaly as expected so the check discounts it; `severity_level_parameters: warning_ratio: 0.1` (warning buffer beyond the confidence interval), `min_confidence_interval_ratio: 0.001`; `alert_directionality` upper/lower; `window_length` default 1000; the check is being deprecated in favour of a rebuilt version — [Soda docs: Anomaly detection](https://docs.soda.io/soda-cl/anomaly-detection)
- Great Expectations vocabulary: "Expectation: a verifiable assertion about data"; "Expectation Suite"; "Validation Definition" (suite ↔ data); "Checkpoint" (runs validation definitions with shared parameters and Actions, "the main way to validate data in production"); "Data Docs" (static sites of Expectations and Validation Results); "Validation Result" — [GX glossary](https://docs.greatexpectations.io/docs/reference/learn/glossary); a Data Assistant/profiler "examines the data, computes metrics, and proposes expectations" — [GX legacy glossary](https://legacy.016.docs.greatexpectations.io/docs/glossary)
- Monte Carlo: Table monitors ("learns the normal patterns of updates, size changes, and growth"), Metric monitors ("learns the behavior of a metric and alerts when those patterns are violated"), Validation monitors (templates or custom SQL), Job monitors; "users can choose between automated or manual thresholds"; each monitor has an Audience (who is notified), Priority (orders triage), and Tags — [Monte Carlo docs: Monitors overview](https://docs.getmontecarlo.com/docs/monitors-overview)
- Layering rationale: GX/Soda/dbt tests "catch what someone anticipated"; anomaly detection on volume, freshness, distribution and schema "catches issues nobody planned for" — e.g., a source silently dropping 30% of records passes schema and row-rule checks but trips a volume anomaly; a renamed column is caught by schema-change detection — [datalakehousehub comparison (secondary)](https://datalakehousehub.com/blog/data-quality-tooling-compared)
- Distribution drift of extraction output: a tutorial recommends comparing current field-value distributions to a baseline (e.g., KS test), noting such checks "need no labeled ground truth, so they catch shifts quickly but can't measure accuracy directly" — [The Neural Base (secondary tutorial)](https://theneuralbase.com/document-ai/learn/advanced/monitoring-extraction-accuracy/)

### Inferences
- The standard **per-field plausibility set** across these tools is: null share (`isComplete`/`not_null` with tolerance), uniqueness (`isUnique`/`unique`), allowed set (`isContainedIn`/`accepted_values`), numeric range/quantile (`hasApproxQuantile`, `isNonNegative`), referential integrity (`relationships`), pattern/format with ratio (`containsURL(_ >= 0.5)`), row count (`hasSize`), and *history-relative* versions of each (Soda/Deequ/Monte Carlo anomaly detection). For a mapping tool these map directly onto "does the proposed column, once transformed, look like this target field usually looks for this customer" — a sanity gate independent of the LLM's confidence.
- Two severities (**warn vs fail/error**) plus a **tolerance parameter** are universal; FORMA's `approval.yaml` auto-approve/review/block already mirrors warn/fail and should carry explicit tolerances (e.g., null share ≤ x) per field rather than binary checks.
- Soda's "mark as expected" and Monte Carlo's priority/audience show that **anomaly feedback is itself a correction channel**: a reviewer saying "this spike is fine" must be stored so the same alert is not raised next cycle.
- History-based checks need a warm-up (Soda ≥ 4 regular measurements, Deequ `MetricsRepository`); with a 14-day cadence that is ~2 months per customer, so drift detection must degrade gracefully to cross-customer priors for new senders.

### Gaps
- GX's `mostly` tolerance parameter and expectation names (e.g., `expect_column_values_to_be_between`) were not retrievable from the fetched pages (gallery page returned navigation only); known from general documentation but unverified here.
- Deequ's anomaly strategies (e.g., rate-of-change) are in example files not fetched.
- No IDP vendor publishes which plausibility rules it ships out of the box beyond "rules" and "built-in checks".

## KQ5. Review UX: smallest decision, question budgets, evidence, verify-by-exception, batching, confirmation fatigue — what does research and practice say?

### Takeaway
The HCI literature is unambiguous that **explanations alone increase deference**, that **confidence displays shape human confidence**, and that **cognitive forcing** (making the person commit or think first) reduces overreliance at a cost in satisfaction; practice counters fatigue with exception-only queues, sampling audits of auto-approved work, priority ordering, and measuring reviewer agreement rate over time.

### Cited Findings
- Buçinca, Malaya & Gajos (CSCW 2021, N=199): "Adding explanations to the AI decisions does not appear to reduce the overreliance and some studies suggest that it might even increase it"; people "rarely engage analytically with each individual AI recommendation and explanation, and instead develop general heuristics"; cognitive forcing functions "significantly reduced overreliance compared to the simple explainable AI approaches"; but "people assigned the least favorable subjective ratings to the designs that reduced the overreliance the most"; benefits accrued more to participants higher in Need for Cognition — [To Trust or to Think, PACM HCI CSCW1 2021, DOI 10.1145/3449287](https://kgajos.seas.harvard.edu/papers/bucinca21trust.pdf)
- Ma et al. (CHI 2024 / arXiv 2403.09552) "Are You Really Sure?": calibrating human **self**-confidence (three mechanisms compared) "improved human-AI team performance" and "encouraged more rational reliance on AI" versus uncalibrated baselines — [arXiv 2403.09552](https://arxiv.org/abs/2403.09552)
- Ma et al. (CHI 2023) "Who Should I Trust": compares showing AI confidence against a "correctness likelihood" display as the reliance aid — [paper PDF](https://shichuhan.github.io/paper/WhoShouldITrust.pdf)
- CHI 2025 work on confidence alignment found that aligning AI confidence to the human's often made people *less* calibrated — [NUS Computing feature (secondary)](https://www.comp.nus.edu.sg/features/ai-confidence-on-human-decision-making)
- "Approval fatigue": repeated permission requests turn careful review into habitual approval (term attributed to Hugging Face and Data & Society researchers); practitioner mitigations: rotate reviewers, a designated skeptic, audit missed errors, track review latency, rejection rate and per-reviewer agreement with the agent over time — [tianpan.co (secondary)](https://tianpan.co/blog/2026/06/25/approval-fatigue-how-human-in-the-loop-gates-decay-into-rubber-stamps); banking coverage of the same phenomenon — [American Banker: "Bored humans miss AI mistakes"](https://www.americanbanker.com/news/another-potential-ai-problem-bored-humans-miss-ai-mistakes)
- A 2024 HBS study is reported (secondhand) as finding reviewers more likely to agree with AI recommendations and narrative explanations increasing deference further — [tianpan.co (secondary; figures unverified)](https://tianpan.co/blog/2026/04/15/human-in-the-loop-rubber-stamp)
- EU AI Act Article 14 requires overseers of high-risk systems to "be alert to automation bias" — [govinfosecurity (secondary)](https://www.govinfosecurity.com/ai-agents-make-human-oversight-less-reliable-a-32768)
- A DEF CON 34 poster pilot on "comprehension gates" frames the problem as approval and verification diverging — [AI Village poster](https://aivillage.org/posters/stop-pressing-1-do-students-verify-before-they-approve-a-pilot-study-of/)
- Practice: Tamr tells reviewers they need not label every pair, to skip when unsure and comment, and to start with high-impact pairs — [Tamr docs](https://docs.tamr.com/new/docs/record-pairs-reviewer); Microsoft used confidence as priority labels while humans still checked everything — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/); Nyckel: prioritise reviewing low-confidence predictions because corrections there improve the model most — [Nyckel docs](https://edge.nyckel.com/docs/best-practices/review-and-improve-predictions/); UiPath Validation Station hides edited fields from the "requires attention" group — [UiPath Forum](https://forum.uipath.com/t/document-understanding-2022-5-community-preview/442187)
- Sampling of auto-approved work as the fatigue-free audit: A2I `Sampling` (e.g., 5% of high-confidence `Pay Date`), Hyperscience QA sampling with consensus, Microsoft "outer loop" of human-checked unflagged results — [AWS docs](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-json-humantaskactivationconditions-textract-example.html); [Hyperscience v43](https://help.hyperscience.ai/v43/docs/scoring-transcription-accuracy); [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)

### Inferences
- **Ask a choice, not a confirmation.** The research shows "confirm?" degrades to a rubber stamp. Choice-shaped questions ("which of these two source columns is the unit price?") are a mild cognitive forcing function and produce a labelled decision; a "yes" produces nothing the system can learn from. Where confirmation is unavoidable, demand the evidence be visible (sample values, source header) in the same glance.
- **Question budget = exception set + a small random audit sample.** Vendors do not ask about everything above threshold; they sample it (A2I 5%, Hyperscience QA). A per-round budget of N questions should be filled first by rule failures, then by below-threshold mappings ordered by criticality × learning value, then by a random sample of auto-approved items to keep calibration honest.
- **Batching by sameness.** Tamr's "use similarity filters to find other unlabeled pairs where Tamr Core makes the same kind of mistake" suggests grouping identical question types across rounds/customers (e.g., all "is this Thai date Buddhist-era?" questions) so one decision closes many.
- **Measure the reviewer, not just the model.** Hyperscience scores keyer accuracy via consensus; practitioners track agreement rate and latency. A rising approve-everything rate with falling time-per-item is the fatigue signal.
- Expect the designs that work best (forced choice, hidden AI answer until the human commits) to be rated least pleasant; budget the number of such moments per session.

### Gaps
- No peer-reviewed study of review interfaces for *schema mapping* or *column matching* specifically was found; findings are from decision-support and document tasks.
- The HBS deference figures (228 evaluators etc.) could not be verified against the primary paper.
- No vendor publishes a recommended "questions per document" budget.

## KQ6. Organisational metrics exposed (STP, review time, correction rate, accuracy by sender) and handling of recurring senders (per-sender templates/memory, drift detection on layout change, versioning with rollback)

### Takeaway
The metrics that matter are **automation/STP rate, accuracy measured on human-verified samples, and accuracy/automation by field and by segment (document type, source)**; recurring senders are handled by versioned layouts/skills/schemas that are matched only when "Live"/published, with learned parameters kept outside the version, and drift is detected as distribution or schema change rather than by the model's own confidence.

### Cited Findings
**Metrics**
- Hyperscience: automation = fields with no human; accuracy per field scored via QA consensus; "Transcription QA" samples a user-defined share of fields; "accuracy cannot be measured if this setting is disabled"; keyer accuracy = matches QA consensus; completed QA entries count toward keyer productivity — [Hyperscience v42 Transcription settings](https://help.hyperscience.ai/v42/docs/transcription-settings); [Hyperscience v43 Scoring](https://help.hyperscience.ai/v43/docs/scoring-transcription-accuracy)
- Rossum: "Automation data" table drives threshold adjustment; `validation_sources` records *why* a field was accepted (`["score"]`) — [Rossum Knowledge Base](https://knowledge-base.rossum.ai/docs/using-ai-confidence-thresholds-for-automation-in-rossum)
- Tamr: Accuracy, Precision, Recall, F score vs expert feedback, recomputed per training run, "track them for upward trends"; confusion-matrix quadrants filter the queue — [Tamr docs](https://docs.tamr.com/new/docs/record-pairs)
- Microsoft: error coverage of the review set (>80%), review-volume reduction (41% fewer values; ~50% burden reduction), separability per field, and an explicit warning that "41% fewer field values" does not mean 41% less staff time — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)
- Instabase: review-performance monitoring per reviewer group; third-party summary claims every decision is logged with document input, extracted values, confidence, human overrides and downstream callbacks — [Instabase blog](https://instabase.com/blog/overcoming-the-limitations-of-llms-data-validation-and-human-review); [aitoolsatlas (secondary)](https://aitoolsatlas.ai/tools/instabase/review)
- STP definition: "the share of invoices that clear every step (capture, matching, coding, and approval) automatically", stricter than touchless; recommended to segment by invoice type since PO-backed vs non-PO rates differ widely — [Kognitos (vendor)](https://www.kognitos.com/blog/accounts-payable-kpis-metrics-that-matter-2026/); [invoicedataextraction.com](https://invoicedataextraction.com/blog/touchless-invoice-processing)
- Monte Carlo attaches Audience, Priority and Tags (team ownership, data contracts) to each monitor for triage and reporting — [Monte Carlo docs](https://docs.getmontecarlo.com/docs/monitors-overview)

**Recurring senders, versioning, drift**
- Hyperscience layouts: every layout has a "working version"; committing creates a new "committed version" and a fresh working copy; a version bundles all variations, the shared field list and field customisations (variations cannot be versioned alone); a version is "Live" only when in a current release and "the system can only match submission pages to Live versions" — [Hyperscience: What is a Layout Version? (v40)](https://help.hyperscience.ai/v40/docs/what-is-a-layout-version); [Layout versions (v42)](https://help.hyperscience.ai/v42/docs/layout-versions.md); [Layout management overview (v41)](https://help.hyperscience.ai/v41/docs/layout-management-overview.md)
- ABBYY: online learning adapts a skill at runtime but "does not create a new skill version"; versions change only on publish; the first learning session after a publish needs 10% new documents — [ABBYY Online Learning](https://docs.abbyy.com/vantage/documentation/runtime/online-learning/online-learning)
- Tamr: persistent cluster IDs are assigned on the initial publish; later runs replace system suggestions but keep IDs — [Tamr docs](https://docs.tamr.com/new/docs/record-pairs)
- Extend (vendor marketing, April 2026): schema versioning with draft/test/publish, regression testing, routing document types to different schema versions by confidence, and "instant rollback" when accuracy drops after deployment; claims competitors lack rollback (unverified) — [Extend blog](https://www.extend.ai/resources/schema-versioning-tools-document-ai-pipelines)
- Drift: monitor extraction output distributions vs baseline (KS test on field values) to catch "when document format changed" without labels — [The Neural Base (secondary)](https://theneuralbase.com/document-ai/learn/advanced/monitoring-extraction-accuracy/); Soda/Monte Carlo schema-change and volume anomaly detection catch renamed columns and silent record drops — [datalakehousehub (secondary)](https://datalakehousehub.com/blog/data-quality-tooling-compared); [Soda docs](https://docs.soda.io/soda-cl/anomaly-detection)
- Microsoft: segment calibration by "form family, version, and source" and revalidate "when monitoring shows drift" — [Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)
- Rossum: customer-specific Aurora models sit on a shared foundation; Rossum University describes learning scoped to the queue — [rossum.university mirror (unofficial)](https://mrtnzlml.github.io/rossum.university/docs/learn/ai-learning)

### Inferences
- The minimal metric set for an ops team, drawn from the above: (1) **auto-approve rate** per customer and overall (Rossum/Hyperscience "automation"), (2) **error rate on a human-verified sample of auto-approved items** (Hyperscience QA, Microsoft outer loop) — the only honest accuracy number, (3) **review items per round and time per item**, (4) **override/correction rate** by field and by customer trending down, (5) **reviewer agreement rate with the proposal** trending up *without* (2) worsening. Report by segment (customer, field criticality, ERP family) because single global numbers hide the bad senders.
- **"Only Live versions match"** (Hyperscience) is the key per-sender pattern: a sender's approved mapping is the matchable template; a new layout that does not match a Live version is itself the drift signal and should open a review task rather than silently falling back to the model. FORMA's fingerprint-vs-approved-format check is this pattern.
- Drift should be detected by **three independent signals**, none of which is the LLM's confidence: schema/header change (column set, order, names), volume (row count vs history), and value-distribution change per mapped field (KS or quantile shift). With a 14-day cadence, history is thin; use the sender's last approved round as the baseline and cross-customer priors before that.
- Keep learned per-sender parameters (synonyms, confirmed column→field memory) **outside** the immutable mapping version (ABBYY pattern), and make "publish" the only rollback-able boundary.

### Gaps
- No vendor publishes review-time-per-document or correction-rate-over-time dashboards in docs; these are described only generically (Instabase "performance monitoring").
- How Hyperscience or Rossum *detect* a sender's layout change (vs just failing to match) is not documented publicly.
- Klippa: nothing found on any of these topics.
- No published accuracy-by-sender data from any vendor.

## Cross-cutting transferable design patterns (synthesis of the above; each traces to the cited findings)

1. **Error budget in, threshold out.** Operator sets target accuracy / error coverage per field criticality; thresholds are derived from verified review history and shown as implied error rate, never as a bare probability (Hyperscience, Microsoft, Rossum caveats).
2. **Rules outrank scores.** Any deterministic plausibility failure blocks auto-approval regardless of confidence (Rossum, ABBYY, UiPath); the human's correction is re-validated by the same rules (ABBYY).
3. **Three bands plus a sample.** Auto / review / block, and a deterministic random sample of auto-approved items for calibration (A2I `Sampling`, Hyperscience QA, Microsoft outer loop).
4. **Missing is its own question.** Unmapped/empty target fields get a distinct policy and task type (A2I `MissingImportantFormKey`, Microsoft empty-field policy).
5. **Corrections point at evidence.** Reviewer picks the source (column/region), producing a reusable rule, not just a value (ABBYY region re-select, Tamr pair label).
6. **Two learning loops.** Immediate deterministic memory per sender; batched, gated statistical update with minimum evidence and measured gain (ABBYY 10%/≥ 1%, Tamr ≥ 50 labels, Norman "confirmed twice").
7. **Queue ordered by learning value and criticality**, with skip-and-comment allowed and "confident but wrong" prioritised (Tamr high-impact pairs).
8. **Choice over confirmation; budget the asks; batch identical questions** (Buçinca cognitive forcing; approval-fatigue literature; Tamr similarity filters).
9. **Versioned, published templates are the only matchable thing**; learned parameters live outside the version; no-match is the drift alarm (Hyperscience Live versions, ABBYY skill versions).
10. **Measure humans and model together**: automation rate, verified-sample error rate, override rate by field/sender, reviewer agreement and latency (Hyperscience keyer accuracy, Tamr metrics, practitioner fatigue metrics).
