# Agent self-verification for data transformations, code and queries — state of the art (2023–2026), transferable to a spreadsheet→schema mapping agent

Scope note: the FORMA mapping agent emits a declarative `MappingDocument` (not code), the engine runs it deterministically, and a policy engine routes to review. So the most transferable evidence is (a) execution-grounded feedback loops where an external oracle (compiler, tests, row counts, schema validator) tells the model it is wrong, (b) best-of-n with a cheap deterministic verifier, (c) separate critic/judge agents and their known biases, (d) deterministic guards (schema-constrained output + validator + bounded repair loop), and (e) confidence→review routing. Everything below is tagged with the primary source where one was reachable; vendor claims are labelled as such.

---

## Key Question 1 — Which verification designs measurably reduce error, by how much, and at what cost?

### Takeaway
Verification helps only when the signal comes from outside the model (execution results, unit tests, compiler, a stronger critic, or a human); "intrinsic" self-correction with no external signal is roughly neutral to harmful. Where an external oracle exists, the measured gains are large: +12 pts absolute (Self-Debugging on TransCoder/MBPP), 19%→44% pass@5 (AlphaCodium), 25.7%→32.0% from test-based patch selection (Agentless), 45.8%→57.4% from verifier-based selection (CodeMonkeys), 15.9%→56% coverage from 250 samples + oracle verifier (Large Language Monkeys). Cost ranges from "one extra call" (Self-Debugging, one turn) to 15–20 calls per solution (AlphaCodium) to $0.70/issue (Agentless) and ~$7.7/instance (CodeMonkeys, $2,300/300 instances).

### Cited Findings

**Execution-feedback loops (single generator re-prompted with results)**
- Self-Debugging (Chen et al., 2023): on TransCoder and MBPP (unit tests available) accuracy improves "by up to 12%" absolute over the baseline; with code explanation added to the feedback, a consistent further +2–3 pts and +9 pts on the hardest problems; it "can match or outperform baseline models that generate more than 10× candidate programs" — [arXiv 2304.05128](https://arxiv.org/abs/2304.05128)
- Self-Debugging detail tables (GPT-4): TransCoder 77.3 → 80.9 (simple feedback) → 88.8 (unit-test feedback) → 90.4 (+explanation); MBPP 72.8 → 78.8 → 80.6 → 80.4. On Spider (text-to-SQL, no tests, only "does it run"), GPT-4 goes 73.2 → 73.4 → 73.6 — essentially nothing; Codex gains 81.3 → 84.1 only with explanation — [arXiv 2304.05128 (full text)](https://arxiv.org/html/2304.05128)
- Follow-up (ACL 2025, "Revisit Self-Debugging with Self-Generated Tests"): post-execution self-debugging "struggles with the test bias introduced by self-generated tests, which can lead to misleading feedback"; in-execution self-debugging (intermediate states) mitigates the bias — [ACL 2025 long.881](https://aclanthology.org/2025.acl-long.881)
- Reflexion (Shinn et al., NeurIPS 2023): 91% pass@1 on HumanEval vs 80% prior SOTA (GPT-4); but on MBPP Python Reflexion *hurts* (0.80 → 0.77) because self-generated tests had a 16.3% false-positive rate on MBPP vs 1.4% on HumanEval — a false positive makes the agent submit a wrong solution prematurely; authors: "false negatives are preferred over false positives". Rust ablation on 50 hardest HumanEval problems (GPT-4): baseline 0.60, full Reflexion 0.68, Reflexion without test generation 0.52, without self-reflection 0.60 — [arXiv 2303.11366](https://arxiv.org/abs/2303.11366), [full text v4](https://arxiv.org/html/2303.11366v4)
- Self-Refine (Madaan et al., NeurIPS 2023): same LLM as generator/feedback/refiner, no training; outputs preferred over single-pass GPT-3.5/GPT-4 by "~20% absolute on average" across 7 tasks; Code Optimization score 27.5 with specific self-feedback vs 26.0 with generic feedback vs 24.8 with no feedback — [arXiv 2303.17651](https://arxiv.org/abs/2303.17651)
- CRITIC (Gou et al., ICLR 2024): black-box LLM verifies and revises its output by calling external tools (search engine, code interpreter); consistent gains on free-form QA, mathematical program synthesis and toxicity reduction; each verify-and-correct iteration adds latency; the paper's central point is that *tool-interactive* critiquing works where purely intrinsic critique does not — [arXiv 2305.11738](https://arxiv.org/abs/2305.11738)
- LATS (Zhou et al.): MCTS over LLM actions + LM value function + self-reflection + environment feedback; 92.7% pass@1 HumanEval with GPT-4; 75.9 average score on WebShop with GPT-3.5 — [arXiv 2310.04406](https://arxiv.org/abs/2310.04406)

**The negative result that bounds all of the above**
- Huang et al. (Google DeepMind, ICLR 2024), "LLMs Cannot Self-Correct Reasoning Yet": under *intrinsic* self-correction (no external feedback, no oracle labels) reasoning performance often *drops*; models alter initially correct answers into wrong ones; earlier positive results relied on oracle labels; multi-agent debate gains are "primarily attributable to self-consistency" (aggregating multiple generations) rather than critique; recommends "high-quality external feedback from humans, training data, and tools" — [arXiv 2310.01798](https://arxiv.org/abs/2310.01798)
- Olausson et al., "Is Self-Repair a Silver Bullet for Code Generation?": at matched sample budget, GPT-4 self-repair on APPS reaches only 1.05× pass@20 (10 initial samples + 1 repair each) and 0.97× (2 initial + 10 repairs each); gains "up to 8%" for GPT-4/APPS, marginal for GPT-3.5/APPS; CodeLlama-13b on HumanEval up to +10%. Replacing the model's own feedback with a *stronger* model's feedback beat both baselines at all budgets. With human feedback GPT-4 repair success went 33.3% → 52.6% (1.58×); GPT-4's self-feedback was judged "obviously inaccurate" in 32/80 cases vs 7/80 for humans; GPT-4 never expressed uncertainty, humans did in 7/80. Conclusion: self-repair is bottlenecked by the model's ability to produce accurate feedback about why its own output is wrong — [arXiv 2306.09896](https://arxiv.org/abs/2306.09896), [full text](https://arxiv.org/html/2306.09896)

**Test-first / flow-engineered pipelines**
- AlphaCodium (Ridnik et al., 2024): CodeContests pass@5, GPT-4 validation 19% → 44%, test 12% → 29%; GPT-3.5 validation 15% → 25%, test 8% → 17%; DeepSeek-33B validation 7% → 20%, test 12% → 24%. Flow: problem reflection → public-tests reasoning → generate 2–3 candidate solutions → rank → generate 6–8 AI tests → initial code → iterate on public tests → iterate on AI tests. Design principles that transfer: YAML structured output "avoids the quoting and escaping problems of JSON"; "soft decisions with double validation" (re-generate and correct rather than yes/no check); "postpone decisions" (keep ranked candidates); "test anchors" (tests that already pass are kept so a fix for a new test may not regress). Cost ≈ 15–20 LLM calls per solution (~100 for pass@5) vs ~1M estimated for AlphaCode pass@10@100K — [arXiv 2401.08500](https://arxiv.org/abs/2401.08500), [full text](https://arxiv.org/html/2401.08500v1)

**Best-of-n + verifier / selection (sample many, pick with a checker)**
- Agentless (Xia et al., 2024): SWE-bench Lite 96/300 = 32.00% resolved at $0.70/issue (~78k tokens). Patch selection ablation: majority vote only 25.67% ($0.00) → + regression tests 27.00% ($0.01) → + reproduction tests 32.00% ($0.25). 40 patches per bug (4 location sets × 10) and 40 reproduction tests per issue; "repair performance plateaus at about 40 samples". Upper bound if any sampled patch counts: 126/300 = 42.0% — i.e. selection, not generation, is the bottleneck — [arXiv 2407.01489](https://arxiv.org/abs/2407.01489), [full text](https://arxiv.org/html/2407.01489)
- CodeMonkeys (Stanford, 2025): SWE-bench Verified 57.4% with Claude 3.5 Sonnet; random selection among candidates 45.8%, oracle selection (coverage) 69.8% — selection via generated tests + model vote "closes approximately half of the gap"; applied to an ensemble of top submissions the selector reaches 66.2%, beating the best member; 10 candidate (edit, test) pairs per instance, state machines capped at 8 iterations; total cost $2,300 for 500 instances — [scalingintelligence.stanford.edu/pubs/codemonkeys](https://scalingintelligence.stanford.edu/pubs/codemonkeys), [arXiv 2501.14723](https://huggingface.co/papers/2501.14723)
- Large Language Monkeys (Brown et al., 2024): coverage (≥1 correct sample) grows log-linearly with samples over ~4 orders of magnitude; DeepSeek-V2-Coder-Instruct on SWE-bench Lite 15.9% (1 attempt) → 56% (250 attempts), above the 43% single-attempt SOTA of a stronger model. Crucial caveat: this only converts into real performance where an automatic verifier exists (unit tests); "majority voting and reward models plateau after several hundred samples" where it doesn't; "building robust verifiers is still an open problem" — [arXiv 2407.21787](https://arxiv.org/abs/2407.21787)
- Self-consistency (Wang et al., ICLR 2023): majority vote over sampled reasoning paths, PaLM-540B GSM8K 56.5% → 74.4% (+17.9 pts absolute); unweighted majority vote ≈ probability-weighted vote — [arXiv 2203.11171](https://arxiv.org/abs/2203.11171)
- Process reward models (Lightman et al., "Let's Verify Step by Step", ICLR 2024): PRM solves 78.2% of a MATH test subset, beating outcome-supervised reward models; released PRM800K (800k step labels) — [arXiv 2305.20050](https://arxiv.org/abs/2305.20050)

**Separate critic / verifier agents**
- CriticGPT (OpenAI, "LLM Critics Help Catch LLM Bugs"): critiques preferred over human critiques 63% of the time on naturally-occurring bugs and >80% on inserted bugs; Human+CriticGPT vs Human win rate 60.4% (CI 58.0–62.8); Human+CriticGPT teams "hallucinate and nitpick less than both CriticGPT and ChatGPT" but absolute rates "are still quite high"; a length penalty traces a Pareto curve: longer critiques catch more bugs and hallucinate more; matching CriticGPT by scaling alone would need ~30× pre-training compute — [arXiv 2407.00215](https://arxiv.org/abs/2407.00215)
- SWE-agent (Yang et al., 2024): a *deterministic* guard in the edit tool — a linter that rejects syntactically broken edits before they are applied — is worth +3.0 pts (18.0% vs 15.0% resolved on SWE-bench Lite with GPT-4 Turbo); no edit command at all 10.3%; the whole agent-computer interface adds 10.7 pts over a shell-only agent — [arXiv 2405.15793](https://arxiv.org/abs/2405.15793), [full text](https://arxiv.org/html/2405.15793v3)
- Anthropic, "Building effective agents": the evaluator-optimizer workflow ("one LLM call generates a response while another provides evaluation and feedback in a loop") "is particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value"; agents should "gain 'ground truth' from the environment at each step (such as tool call results or code execution)"; for coding agents "solutions are verifiable through automated tests", with human review still needed for alignment with broader requirements — [anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents)
- Claude Code best practices: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually is done, 'looks done' is all it has to go on"; recommends a pass/fail check (test file, typecheck, screenshot next to mockup), escalating enforcement from prompt → `/goal` (separate model checks the condition after every turn) → `Stop` hook (harness re-runs the check and blocks the turn) → review "by someone who didn't write the code" in "a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code"; always ask for *evidence* (the command and its output); "A reviewer that's asked to find problems will always find something" — scope the reviewer; a "failing test it has to turn green" is a recommended definition of done — [code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices)
- OpenAI Codex (May 2025 launch coverage): runs each task in an isolated sandbox, "iteratively runs code and tests until it reaches a correct solution, then commits changes and provides test outputs and logs" — [InfoQ](https://infoq.com/news/2025/05/openai-codex)
- Agent-as-a-Judge (Zhuge et al., Meta/KAUST): an agentic judge (reads the workspace, runs things) matched a 3-expert human consensus on 86.6–92.1% of DevAI code-generation requirements vs 68.9–71.9% for a plain LLM judge; evaluation cost/time cut ~97% (86 h / $1,297 → ~2 h / $31). Caveat from reviewers: only 55 coding tasks — [arXiv 2410.10934](https://arxiv.org/abs/2410.10934)

**Schema-matching-specific pipelines (closest analogue to a mapping agent)**
- Matchmaker (Seedat & van der Schaar, NeurIPS 2024 workshops; ICML 2025 follow-up): zero-shot LLM program for schema matching = multi-vector retrieval (ColBERT-v2, top-5) + LLM chain-of-thought candidate proposals → refiner LLM → confidence scoring as a multiple-choice question with an explicit "none of the above" abstain option, each candidate scored 0–100. Self-improvement with no labels: build an eval set from unlabeled schemas (easy = top-5 similarity > 0.95, hard = weakest matches), LLM evaluator scores traces 0–5, best traces become ≤4 synthetic in-context demos per stage (DSPy-style bootstrapping). acc@1: MIMIC-OMOP 62.2 (vs ReMatch 42.5, LLM-DP 29.6, Jellyfish-13b 15.4, supervised SMAT 6–11); Synthea-OMOP 70.2 (vs ReMatch 50.5). Self-improvement ablation acc@1: optimized 62.2 vs vanilla 57.9 vs "self-reflection" 57.1 (MIMIC) — i.e. bootstrapped demos beat asking the model to reflect; reasoning-based candidates contribute more than semantic retrieval (reasoning-only 61.6 vs semantic-only 60.2 on MIMIC). Deferring the highest-entropy confidence cases to an oracle at 0–50% deferral rates improved accuracy more than random deferral — [arXiv 2410.24105](https://arxiv.org/abs/2410.24105), [full text](https://arxiv.org/html/2410.24105v1), [ICML 2025 version](https://mlanthology.org/icml/2025/seedat2025icml-bootstrapping)
- Magneto (NYU, VLDB 2025): small-model retrieval + LLM reranking for schema matching; the small models are fine-tuned self-supervised on LLM-generated synthetic variants; the paper's stated motivation is that cheap small-model retrieval "reduces how many candidates the costlier LLM must check" without hurting accuracy (figures given as MRR/runtime curves, not extracted here) — [arXiv 2412.08194](https://arxiv.org/html/2412.08194v2)

**Text-to-SQL correction layers (academic)**
- SQLens (2025): applying a grounded error-detection/correction layer lifts CHESS on BIRD 67.91% → 69.74%; "LLM self-reflection breaks the most correct queries, highlighting the need for grounded, signal-driven correction" — [arXiv 2506.04494](https://arxiv.org/pdf/2506.04494)
- MAGIC (2024): automatically generated self-correction guidelines lift MAC-SQL 59.39 → 61.92 and outperform expert-written guidelines — [arXiv 2406.12692](https://arxiv.org/abs/2406.12692)
- LitE-SQL (2025): execution-guided self-correction; "the first self-correction pass yields the largest accuracy gain on BIRD... subsequent passes... diminish progressively" — [arXiv 2510.09014](https://arxiv.org/pdf/2510.09014)

**Small model + verification loop vs bigger model single-shot (cost/accuracy)**
- Snell et al. (ICLR 2025 oral): FLOPs-matched, a smaller model with compute-optimal test-time search against a PRM verifier beats a 14× larger model — but only "on problems where a smaller base model attains somewhat non-trivial success rates"; on the hardest problems the larger model still wins; compute-optimal allocation is >4× more efficient than plain best-of-N — [arXiv 2408.03314](https://arxiv.org/abs/2408.03314)
- Mixture-of-Agents (Wang et al., ICLR 2025): layered open-source proposers + aggregator reach 65.1% LC win rate on AlpacaEval 2.0 vs 57.5% for GPT-4o (05/13); MoA-Lite is comparable to GPT-4o at lower cost — preference-style benchmark, not a correctness benchmark — [arXiv 2406.04692](https://arxiv.org/abs/2406.04692)
- Agentless vs agents: 32.0% at $0.70/issue (and 27.33% at $0.34/issue in v1) vs contemporaneous agent systems that cost several dollars per issue — the paper's thesis is that a fixed localize→repair→validate pipeline matches or beats autonomous agents at a fraction of the cost — [arXiv 2407.01489](https://arxiv.org/abs/2407.01489)
- Large Language Monkeys: a weaker model + 250 samples + oracle verifier (56%) beats a stronger model single-shot (43%) on SWE-bench Lite — [arXiv 2407.21787](https://arxiv.org/abs/2407.21787)

### Inferences
- For FORMA the cheap, high-yield designs are the ones with a *deterministic oracle*: simulate the mapping on the real sheet and feed back schema-validation failures, null/parse rates per field, identity-key duplicates, row counts and sample output rows. That is Self-Debugging "unit-test feedback" (+8–12 pts) and the SWE-agent linter (+3 pts) rolled into one, and it costs one extra model call.
- "Ask the model to re-read its mapping and fix it" with no new information is the Huang et al. / Olausson regime: expect ≈0 to slightly negative. The Self-Debugging Spider row (73.2 → 73.6) is the closest published analogue to a declarative-query task with only a "does it run" oracle — almost no gain. The gain comes from *what the oracle can detect*, so invest in richer deterministic checks rather than more rounds.
- Best-of-n + deterministic scorer (sample 3–5 mapping candidates, score each by validation pass rate / coverage / identity integrity, keep the best) is the pattern with the strongest evidence (Agentless, CodeMonkeys, Monkeys) and maps directly onto a mapping DSL because candidates are cheap to simulate. Majority vote across candidate mappings per field is a free extra signal (Wang et al.; Agentless uses it before test filtering).
- Matchmaker is the closest existing blueprint: candidate generation from two sources (retrieval + reasoning), refinement, confidence scoring with an explicit abstain option, entropy-based deferral to a human. Its ablation also shows that bootstrapped in-context examples from *past successful runs* beat self-reflection — supporting FORMA's "memory reuse → heuristics → agent" ordering.
- The small-model + verifier result (Snell) is conditional on the small model having a non-trivial base success rate; for FORMA that argues for a cheap model on routine layouts already seen (drift re-mapping) and a frontier model single-shot on novel/hard layouts, with the verifier deciding which regime a round is in.

### Gaps
- No paper was found that measures a verification loop specifically on *spreadsheet→schema mapping DSL generation*; the closest are schema matching (Matchmaker/Magneto — column-pair matching, not transformations) and text-to-SQL.
- Cognition's "Don't build multi-agents" essay could not be fetched directly; only secondary summaries (single thread of execution, shared context) were seen.
- The ICML 2025 Matchmaker follow-up's numbers were not retrieved.

## Key Question 2 — How many self-check rounds are worth it before diminishing returns?

### Takeaway
Across code, SQL and text tasks the first execution-grounded round captures most of the gain; by round 3 the curve is flat, and without an external oracle extra rounds can regress correct outputs. Production systems cap loops explicitly (AlphaCodium ~15–20 calls total, CodeMonkeys 8 iterations, Instructor 2–3 retries, Anthropic "maximum number of iterations" as a stopping condition).

### Cited Findings
- Self-Debugging: maximum 10 turns allowed, but "successful debugging mostly finishes within 3 turns"; "typically one debugging turn is sufficient"; on Spider accuracy changes by <0.1% after the first turn; on TransCoder a single turn with full feedback improves greedy accuracy by ~12% — [arXiv 2304.05128 full text](https://arxiv.org/html/2304.05128)
- Self-Refine: "the marginal improvement naturally decreases with more iterations" (Constrained Generation 29.0 → 49.7 over three iterations, Figure 4 shows flattening); on multi-aspect tasks quality can improve in one aspect while declining in another — [arXiv 2303.17651](https://arxiv.org/abs/2303.17651)
- Reflexion: AlfWorld keeps improving over 12 trials (130/134 tasks), with "an immediate jump between the first two trials, then steady gains"; ReAct-only stalls at trials 6–7 with a 22% hallucination rate; HotPotQA runs stop after 3 consecutive failures — [arXiv 2303.11366 full text](https://arxiv.org/html/2303.11366v4)
- LitE-SQL (BIRD): first self-correction pass gives the largest gain, later passes "diminish progressively" — [arXiv 2510.09014](https://arxiv.org/pdf/2510.09014)
- Agentless: "repair performance plateaus at about 40 samples" because majority voting after test filtering outweighs later samples — [arXiv 2407.01489 full text](https://arxiv.org/html/2407.01489)
- Olausson et al.: with GPT-4 on APPS, 2 initial samples + 10 repairs each is *worse* than i.i.d. sampling (0.97×), while 10 initial + 1 repair is 1.05× — breadth beats depth of repair at fixed budget — [arXiv 2306.09896 full text](https://arxiv.org/html/2306.09896)
- Huang et al.: without oracle labels, more intrinsic self-correction rounds decrease performance and flip correct answers to wrong — [arXiv 2310.01798](https://arxiv.org/abs/2310.01798)
- CodeMonkeys limits all state machines to 8 iterations and 10 candidates per instance — [scalingintelligence.stanford.edu/pubs/codemonkeys](https://scalingintelligence.stanford.edu/pubs/codemonkeys)
- AlphaCodium total budget ≈ 15–20 LLM calls per solution across all stages, including both test-iteration loops — [arXiv 2401.08500 full text](https://arxiv.org/html/2401.08500v1)
- Anthropic: "stopping conditions, such as a maximum number of iterations, help maintain control" — [anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents)
- Instructor (structured-output library): `max_retries` counts retries on top of the first attempt; validation errors are formatted as feedback and re-asked; docs examples use 2–3; exhausted retries raise `InstructorRetryException` for the caller to handle — [python.useinstructor.com/concepts/retrying](https://python.useinstructor.com/concepts/retrying/)
- Snowflake's Cortex Analyst optimization feature "may run each query up to four times" and warns that >20 verified queries makes optimization slow — [Snowflake docs: analyst-optimization](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst/analyst-optimization)

### Inferences
- A sensible default for a mapping agent: 1 grounded repair round by default, a hard cap of 2–3, and spend any remaining budget on *more candidates* (breadth) rather than more rounds on one candidate (depth), per Olausson and Agentless.
- Stop early when the deterministic score stops improving between rounds (Agentless' plateau logic), and never accept a round whose score is lower than the best seen — "keep the best candidate" is implied by every best-of-n paper and by AlphaCodium's test anchors.
- Because declarative mappings can be simulated in milliseconds, the economic constraint is LLM calls, not execution; the measured plateau at 1–3 rounds means a per-round budget of ~3 calls (propose, critique, repair) is already generous.

### Gaps
- No source gives a per-round curve for a *mapping* or *schema-matching* task; the 1–3 round plateau is extrapolated from code/SQL.
- Reflexion's 12-trial improvement on AlfWorld is a sequential decision task with a true environment reward; it is not evidence that 12 rounds help on a one-shot artefact.

## Key Question 3 — What makes execution feedback effective (what to show the model: errors only, samples, diffs, metrics)?

### Takeaway
The feedback that works is specific, external, and compact: unit-test / assertion results with expected-vs-actual beat "it failed" (Self-Debugging +4–8 pts over simple feedback), a natural-language explanation of what the artefact does adds 1–3 pts, raw execution traces help less than tests and sometimes hurt, overly long context hurts (SWE-agent), and the most valuable feedback is information the generator did not have (LinkedIn). Feedback from a stronger model or a human is worth far more than feedback from the generating model itself (1.58× for human feedback).

### Cited Findings
- Self-Debugging feedback ladder (GPT-4, TransCoder): baseline 77.3 → "simple" (just says wrong) 80.9 → unit-test feedback (which tests failed, expected vs actual) 88.8 → + code explanation 90.4 → + execution trace 89.5 (trace slightly below explanation; for Codex trace 87.9 vs UT 91.6, i.e. traces hurt). MBPP (GPT-4): simple 78.8, UT 80.6, +Expl 80.4, +Trace 80.2 — [arXiv 2304.05128 full text](https://arxiv.org/html/2304.05128)
- Self-Refine: specific, actionable self-feedback 27.5 vs generic feedback 26.0 vs none 24.8 (Code Optimization) — [arXiv 2303.17651](https://arxiv.org/abs/2303.17651)
- Olausson et al.: feedback quality is the bottleneck — human feedback 52.6% vs GPT-4 self-feedback 33.3% repair success; GPT-4's own feedback "obviously inaccurate" in 32/80 cases; a stronger model's feedback improves a weaker model's repair at every budget — [arXiv 2306.09896 full text](https://arxiv.org/html/2306.09896)
- Reflexion: self-generated tests must be biased toward false negatives; a 16.3% false-positive test rate (MBPP) turned the loop net-negative; up to 6 syntactically valid tests sampled per task — [arXiv 2303.11366 full text](https://arxiv.org/html/2303.11366v4)
- ACL 2025 revisit of Self-Debugging: post-execution feedback inherits the bias of self-generated tests; in-execution feedback (intermediate states) mitigates it — [ACL 2025 long.881](https://aclanthology.org/2025.acl-long.881)
- SWE-agent interface ablations (SWE-bench Lite, GPT-4 Turbo): linter guard on edits 18.0% vs 15.0% without; summarized search 18.0% vs iterative one-result-at-a-time 12.0% vs no search tools 15.7% (bad search is worse than none); file viewer 100 lines 18.0% vs 30 lines 14.3% vs full file 12.7%; keeping only the last 5 observations 18.0% vs full history 15.0%. Authors: guardrails help recovery; search results should be summarized and bounded (cap 50, ask for a more specific query above that); "informative but concise feedback" — [arXiv 2405.15793 full text](https://arxiv.org/html/2405.15793v3)
- LinkedIn SQL Bot: validators check table/field existence and run `EXPLAIN` "to detect syntax and other errors"; errors go to a self-correction agent "equipped with tools to retrieve additional tables or fields if needed"; key finding: "Validators work best when they access new information not available to the query writer" — [LinkedIn engineering blog](https://www.linkedin.com/blog/engineering/ai/practical-text-to-sql-for-data-analytics)
- LinkedIn Trino Summit 2024 deck lists pre-return checks (all tables/columns exist, query will run, user has access) and reports the self-correction agent's benchmark delta as "+2% +1% −14%" across three columns (labels not legible in the snippet) — [Trino Summit 2024 deck](https://trino.io/assets/blog/trino-summit-2024/trino-summit-2024-linkedin-ai.pdf)
- Snowflake Cortex Analyst: generated SQL is checked "by utilizing core Snowflake services, such as the SQL compiler"; compiler errors trigger a correction loop that also targets "hallucinated entities or functions" — [Snowflake engineering blog](https://www.snowflake.com/en/blog/engineering/snowflake-cortex-analyst-behind-the-scenes/)
- MAC-SQL's Refiner (as summarized): executes candidate SQL, observes errors *or empty result sets*, rewrites — empty results treated as a failure signal — [MAGIC paper context, arXiv 2406.12692](https://arxiv.org/abs/2406.12692)
- SQLens: ungrounded LLM self-reflection "breaks the most correct queries"; grounded signals (schema, execution) are what make a correction layer net-positive — [arXiv 2506.04494](https://arxiv.org/pdf/2506.04494)
- AlphaCodium: iterate first on *public* (trusted) tests, then on AI-generated tests, keeping passed tests as anchors; prefer "soft decisions with double validation" (regenerate + correct) over a yes/no verdict — [arXiv 2401.08500 full text](https://arxiv.org/html/2401.08500v1)
- Claude Code best practices: a `Stop` hook sends the check's stderr back "as the reason it can't finish yet", and the human should demand evidence (command + output), because "'All tests pass' on its own tells you very little" — [code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices)
- Anthropic: treat tool definitions like a human-computer interface, include example usage and edge cases, and make tools "harder to misuse" (e.g., requiring absolute paths fixed a class of errors) — [anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents)
- Deterministic format guards: OpenAI Structured Outputs reports 100% schema adherence on its internal eval for gpt-4o-2024-08-06 vs <40% for gpt-4-0613, via constrained decoding + training; subset of JSON Schema (≤100 properties, ≤5 nesting levels) — [OpenAI announcement](https://openai.com/index/introducing-structured-outputs-in-the-api/)
- Format constraints can cost reasoning: Tam et al. (EMNLP 2024 Industry) find "stricter constraints generally leading to greater performance degradation in reasoning tasks"; JSON-mode performs worst in most reasoning cases (GSM8K, Last Letter, Shuffled Objects) partly via key misordering (answer before reasoning), while constrained decoding *helps* classification accuracy — [arXiv 2408.02442](https://arxiv.org/abs/2408.02442)
- Practitioner consensus on repair loops (secondary, no benchmark): a real schema validator yields path+reason messages that are exactly what a repair turn needs; ~2 iterations recover most failures; do not raise temperature on retry; track parse success, schema compliance, semantic validity and repair attempts separately — [gmicloud blog](https://www.gmicloud.ai/zh-tw/blog/structured-output-for-llm-inference-json-schema-enforcement-constrained-decoding-and-parse-failure-rates), [ndthuan.com](https://www.ndthuan.com/reliable-structured-output-llms/)

### Inferences
- For a mapping agent the "unit test" is the simulation: show per-field *assertion-style* results (field X: 37% of rows failed date parse, examples "31/02/2568", "2025-13-01"; identity key duplicated in 12 rows; required field Y empty in 100% of rows) rather than a raw stack trace or the whole output table. That is the Self-Debugging UT+explanation configuration, the best-performing one.
- Show a *small* sample of concrete failing cells with expected type/format, not full rows; SWE-agent's 100-line window and 5-observation history, and its "bad search is worse than none" result, say that oversized context measurably hurts.
- Make the critic see things the proposer did not: distinct-value profiles, the approved mapping for the same customer, the other-customer match, drift report. LinkedIn's "new information" principle plus Olausson's "stronger/human feedback" result both point the same way — a critic with the same information as the generator adds little.
- Treat self-generated expectations (e.g., the model's own guess of what a column "should" contain) as low-trust tests: bias them toward false negatives (route to review) rather than false positives (auto-approve), per Reflexion's 16.3% false-positive failure.
- Keep the DSL emission in structured output for schema validity but let the model reason in free text *before* the structured block (Tam et al.), and never let a constrained decoder substitute for a semantic validator (OpenAI's 100% is structural adherence only).

### Gaps
- No controlled study was found comparing "errors only" vs "errors + sample output rows" vs "diff vs previous mapping" vs "aggregate metrics" for data-transformation feedback; the ranking above is inferred from code-repair ablations.
- The LinkedIn deck's three benchmark columns for the self-correction agent (+2/+1/−14) could not be labelled from the available snippet.

## Key Question 4 — How do production teams decide when to ask the human instead of iterating?

### Takeaway
Production analytics systems do not iterate indefinitely; they classify up-front (ambiguous/out-of-scope → refuse or suggest answerable questions), put a human confirmation at the cheapest high-leverage point (table/asset selection), mark outputs as "trusted" only when produced by human-verified logic, and run offline benchmarks with exact-result matching to decide what is safe to automate. Where confidence scores are used, the literature says to calibrate them on held-out data and pick the threshold from a target accuracy/risk, because verbalized confidence is overconfident (ECE > 0.377 average on smaller models; GPT-4 AUROC 62.7%).

### Cited Findings

**Product behaviour**
- Snowflake Cortex Analyst: a classification agent sorts questions into ambiguous / non-data / non-SQL; "It only answers questions that are unambiguous and can be answered using SQL"; ambiguous or out-of-scope questions are rejected and the user gets "a list of similar questions that can be answered confidently" (refusal + redirect, not iteration); verified queries written by human analysts are retrieved as examples; multiple LLMs generate SQL in parallel, a compiler-based error-correction agent fixes errors, a synthesizer picks the final query; vendor claims >90% SQL accuracy, "close to 2× more accurate than single-shot" GPT-4o — [Snowflake engineering blog](https://www.snowflake.com/en/blog/engineering/snowflake-cortex-analyst-behind-the-scenes/)
- Snowflake Cortex Analyst evaluations: runs generated SQL and compares *results* against verified queries to report an accuracy %, excludes the evaluated queries from the semantic view so the model cannot copy them, tracks latency and regressions (verified queries that used to pass and now fail) — [Snowflake docs: Cortex Analyst evaluations](https://docs.snowflake.com/ko/en/user-guide/snowflake-cortex/cortex-analyst-evaluations); verified queries must reference logical names and "must actually answer the question... Bad queries can hurt accuracy" — [Snowflake docs: verified query repository](https://docs.snowflake.com/user-guide/snowflake-cortex/cortex-analyst/verified-query-repository)
- Databricks Genie trusted assets: predefined SQL functions / parameterized example queries are "exact answers to specific questions and are not reused by Genie to address adjacent questions"; a response is labelled *Trusted* only when the exact text of a trusted asset produced it; recommended for "well-established recurring questions" — [Databricks docs: trusted assets](https://docs.databricks.com/aws/en/genie/trusted-assets)
- Databricks Genie benchmarks: each benchmark question is labelled Correct or Needs Review; "Questions are marked Correct if Genie's query result exactly matches the benchmark's query result" — [Databricks blog: benchmarks and ask review](https://www.databricks.com/blog/building-confidence-your-genie-space-benchmarks-and-ask-review); up to 500 benchmark questions per Genie Agent and a Monitor tab for conversation/feedback review — [Microsoft Learn: Test and monitor a Genie Agent](https://learn.microsoft.com/azure/databricks/genie-agents/monitor); Genie asks clarifying questions on ambiguity and learns from saved instructions and thumbs up/down — [Databricks answers](https://answers.databricks.com/ai-tools-handle-ambiguity-without-hallucinating); a third-party evaluation harness notes Genie shows "no confidence indicator, no ranked alternative" and recommends deliberately including ambiguous questions in test suites — [codecentric](https://www.codecentric.de/en/knowledge-hub/blog/reliable-by-design-building-an-evaluation-harness-for-databricks-genie)
- Uber QueryGPT: a Table Agent proposes tables and "The user would either select the 'Looks Good' button or edit the existing list" (added after users reported wrong tables); no confirmation step for intent or SQL; evaluation uses a hand-curated golden set with Vanilla (end-to-end) and Decoupled (correct intent/tables supplied) flows, scoring intent accuracy, table overlap 0–1, runs?, returns rows?, and LLM-scored SQL similarity 0–1; the team ignores "~5% run-to-run changes" as LLM noise; hallucinated tables/columns "remains an area that we haven't completely solved yet", with a validation agent planned; ~300 DAU, 78% say it saves time, ~10 min → ~3 min per query — [Uber blog](https://www.uber.com/blog/query-gpt/)
- LinkedIn SQL Bot: guided mode where "The user can interact at each step to provide feedback on the table or queries"; table checkboxes, product-area datasets, custom instructions, example queries; benchmark of 130+ expert-written questions across 10 product areas with table/field recall, hallucination rate, syntax correctness, latency; query accuracy = human eval + LLM-as-judge against a rubric (tables, columns, joins, filters, aggregations); ~60% of questions have multiple accepted answers and without them recall was under-reported 10–15%; LLM judge within 1 point of the human score 75% of the time; "~95% rated SQL Bot's query accuracy 'Passes' or above", ~40% "Very Good"/"Excellent"; "Fix with AI" is 80% of sessions — [LinkedIn engineering blog](https://www.linkedin.com/blog/engineering/ai/practical-text-to-sql-for-data-analytics)
- Pinterest text-to-SQL: table-retrieval hit rate was only ~40% without table documentation in the embeddings and rose roughly linearly with the weight on metadata (secondary summaries quote 90% with full documentation; not confirmed in the primary excerpt) — [Pinterest engineering (Medium)](https://medium.com/pinterest-engineering/how-we-built-text-to-sql-at-pinterest-30bad30dabff), [ZenML summary](https://www.zenml.io/llmops-database/text-to-sql-system-with-rag-enhanced-table-selection)
- Hex: Notebook Agent is "meant for technical users who can audit the SQL and code it suggests", with cell-by-cell diff review and "fix with agent" for errored cells; a 2026 write-up from Hex describes the loop as human-in-the-loop (agent acts → error flagged → data team updates guides/semantic models) — [Hex docs](https://learn.hex.tech/docs/getting-started/ai-overview), [Building data agents at Hex](https://dvmblog.pages.dev/posts/2026/04/building-data-agents-at-hex)
- Vanna: open-source RAG text-to-SQL "trained" on DDL, documentation and verified question→SQL pairs; accuracy depends on this corpus and user feedback on generated SQL is fed back as training data — [Daily Dose of DS review](https://blog.dailydoseofds.com/p/vanna-the-trainable-text-to-sql-agent)
- Claude Code: before an unattended run "make sure it knows what done looks like, can check its own work, and can only touch what it should. Give it a cap on turns or spend, and have a person approve the result at the end" — [code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices); Anthropic: agents "can then pause for human feedback at checkpoints or when encountering blockers" — [anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents)

**Confidence calibration and routing**
- Xiong et al. (ICLR 2024): LLMs "tend to be highly overconfident when verbalizing their confidence"; verbalized confidence of GPT-3/3.5/Vicuna has ECE > 0.377 on average; GPT-4's average AUROC 62.7% is "still close to a random guess"; consistency-based methods beat vanilla verbalized; hybrid (verbalized + consistency) best in 13/20 cases — [arXiv 2306.13063](https://arxiv.org/abs/2306.13063)
- Geng et al. survey of confidence estimation/calibration: separates logit-based, verbalized (linguistic) and consistency-based estimation; evidence on whether RLHF worsens calibration goes both ways — [arXiv 2311.08298](https://arxiv.org/abs/2311.08298)
- Matchmaker: deferring the highest-entropy confidence cases to an oracle at 0–50% deferral beats random deferral; errors whose predicted attribute has cosine ≥0.8 to the truth are "easier to fix after the fact" — [arXiv 2410.24105 full text](https://arxiv.org/html/2410.24105v1)
- Certified deferral (2026 preprint): answer automatically when confidence ≥ τ else defer; calibrate on a held-out set and choose τ with a finite-sample error guarantee — [arXiv 2608.05064](https://arxiv.org/pdf/2608.05064)
- "Trust or Escalate" (LLM judges): sequential testing on a calibration set keeps human-disagreement risk below α while retaining high coverage — [arXiv 2407.18370](https://arxiv.org/pdf/2407.18370)
- A domain study (conflict monitoring, 2026): raw confidence overstated accuracy; isotonic calibration made thresholds reliable; vanilla models would need human review for ~47% of cases to reach >80% accuracy in one country — single-domain, indicative only — [arXiv 2605.04177](https://arxiv.org/pdf/2605.04177)
- Calibration ≠ good selective prediction: a model need not be perfectly calibrated to abstain well, and standard training rewards confident answers on every input — [arXiv 2607.03528 (via Emergent Mind)](https://www.emergentmind.com/papers/2607.03528)

### Inferences
- The industry pattern is "classify → confirm the cheap structural choice with the human → generate with verified examples → deterministic validation → label trust level", not "iterate until confident". For FORMA the analogue of "confirm the tables" is confirming sheet/header-row/identity-column selection — cheap for the ops person, and it removes the error class (wrong source table/column) that is 27.6% of Spider 2.0 failures.
- Exact-result benchmarks (Snowflake, Databricks) and golden sets (Uber, LinkedIn) are the real decision instrument for *what to automate*: a layout/field class is auto-approvable when its benchmark accuracy on the corpus is high, not when the model says it is confident. FORMA already has this in `eval-gate`; the step is to feed per-field eval accuracy into `policies/approval.yaml` thresholds.
- Use consistency (agreement across sampled candidates or across heuristic vs LLM proposals) and deterministic simulation metrics as the confidence signal, with verbalized confidence as a tie-breaker only (Xiong: hybrid best, verbalized alone near random for GPT-4). Calibrate the threshold on the synthetic corpus + real review outcomes, and report coverage (auto-approved share) next to accuracy.
- Mark outputs produced by reused approved mappings or memory as "trusted" (Databricks' exact-match rule) and anything LLM-synthesized as "needs review" unless its deterministic score passes the calibrated threshold — this is already FORMA rule 11 (`llm_fallback=True` → review).

### Gaps
- No vendor publishes how its confidence threshold for review routing is set; Snowflake refuses ambiguous questions, Databricks shows no confidence indicator, Uber/LinkedIn rely on user confirmation and surveys.
- Uber publishes no accuracy numbers; LinkedIn's recall numbers exist only as a chart; Snowflake's >90% is an unverified vendor claim with a promised benchmark post not found.
- Julius AI: no documentation of a verification step was found.

## Key Question 5 — Does giving a model inspection tools over the data improve mapping/wrangling accuracy, and do models actually use them?

### Takeaway
Grounding in actual values (sample values, distinct values, literal→value mappings, table docs) is consistently reported as the largest single lever in enterprise text-to-SQL and data-wrangling agents (Pinterest 40% → ~90% retrieval with docs; Snowflake "relevant literals" and sample values; ProfiliTable +12–31 ATS points over scaffolds that do not inspect values), and schema/column linking still accounts for ~28% of failures on Spider 2.0 even with exploration tools. Evidence on whether models *spontaneously* inspect data is thin; the systems that work force the inspection step rather than leaving it to the agent.

### Cited Findings
- Spider 2.0 (ICLR 2025): 632 enterprise tasks over BigQuery/Snowflake, DBs often >1,000 columns; Spider-Agent with o1-preview 21.36%, Claude 3.5 Sonnet 14.87%, GPT-4o 12.34%, Qwen2.5-72B 6.17% vs 91.2% on Spider 1.0 and 73.0% on BIRD; Reflexion-style agent with GPT-4o only 7.28%. Error analysis of 300 failures: erroneous data analysis 35.5% (query planning 17.7%, dialect functions 10.3%, advanced calculation 7.5%), wrong schema linking 27.6% (column 16.6%, table 10.1%), JOIN errors 8.3%. Nested columns: 10.34% success vs 27.38% without; tasks needing external docs 11.54% vs 26.64%. Agents "must debug from SQL execution feedback and explore schemas of different database types". Oracle function docs barely helped DAIL-SQL (5.68% → 5.85%) and apparently *hurt* o1-preview (12.60% → 9.51%) — [arXiv 2411.07763](https://arxiv.org/abs/2411.07763), [full text v2](https://arxiv.org/html/2411.07763v2)
- DA-Code (2024): 500 agentic data-science tasks (wrangling, ML, EDA); best LLM in the DA-Agent sandbox only 30.5% — [arXiv 2410.07331](https://arxiv.org/abs/2410.07331)
- ProfiliTable (2026): a Profiler agent runs a ReAct loop (≤7 steps) that inspects actual values ("unique values rather than relying on schema metadata alone"), e.g. to standardize a currency column; baselines CleanAgent "does not actively sample or inspect the actual cell values during code generation" and DataGovAgent "samples only a few rows per column". Results (ATS): single-step gpt-4o 86.82 vs best baseline 56.21; gpt-5.2 89.66 vs 70.02; multi-step gpt-4o 80.19 vs 57.26; gpt-5.2 82.49 vs 70.18. Ablation: removing the Profiler lowers all metrics, especially multi-step; removing *feedback* causes the largest drop. The Profiler is always forced to run, so the paper never measures whether an agent would inspect on its own — [arXiv 2605.12376](https://arxiv.org/html/2605.12376v1)
- Pinterest: table-retrieval hit rate ~40% without table documentation in embeddings, rising linearly with metadata weight (secondary sources quote 90% with full docs) — [Pinterest engineering](https://medium.com/pinterest-engineering/how-we-built-text-to-sql-at-pinterest-30bad30dabff), [ZenML summary](https://www.zenml.io/llmops-database/text-to-sql-system-with-rag-enhanced-table-selection)
- Snowflake Cortex Analyst: a context-enrichment agent adds "relevant literals" via semantic search mapping business vocabulary to stored values ("USA" → "United States of America"), and the semantic model carries sample values (model must stay <32K tokens excluding sample values and verified queries; 1 MB file limit) — [Snowflake engineering blog](https://www.snowflake.com/en/blog/engineering/snowflake-cortex-analyst-behind-the-scenes/), [semantic model spec](https://docs.snowflake.com/user-guide/snowflake-cortex/cortex-analyst/semantic-model-spec)
- LinkedIn: self-correction agent has tools to retrieve additional tables/fields; the whole system uses a knowledge graph for retrieval *and* validation; without multiple accepted answers recall was under-reported 10–15% (i.e., the "oracle" itself needed grounding) — [LinkedIn engineering blog](https://www.linkedin.com/blog/engineering/ai/practical-text-to-sql-for-data-analytics)
- Matchmaker: schema matching done from names/descriptions/types only (healthcare privacy prevents value access); even so, reasoning-based candidate generation (LLM proposes matches by meaning) contributed more than embedding retrieval (reasoning-only 61.6 vs semantic-only 60.2 acc@1 on MIMIC; 73.0 vs 63.1 on Synthea) — [arXiv 2410.24105 full text](https://arxiv.org/html/2410.24105v1)
- SWE-agent: giving the agent a search tool that returns results one at a time made it *worse* than no search tool (12.0% vs 15.7%), because the agent "inspect[ed] results exhaustively"; summarized, bounded search (18.0%) was best — evidence that how an inspection tool presents results determines whether it helps — [arXiv 2405.15793 full text](https://arxiv.org/html/2405.15793v3)
- Practitioner post (vendor, no benchmark): grounding every mapping decision in actual sample values "dramatically reduces hallucination risk"; a `cust_id` integer vs `customer_number` prefixed-string example where a cast-only transform "loads cleanly and every number is wrong" — validation must run on real rows, not on schema agreement — [HackerNoon](https://hackernoon.com/ai-is-changing-schema-matching-in-ways-rule-based-systems-couldnt)
- CRITIC's thesis: critique is useful when the model can call tools (interpreter, search) to check facts it cannot verify internally — [arXiv 2305.11738](https://arxiv.org/abs/2305.11738)
- Anthropic: agents should get "ground truth from the environment at each step"; tools should be tested by running many example inputs "to find the model's mistakes" — [anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents)

### Inferences
- The working systems do not rely on the model deciding to look: Snowflake pre-computes sample values and literal mappings, ProfiliTable forces a profiling pass, LinkedIn retrieves via a KG, Pinterest embeds docs. For FORMA this supports keeping `profile_round` (distinct values, fingerprints, drift, other-customer match) as mandatory precomputed context given to the agent, rather than exposing a free-form "inspect" tool and hoping it is used.
- When an inspection tool *is* exposed, present bounded, summarized results (top-k distinct values with counts, min/max, null rate, 3 examples) — SWE-agent shows that exhaustive, paginated inspection degrades performance.
- The Spider 2.0 breakdown (27.6% schema linking, 35.5% wrong analysis) suggests that for a mapping agent the two deterministic checks with the most leverage are (1) "does every source column referenced exist, and is the chosen column's value distribution compatible with the target type/enum" and (2) "does the transformation reproduce known-good rows" (golden rows from previously approved rounds of the same customer).
- Column-level value compatibility checks (type parse rate, enum membership, Thai date/number plausibility) are the mapping analogue of LinkedIn's `EXPLAIN`: cheap, deterministic, and catching the error class that Self-Debugging's "does it run" oracle cannot.

### Gaps
- No controlled experiment was found that measures how often LLM agents voluntarily inspect data values when given the tool but not forced; ProfiliTable forces it, Spider 2.0 does not report step/tool statistics.
- No study isolates "distinct values" vs "a few sample rows" vs "full column profile" as the grounding input for column mapping accuracy.
- Spider 2.0 later leaderboard entries (ReFoRCE ~31%, third-party boards showing much higher numbers) could not be verified against the official site.

## Key Question 6 — What is known about verifier/judge reliability and failure modes (agreement bias, self-preference)?

### Takeaway
Strong LLM judges reach human-level agreement on preference tasks (GPT-4 vs humans 85% without ties, humans vs humans 81%), and agentic judges that can inspect artefacts do much better than plain LLM judges on requirement checking (~90% vs ~70%). But judges systematically favour their own outputs (self-preference is causally linked to self-recognition), show position bias that is systematic rather than random, hallucinate problems (CriticGPT), and are fooled by self-generated tests with false positives (Reflexion 16.3%). Deterministic verifiers and stronger/different-model critics are the mitigations with evidence.

### Cited Findings
- Zheng et al., "Judging LLM-as-a-Judge" (NeurIPS 2023): GPT-4 agreement with human experts 85% under the no-tie setup vs 81% human–human; documented biases: position, verbosity, self-enhancement, limited math/reasoning grading — [arXiv 2306.05685](https://arxiv.org/abs/2306.05685)
- Panickssery, Bowman & Feng (NeurIPS 2024): frontier LLMs recognise their own outputs and prefer them; fine-tuning to change self-recognition causes a corresponding change in self-preference (causal link); all three evaluators most easily distinguished their summaries from human ones and showed the greatest self-preference against the human summary; relabelling the source reverses self-preference for some models — [arXiv 2404.13076](https://arxiv.org/abs/2404.13076)
- Wataoka et al., "Self-Preference Bias in LLM-as-a-Judge": proposes a quantitative metric; GPT-4 shows significant self-preference; the proposed cause is familiarity (low perplexity) of the text — [arXiv 2410.21819](https://arxiv.org/abs/2410.21819)
- Shi et al., "Judging the Judges" (position bias): "Position bias is not due to random chance and varies significantly across judges and tasks"; it is driven mainly by quality gaps between candidates and only weakly by length; inter-judge consensus >80% on about two-thirds of instances across nine judges — [arXiv 2406.07791](https://arxiv.org/abs/2406.07791)
- Gu et al., "A Survey on LLM-as-a-Judge" (v6, Oct 2025): catalogue of biases (self-preference, position, verbosity, etc.) and mitigations — [arXiv 2411.15594](https://arxiv.org/abs/2411.15594)
- CriticGPT: critic preferred over humans 63%/>80% (natural/inserted bugs), but hallucination and nitpick rates "are still quite high"; precision–recall trade-off is tunable by critique length; human+critic teams hallucinate less than the critic alone — [arXiv 2407.00215](https://arxiv.org/abs/2407.00215)
- Olausson et al.: GPT-4 as its own critic gave "obviously inaccurate" feedback in 32/80 cases and never expressed uncertainty; humans 7/80 inaccurate, 7/80 expressed uncertainty — [arXiv 2306.09896 full text](https://arxiv.org/html/2306.09896)
- Reflexion: self-generated tests had 16.3% false-positive rate on MBPP (vs 1.4% HumanEval) and flipped the loop to net-negative — [arXiv 2303.11366 full text](https://arxiv.org/html/2303.11366v4)
- Huang et al.: the core failure is that "LLMs have trouble reliably evaluating the correctness of their own responses" — [arXiv 2310.01798](https://arxiv.org/abs/2310.01798)
- Agent-as-a-Judge: 86.6–92.1% agreement with 3-expert consensus vs 68.9–71.9% for LLM-as-a-Judge on DevAI; small benchmark (55 tasks) — [arXiv 2410.10934](https://arxiv.org/abs/2410.10934)
- Large Language Monkeys: without a ground-truth verifier, majority vote and reward-model selection plateau after a few hundred samples even as coverage keeps rising — selection, not generation, caps performance — [arXiv 2407.21787](https://arxiv.org/abs/2407.21787)
- Agentless: reproduction tests are themselves unreliable — of 300 issues, 213 generated tests reproduced the error on the original repo, but only 94 printed "Issue resolved" when the *ground-truth* patch was applied — yet filtering with them still added +5 pts because they are used as a filter plus majority vote, not as a sole oracle — [arXiv 2407.01489 full text](https://arxiv.org/html/2407.01489)
- LinkedIn: LLM judge within 1 point of the human rubric score 75% of the time; ~60% of benchmark questions needed multiple accepted answers or recall was under-reported 10–15% — the judge's reference set is itself a source of error — [LinkedIn engineering blog](https://www.linkedin.com/blog/engineering/ai/practical-text-to-sql-for-data-analytics)
- Uber: ~5% run-to-run metric variation from LLM non-determinism is treated as noise — [Uber blog](https://www.uber.com/blog/query-gpt/)
- Mitigation from practice: swap candidate positions and count only consistent verdicts (cost: one extra call) — [Adaline blog, secondary](https://www.adaline.ai/blog/llm-as-a-judge-reliability-bias)
- Claude Code: use a reviewer "in a fresh subagent that never saw your conversation", and scope it ("skip style") because "A reviewer that's asked to find problems will always find something" — [code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- A self-check by the same model with the same context is the least reliable verifier available (self-preference + inaccurate self-feedback + no expressed uncertainty). Ranked by evidence: deterministic validator/simulation > human > stronger or different-family model critic with *new* information > same model in a fresh context (no shared reasoning) > same model in the same context.
- An LLM critic's verdict should be a *filter plus signal* feeding the deterministic score, never the sole gate (Agentless pattern); and its false positives (claiming a mapping is fine) are the dangerous direction for FORMA, so a critic "pass" should not upgrade an item from review to auto-approve on its own — only the policy engine with deterministic evidence should.
- Expect ~5% metric noise between runs of any LLM-scored evaluation (Uber); use exact-result or deterministic metrics for the eval gate and keep LLM-judged scores for diagnostics.
- Reference answers used by a judge must allow multiple correct mappings (LinkedIn's 10–15% under-reporting) — e.g., equivalent op chains producing identical output should score equal; compare *outputs*, not DSL text.

### Gaps
- No study of self-preference or judge bias specifically on data-mapping or schema-matching verdicts was found.
- Numeric self-preference magnitudes (e.g., "+10–25% self win rate") appear only in unsourced blogs and were not used.
- Verifier reliability for *declarative DSL* outputs (as opposed to code or free text) is not covered in the literature found; the closest is Agentless' reproduction-test unreliability and Reflexion's test false-positive rates.
