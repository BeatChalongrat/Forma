# เจ้าใหญ่ให้ "เครื่อง" ตรวจโมเดล ไม่ให้โมเดลตรวจตัวเอง

ทุกระบบที่ทำ AI-assisted schema mapping ได้จริงในระดับผลิตภัณฑ์ — ตั้งแต่ Informatica, Microsoft, Databricks ไปจนถึง Flatfile, Ingestro, Rossum และงานวิจัยอย่าง Matchmaker — ทำให้ผลของโมเดลเชื่อถือได้ด้วยกลไกชุดเดียวกัน: **ให้โมเดลเขียน artifact เชิงประกาศ (ไม่ใช่โค้ด) → ให้ engine เชิงกำหนดรันมันบนข้อมูลจริง → ป้อนผลที่วัดได้กลับ (ไม่ใช่ขอให้ "คิดทบทวน") → ให้กฎเชิงกำหนดตัดสินเหนือคะแนนความมั่นใจ → ส่งส่วนที่ไม่แน่ใจให้คนตัดสินแบบมีทางเลือก → จำคำตอบของคนไว้เป็นหน่วยความจำที่ใช้ซ้ำได้ทันที** หลักฐานเชิงตัวเลขชี้ชัดว่าการตรวจงานตัวเองช่วยก็ต่อเมื่อสัญญาณมาจากนอกตัวโมเดล: Self-Debugging ได้ **+12 จุด** เมื่อมี unit test แต่บน Spider ที่มีแค่ "รันได้ไหม" ได้เพียง 73.2 → 73.6 ([arXiv 2304.05128](https://arxiv.org/html/2304.05128)); Matchmaker ที่ให้โมเดล self-reflect ได้ **57.1** เทียบกับ 62.2 ของ bootstrapped demos และ 57.9 ของการไม่ทำอะไรเลย ([arXiv 2410.24105](https://arxiv.org/html/2410.24105v1)); และ Huang et al. (DeepMind) พบว่า intrinsic self-correction มักทำให้ผลแย่ลง ([arXiv 2310.01798](https://arxiv.org/abs/2310.01798)) ส่วนสิ่งที่ให้ผลใหญ่สุดในงาน schema matching คือการ **ย่อชุดผู้สมัครและให้ anchor จาก mapping ที่เคยอนุมัติ** (+20.4 จุด acc@1 จาก mapping ที่รู้แล้วหนึ่งคู่ต่อตาราง — [ReMatch](https://arxiv.org/html/2403.01567v2)) และการ **ให้โมเดลเห็นค่าจริงในคอลัมน์** (Pinterest ดึงตารางถูก ~40% → ~90% เมื่อฝัง documentation — [Pinterest](https://medium.com/pinterest-engineering/how-we-built-text-to-sql-at-pinterest-30bad30dabff)) โดยระบบที่ได้ผล *บังคับ* ขั้นตอนนี้ ไม่ปล่อยให้โมเดลเลือกเอง FORMA หลัง ADR-058 อยู่ตรงแกนของแนวทางนี้แล้ว — DSL เชิงประกาศ, self-check บน 50 แถวแรกด้วย oracle เชิงกำหนด, จำกัด 2 รอบและเก็บคำตอบที่ดีที่สุด, plausibility เป็นกฎไม่ใช่ความเห็น, คำถามแบบ choice, memory ต่อลูกค้า, PolicyEngine — และผลวัด (self-check แก้ 3 จาก 12 ครั้งในรอบเดียว, คำถาม 58 → 21, โมเดลใหญ่ไม่ช่วย) สอดคล้องกับวรรณกรรมทุกข้อ ช่องว่างที่เหลือและคุ้มลงทุนตามหลักฐานมีสามเรื่อง: ทำให้การ ground ค่าในคอลัมน์เป็นสิ่งบังคับแทน inspect ที่โมเดลใช้แค่ 1 ใน 12 โอกาส, ดึง mapping ที่อนุมัติแล้วของลูกค้ารายอื่นมาเป็น anchor ให้ลูกค้าใหม่, และย้ายความมั่นใจจากคำพูดของโมเดลไปเป็นคะแนนจากหลักฐานเชิงกำหนดที่แคลิเบรตกับผลรีวิวจริง ส่วนสิ่งที่หลักฐานบอกว่า *ไม่ควร* ลงทุนคือ LLM critic ตัวที่สอง, การเพิ่มรอบ self-check, และการเปลี่ยนโมเดลให้ใหญ่ขึ้น

## ทุกเจ้าเรียงลำดับเดิม — exact → alias → history → LLM → fuzzy — และให้โมเดลเขียน artifact เชิงประกาศ

รูปทรงของระบบที่ใช้งานจริงแทบไม่ต่างกันเลยไม่ว่าจะเป็นแพลตฟอร์มองค์กรหรือ importer สำหรับ SaaS: ชั้นเชิงกำหนดทำงานก่อน และ AI รับผิดชอบเฉพาะคอลัมน์ที่เหลือ Ingestro (เดิมคือ nuvo) เขียนลำดับนี้ไว้ตรง ๆ ในค่าตั้งต้น `columnMappingConfiguration.layers = ["exact", "historic", "smart", "fuzzy"]` — จับคู่ตรงตัวก่อน แล้วใช้ mapping จากการนำเข้าครั้งก่อน ตามด้วย "Ingestro AI" และปิดด้วย fuzzy ([Ingestro SDK settings](https://docs.ingestro.com/sdk/settings)) CSVbox อธิบายคาสเคดเดียวกันสี่ชั้น (exact → normalised → fuzzy ด้วย Levenshtein/Jaro-Winkler → semantic ด้วย embedding หรือ LLM) พร้อมเกณฑ์สามระดับ High = ใส่ให้เลย, Medium = ใส่ไว้แต่ธงให้ยืนยัน, Low = ปล่อยว่าง และกฎ "Never auto-apply a low-confidence match silently" ([CSVbox](https://csvbox.io/resources/ai-column-mapping)) Flatfile อ้างว่าโมเดลที่ฝึกจาก "1.8 billion rows" บวก "memory of past selections" ทาย matching action ได้ **"over 90%"** ([Flatfile support](https://support.flatfile.com/articles/8569925090-mapping-data)) และ OneSchema จำ "historical mappings that your users may have successfully imported in the past" ก่อนจะเรียก AI ([OneSchema changelog](https://docs.oneschema.co/changelog/intelligent-column-mapping)) งานเขียนอิสระจาก Catalogit ยืนยันเหตุผลเชิงประจักษ์: PoC แรกที่ส่ง CSV ทั้งไฟล์บวก schema ทั้งหมดในหนึ่ง prompt "worked often enough to be encouraging and rarely enough to be useless" เพราะโมเดลต้องทำ retrieval, classification และ reasoning พร้อมกันโดยไม่มี fallback; เมื่อแยกเป็น LLM ทำ profile ต่อคอลัมน์หนึ่งครั้ง + embedding match เชิงกำหนด + type filter + history ที่ข้าม AI ได้ backlog ลดจาก **16 สัปดาห์เหลือ 4** และ **>85% ของข้อเสนอถูกยอมรับ** ([Catalogit](https://dchoiboi00.github.io/projects/csv-schema-mapper-at-catalogit))

สิ่งที่โมเดลผลิตออกมาก็แบ่งค่ายชัดเจนตาม asset model ที่ผลิตภัณฑ์มีอยู่ก่อน ไม่ใช่ตามปรัชญา AI ของผู้ขาย ผู้ขายที่มี validator สำหรับ artifact เชิงประกาศอยู่แล้วให้ LLM เขียนลง artifact นั้น: Informatica มี "our own grammar as to how this describes the mapping" และ "the natural language translated into Informatica grammar is where our secret sauce comes in" โดยเป็นรายเดียวที่อ้างว่า fine-tune โมเดลลง grammar ของตน ([VentureBeat](https://venturebeat.com/ai/enterprise-data-fragmentation-isnt-going-away-how-informatica-has-evolved-its-ai-capabilities-to-solve-real-challenges)); Palantir Pipeline Builder "Generate" ออกเป็น transform node ที่ "saved to pipeline logic like any other transform" ([Palantir](https://palantir.com/docs/foundry/pipeline-builder/pipeline-builder-aip/)); Oracle Integration 3 ให้ XSLT ([Oracle](https://docs.oracle.com/en/cloud/paas/application-integration/mapper-user/generate-mapping-recommendations.html)); Flatfile ออกเป็น execution plan ที่มี `plan.fieldMapping[]` แต่ละรายการถือ `sourceField`, `destinationField`, `preview` และ `metadata {certainty, source}` ([Flatfile support](https://support.flatfile.com/en/articles/8148440-retrieve-mapping-information)) ส่วนค่ายที่เป็น code-first (AWS Glue/Amazon Q, Databricks Genie Code, Fabric Copilot) ให้โค้ด PySpark/M/SQL ที่คนต้องรีวิวใน editor พร้อมคำเตือนอย่าง AWS ที่ว่า "there can be mistakes, sometimes called hallucinations... Test and review all code" ([AWS Glue docs](https://docs.aws.amazon.com/glue/latest/dg/q.html)) ประเด็นสำคัญสำหรับ FORMA คือ **ไม่มีผู้ขายรายใดให้ LLM รันโค้ดต่อข้อมูลจริงใน data path** แม้ค่าย code-first ก็ส่งโค้ดเข้า runtime ปกติภายใต้สิทธิ์ของผู้ใช้ และ Palantir เป็นผู้ที่พูดชัดที่สุดว่าทำไมต้องมี output guard แยกจาก access control: สิทธิ์การอ่าน "do not extend to the model's output or to Ontology edits it composes" ([Palantir AIP Logic](https://www.palantir.com/docs/foundry/logic/overview/))

งานวิจัยให้ตัวเลขว่าทำไมการ *ย่อชุดผู้สมัครก่อน* ถึงสำคัญกว่าทุกอย่าง ReMatch บน MIMIC-III→OMOP ได้ acc@1 **0.424** เมื่อ retrieve ตารางเป้าหมาย 2 ตารางก่อน แต่ตกเหลือ **0.311** เมื่อให้ GPT-4 ดูทั้ง 38 ตาราง และ acc@5 ตกจาก 0.729 เหลือ 0.518; ให้มากเกินไป (J=7) ก็แย่ลงเป็น 0.317 และการตัด description เหลือแค่ชื่อฟิลด์ทำให้ acc@5 ร่วงจาก 0.729 เหลือ 0.503 ([ReMatch](https://arxiv.org/html/2403.01567v2)) Parciak et al. สรุปว่า "too little and too much context both hurt": prompt แบบ 1-ต่อ-1 ที่ไม่มีบริบทได้ F1 0.241 ส่วน N-to-M ที่ยัดทุกคู่ลง prompt ได้ 0.469 ต่ำกว่า N-to-1 ที่ 0.580 และ decisiveness ของ GPT-4 ร่วงจาก 0.992 เหลือ **0.029** ([Parciak et al.](https://arxiv.org/html/2407.11852v1)) Matchmaker ซึ่งเป็น SOTA ใช้สองแหล่งผู้สมัคร (ColBERT-v2 retrieval + LLM reasoning) แล้วให้ refiner ย่อ ได้ acc@1 **62.20** บน MIMIC เทียบกับ ReMatch 42.50, Jellyfish-13B 15.36 และ SMAT ที่ 6.05 โดยที่ reasoning-only (61.6) ให้มากกว่า semantic-only (60.2) ([Matchmaker](https://arxiv.org/html/2410.24105v1)) และตัวเลขที่ตรงกับ "memory reuse" ของ FORMA ที่สุดคือ **anchor หนึ่งคู่ต่อตาราง** ซึ่งยก acc@1 ของ ReMatch จาก 0.424 เป็น **0.539** ([ReMatch](https://arxiv.org/html/2403.01567v2)) — ของถูกที่สุดที่ให้ผลใหญ่ที่สุดในวรรณกรรมทั้งชุด ความรู้เชิงโดเมนที่ฉีดเข้า prompt อย่างชัดแจ้งก็ให้ผลใหญ่บนโมเดลอ่อน: Prompt-Matcher เพิ่ม abbreviation rules และ value-overlap cues ยกความถูกต้องบน Valentine-Fabricated จาก **70% → 91.8%** ([Prompt-Matcher](https://arxiv.org/html/2408.14507v3)) และ Jellyfish ที่ fine-tune แล้วล้มบน schema ที่ไม่เคยเห็น (CMS F1 7.14) จนกระทั่งฉีดความรู้เข้าไปจึงขึ้นเป็น 59.29 ([Jellyfish](https://arxiv.org/html/2312.01678v5)) — เป็นเหตุผลเดียวกับที่ FORMA เก็บ synonyms ในไฟล์ schema และเพิ่มรหัสหน่วย SAP (ST, PAK, KAR, KI, FL, DO, BT) ลง `unit_normalize` หลังรันจริง

ควรจำไว้ด้วยว่าเพดานของ benchmark เหล่านี้ยังต่ำ: acc@1 ที่ดีที่สุดบน MIMIC/Synthea อยู่แค่ **62–70%** คือราวหนึ่งในสามของคำตอบอันดับหนึ่งผิดถ้าไม่มีคน ([Matchmaker](https://arxiv.org/html/2410.24105v1)) และ benchmark ไฟล์จริงยิ่งโหด — SpreadsheetBench ให้ทุก LLM และ agent ได้ **0.05–23.65%** ([SpreadsheetBench](https://www.arxiv.org/pdf/2406.14991)) Spider 2.0 ให้ o1-preview ~17–21% เทียบกับ ~91% บน Spider 1.0 ([spider2-sql.github.io](https://spider2-sql.github.io/)) ตัวเลขเหล่านี้คือเหตุผลที่ทุกบทความลงท้ายด้วย "ต้องมีคนในลูป" และเป็นเหตุผลที่ค่าความถูกต้อง 0.84–1.0 ของ FORMA บนไฟล์ ERP หกแบบนั้นดีเกินค่าเฉลี่ยของสนาม — แต่ก็มาจากไฟล์สังเคราะห์ที่ไม่ควรถือเป็นตัวแทนของลูกค้าจริง 300 ราย

## การตรวจที่ได้ผลต้องมี oracle นอกตัวโมเดล — +12 จุดเมื่อมี test, ≈0 เมื่อให้คิดทบทวนเอง

หลักฐานเรื่อง self-verification แบ่งเป็นสองโลกที่ผลต่างกันราวฟ้ากับดิน โลกแรกคือการป้อนผลจาก oracle ภายนอกกลับให้โมเดล: Self-Debugging บน TransCoder ด้วย GPT-4 ไล่จาก baseline **77.3 → 80.9** (บอกแค่ว่าผิด) **→ 88.8** (บอกว่า test ใดตก พร้อม expected vs actual) **→ 90.4** (เพิ่มคำอธิบายโค้ด) และผู้เขียนระบุว่า "typically one debugging turn is sufficient" โดย "successful debugging mostly finishes within 3 turns" ([arXiv 2304.05128](https://arxiv.org/html/2304.05128)); AlphaCodium ยก pass@5 บน CodeContests ของ GPT-4 จาก **19% → 44%** ด้วย flow ที่วนบน public test ก่อนแล้วค่อยวนบน AI test โดยเก็บ test ที่ผ่านแล้วเป็น "test anchors" กันถดถอย ([AlphaCodium](https://arxiv.org/html/2401.08500v1)); SWE-agent ได้ **+3.0 จุด** (18.0% vs 15.0%) จากแค่ linter เชิงกำหนดที่ปฏิเสธการแก้ที่ syntax พัง ก่อนที่มันจะถูก apply ([SWE-agent](https://arxiv.org/html/2405.15793v3)) โลกที่สองคือ intrinsic self-correction ที่ไม่มีสัญญาณใหม่: Huang et al. พบว่าโมเดล "alter initially correct answers into wrong ones" และผลบวกในงานก่อน ๆ อาศัย oracle label ทั้งสิ้น ([arXiv 2310.01798](https://arxiv.org/abs/2310.01798)); Olausson et al. วัดว่า GPT-4 ให้ feedback ต่องานตัวเองที่ "obviously inaccurate" ถึง **32 จาก 80 กรณี** (คน 7/80) และไม่เคยแสดงความไม่แน่ใจเลย ขณะที่ feedback จากคนยก repair success จาก 33.3% เป็น **52.6%** (1.58×) ([arXiv 2306.09896](https://arxiv.org/html/2306.09896)); SQLens สรุปตรง ๆ ว่า "LLM self-reflection breaks the most correct queries" และ layer แก้ไขที่ grounded ด้วย schema/execution เท่านั้นที่เป็นบวกสุทธิ (CHESS บน BIRD 67.91% → 69.74%) ([SQLens](https://arxiv.org/pdf/2506.04494)) ในงาน schema matching โดยตรง Matchmaker ablation คือหลักฐานชี้ขาด: self-reflection ได้ **57.10** บน MIMIC เทียบ vanilla 57.90 คือไม่ช่วยเลย ส่วนกลไกที่ได้ผล (62.20) คือ LLM evaluator ให้คะแนน trace 0–5 แล้วเอา trace ที่ดีที่สุดเป็น demonstration ไม่เกิน 4 ตัวอย่าง ([Matchmaker](https://arxiv.org/html/2410.24105v1)) บทเรียนที่ตรงกับ FORMA ที่สุดคือแถว Spider ของ Self-Debugging: งานเชิงประกาศ (SQL) ที่ oracle บอกได้แค่ "รันผ่าน" ได้ 73.2 → 73.4 → 73.6 — แทบไม่มีอะไร ([arXiv 2304.05128](https://arxiv.org/html/2304.05128)) กำไรจึงอยู่ที่ **oracle ตรวจอะไรได้บ้าง** ไม่ใช่จำนวนรอบ

เรื่องจำนวนรอบ วรรณกรรมเห็นพ้องว่ารอบแรกที่ grounded กินกำไรเกือบหมด: LitE-SQL รายงานว่า "the first self-correction pass yields the largest accuracy gain... subsequent passes diminish progressively" ([LitE-SQL](https://arxiv.org/pdf/2510.09014)); Self-Refine บอกว่า "the marginal improvement naturally decreases with more iterations" ([Self-Refine](https://arxiv.org/abs/2303.17651)); ระบบผลิตจริงล็อกเพดานไว้หมด — CodeMonkeys จำกัด state machine ที่ 8 iteration และ 10 candidate ต่อ instance ([CodeMonkeys](https://scalingintelligence.stanford.edu/pubs/codemonkeys)), Instructor ใช้ `max_retries` 2–3 ([Instructor](https://python.useinstructor.com/concepts/retrying/)), Snowflake Cortex Analyst "may run each query up to four times" ([Snowflake docs](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst/analyst-optimization)), Anthropic แนะ "stopping conditions, such as a maximum number of iterations" ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)) ที่สำคัญกว่าคือ **ความกว้างชนะความลึก** เมื่องบเท่ากัน: Olausson วัดว่า GPT-4 บน APPS ด้วย 10 initial sample + 1 repair ได้ 1.05× ของ i.i.d. sampling ส่วน 2 initial + 10 repair ได้ **0.97×** คือแย่กว่าไม่ซ่อม ([arXiv 2306.09896](https://arxiv.org/html/2306.09896)); Agentless ได้ 32.00% บน SWE-bench Lite ที่ $0.70/issue โดย "repair performance plateaus at about 40 samples" และเพดานถ้านับ patch ใดก็ได้ที่ถูกคือ 42.0% — คอขวดคือ *การเลือก* ไม่ใช่การสร้าง; majority vote เปล่า ๆ ให้ 25.67%, บวก regression test 27.00%, บวก reproduction test 32.00% ([Agentless](https://arxiv.org/html/2407.01489)); CodeMonkeys ปิดช่องว่าง random selection 45.8% → oracle 69.8% ได้ประมาณครึ่งหนึ่งที่ 57.4% ด้วย test ที่สร้างเอง + model vote ([CodeMonkeys](https://scalingintelligence.stanford.edu/pubs/codemonkeys)) และ Large Language Monkeys แสดงว่า DeepSeek-V2-Coder ที่อ่อนกว่าได้ 15.9% → **56%** เมื่อ sample 250 ครั้งแล้วให้ unit test เลือก ชนะ SOTA single-shot ของโมเดลแข็งกว่าที่ 43% — แต่ "only where an automatic verifier exists" และ "majority voting and reward models plateau after several hundred samples" เมื่อไม่มี ([Large Language Monkeys](https://arxiv.org/abs/2407.21787)) Snell et al. เสริมเงื่อนไข: โมเดลเล็ก + search ชนะโมเดลใหญ่ 14× ที่ FLOPs เท่ากัน "only on problems where a smaller base model attains somewhat non-trivial success rates" ([arXiv 2408.03314](https://arxiv.org/abs/2408.03314))

สิ่งที่ควรป้อนกลับก็มีคำตอบเชิงประจักษ์ ไม่ใช่ความชอบ Self-Debugging ladder บอกว่า assertion-style (test ใดตก, expected vs actual) ชนะ "ผิด" เฉย ๆ 4–8 จุด, คำอธิบายเพิ่มอีก 1–3 จุด แต่ execution trace ดิบ ๆ ให้น้อยกว่าและบางครั้งแย่ลง (Codex: trace 87.9 vs UT 91.6) ([arXiv 2304.05128](https://arxiv.org/html/2304.05128)) SWE-agent ablation สอนเรื่องขนาดบริบท: file viewer 100 บรรทัดได้ 18.0% ส่วน 30 บรรทัด 14.3% และทั้งไฟล์ **12.7%**; เก็บแค่ 5 observation ล่าสุดได้ 18.0% ส่วน history เต็ม 15.0%; search ที่คืนผลทีละรายการ (12.0%) *แย่กว่าไม่มี search* (15.7%) เพราะ agent "inspected results exhaustively" ([SWE-agent](https://arxiv.org/html/2405.15793v3)) LinkedIn SQL Bot ให้หลักการที่สรุปทุกอย่าง: "Validators work best when they access new information not available to the query writer" — validator ตรวจว่าตาราง/ฟิลด์มีจริงและรัน `EXPLAIN` แล้วส่ง error ไปยัง self-correction agent ที่มี tool ดึงตาราง/ฟิลด์เพิ่มได้ ([LinkedIn](https://www.linkedin.com/blog/engineering/ai/practical-text-to-sql-for-data-analytics)) และ Reflexion เตือนทิศทางของความผิด: test ที่โมเดลสร้างเองมี false-positive **16.3%** บน MBPP (1.4% บน HumanEval) จนลูปกลายเป็นลบสุทธิ (0.80 → 0.77) — "false negatives are preferred over false positives" ([Reflexion](https://arxiv.org/html/2303.11366v4)) นั่นคือเหตุผลเชิงหลักฐานว่าทำไม critic ที่บอกว่า "ผ่าน" ไม่ควรมีสิทธิ์ยก item จาก review เป็น auto-approve

ในฝั่งผู้ขาย การ "รันแล้วดูก่อน commit" เป็นสากลแต่ลูปที่ส่งผลกลับ *ให้โมเดล* อัตโนมัติมีแค่สองราย: Databricks Genie Code "can also run a transformation, inspect the output, and try another approach if a join fails or returns no rows" ([Databricks](https://www.databricks.com/blog/announcing-public-preview-lakeflow-designer)) และสำหรับเอกสารมันรัน "field-level evaluation against a labeled table of expected outputs" แล้วเสนอ fix "as a diff you approve" วนจน "quality meets your bar" ([Databricks docs](https://docs.databricks.com/aws/en/large-language-models/genie-code-document-processing)); Palantir AIP Evals "categorizes failing test cases by root cause" และเสนอแก้ prompt ([Palantir](https://www.palantir.com/docs/foundry/logic/overview/)) ที่เหลือทั้งหมด — BigQuery data prep ที่ทำ sample ~10k แถว, Fabric Dataflow Gen2 ที่เตือนว่า Copilot "might produce inaccurate results when the intent is to evaluate data that isn't present within the sampled results", SageMaker Canvas preview → "Add to steps", Dromo Transform Data, Flatfile AI Assist — ปิดลูปผ่านคน ([Google](https://docs.cloud.google.com/bigquery/docs/data-prep-introduction); [Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/get-started-copilot-fabric-data-engineering/dataflow-gen2); [Dromo](https://developer.dromo.io/guides/using-transform-data.md); [Flatfile](https://flatfile.com/docs/guides/ai-transformations)) นั่นหมายความว่า self-check ของ FORMA ที่ป้อน record count, compile/join problems, schema errors, plausibility warnings และ 3 sample records กลับให้โมเดลแก้ อยู่ *ล้ำกว่า* ผู้ขายส่วนใหญ่แล้ว และตรงกับ configuration ที่วัดได้ว่าดีที่สุด (UT + explanation) โดยไม่ตกหลุม trace ดิบหรือบริบทยาวเกิน

## ระบบที่ใช้งานจริงบังคับให้มองค่าในไฟล์ ไม่รอให้โมเดลอยากมอง

การ ground ใน *ค่าจริง* เป็นคันโยกเดี่ยวที่ใหญ่ที่สุดในงาน text-to-SQL และ data wrangling ระดับองค์กร และข้อค้นพบที่สำคัญสำหรับ FORMA คือ **ไม่มีระบบใดพึ่งพาว่าโมเดลจะตัดสินใจไปดูเอง** ProfiliTable ให้ Profiler agent วน ReAct ≤7 ขั้นเพื่อดู "unique values rather than relying on schema metadata alone" และได้ ATS **86.82 เทียบ 56.21** ของ baseline ที่ดีที่สุดบน gpt-4o (single-step) โดย baseline อย่าง CleanAgent "does not actively sample or inspect the actual cell values" และ DataGovAgent "samples only a few rows per column"; ที่สำคัญคือ Profiler **ถูกบังคับให้รันเสมอ** จนบทความไม่เคยวัดเลยว่าถ้าปล่อยให้เลือกเองโมเดลจะดูหรือไม่ และการตัด feedback ทำให้ตกมากที่สุด ([ProfiliTable](https://arxiv.org/html/2605.12376v1)) Snowflake Cortex Analyst ไม่ให้โมเดลถาม แต่ *คำนวณล่วงหน้า*: context-enrichment agent เติม "relevant literals" ผ่าน semantic search ที่โยงคำธุรกิจเข้ากับค่าที่เก็บจริง ("USA" → "United States of America") และ semantic model พก sample values ติดไว้ ([Snowflake](https://www.snowflake.com/en/blog/engineering/snowflake-cortex-analyst-behind-the-scenes/)) Pinterest วัดว่า table-retrieval hit rate อยู่แค่ **~40%** เมื่อไม่ฝัง table documentation ใน embedding และไต่เป็นเส้นตรงตามน้ำหนัก metadata (แหล่งทุติยภูมิอ้าง ~90% เมื่อมีเอกสารครบ) ([Pinterest](https://medium.com/pinterest-engineering/how-we-built-text-to-sql-at-pinterest-30bad30dabff)) Spider 2.0 แจกแจงความล้มเหลว 300 กรณี: **wrong schema linking 27.6%** (คอลัมน์ 16.6%, ตาราง 10.1%) และ erroneous data analysis 35.5% — ชั้นที่ชี้คอลัมน์ผิดยังเป็นหนึ่งในสี่ของความผิดแม้ agent จะมี tool สำรวจ schema ([Spider 2.0](https://arxiv.org/html/2411.07763v2))

วิธี serialize คอลัมน์ก็มีสูตรที่วัดแล้ว Magneto พบว่า header-only ให้ผล *แย่ที่สุด* ทุกชุดข้อมูลเมื่อมีค่าให้ใช้ และตั้งค่าเริ่มต้นเป็น ชื่อ + ชนิดที่อนุมาน + ~10 sample values โดย priority sampling (ถ่วงด้วยความถี่) ชนะ random/weighted; มันยังเตือนว่าทั้งสัญญาณจากชื่อและค่าล้มพร้อมกันเมื่อ representation ต่าง เช่น "FIGO grade 1" กับ "G1" ([Magneto](https://arxiv.org/html/2412.08194v2)) — กรณีเดียวกับ "EA" กับ "PCS" หรือหัวไทย/อังกฤษของ FORMA ซึ่งคำตอบของวรรณกรรมคือ dictionary ที่ฉีดเข้า prompt อย่างชัดแจ้ง ไม่ใช่หวังให้โมเดลเดา กรณี ERP อุตสาหกรรม (ColRel, DaWaK 2026) ชี้ว่าชื่อคอลัมน์ ERP "coded/abbreviated" และ metadata "sparse or weakly informative" จึงใช้ business dictionary ถอดชื่อและให้ LLM เขียนคำอธิบายสั้นต่อคอลัมน์ — **หนึ่งครั้งต่อคอลัมน์ ไม่ใช่ต่อคู่** ([arXiv 2608.26750](https://arxiv.org/abs/2608.26750)) ส่วน SpreadsheetLLM เตือนอีกด้าน: การยัดสี/เส้นขอบของเซลล์ทำให้ผลแย่ลงจนต้องตัดออก และ vanilla encoding ของทั้งชีตแพ้ compressed encoding ขาดลอย (table detection F1 ของ GPT-4 ICL 0.154 → 0.410) ([SpreadsheetLLM](https://arxiv.org/html/2407.09025v2)) สูตรปฏิบัติที่ตกตะกอน: การ์ดต่อคอลัมน์ = header + ชื่อที่ถอดแล้ว + ชนิด + ~10 ค่าไม่ซ้ำถ่วงความถี่ + null rate + คำอธิบายหนึ่งบรรทัด, เสนอ *shortlist* ของฟิลด์เป้าหมาย, และใส่ cue ที่แยกคอลัมน์ที่คล้ายกัน (ConStruM ทำ "differentiation cues" สำหรับคอลัมน์เกือบซ้ำ และสรุปจาก search คือ 0.935 เทียบ 0.503 ของ ReMatch บนชุดหนึ่ง — [ConStruM](https://arxiv.org/abs/2601.20482))

ฝั่ง importer เชิงพาณิชย์ ความจริงที่น่าสนใจคือ "โมเดลเห็นค่า" เป็น *ข้อยกเว้น* ไม่ใช่กฎ: มีเพียง Flatfile (เอกสาร legacy) ที่บอกว่าใช้ "the column names and values in the source data" ([Flatfile legacy docs](https://flatfile.com/docs/legacy-docs/concepts/mapping.md)); Dromo Transform Data ระบุว่า "The AI never sees the import data" จึงต้องให้ผู้ใช้บอกรูปแบบปัจจุบันและเป้าหมายเอง (ตัวอย่างดี: "Change the date format from 'Jul-8-1999' to MM-DD-YYYY") ([Dromo](https://developer.dromo.io/guides/using-transform-data.md)); Ingestro ใช้ `key`, `label`, `alternativeMatches` โดยไม่ระบุ sample value เป็น input ([Ingestro columns](https://docs.ingestro.com/sdk/columns)); Collibra "never accesses your actual data rows" ([Collibra](https://productresources.collibra.com/docs/collibra/2026.08/Content/UnifiedDataQuality/ta_suggest-rules.htm)) ผู้ขายกลุ่มนี้ชดเชยด้วย alias ที่นักพัฒนาประกาศและ history แทนการมองค่า — ซึ่งก็คือเหตุผลที่พวกเขาต้องการ human confirm ทุกคอลัมน์ที่ไม่ exact และเป็นข้อได้เปรียบเชิงโครงสร้างของ FORMA ที่รันในเครื่องของตนและมองค่าได้โดยไม่ติดปัญหา privacy แบบ ReMatch/LSM ที่ต้องเป็น data-free ([ReMatch](https://arxiv.org/html/2403.01567v2); [LSM](https://www.microsoft.com/en-us/research/?p=909858))

เรื่องโครงสร้างชีต (หัวหลายชั้น, แถวหมวด, แถวรวม) วรรณกรรมบอกว่าส่วนที่แก้ได้คือ "ตารางอยู่ตรงไหน" และส่วนที่ยังยากคือ "หัวหมายความว่าอะไรเมื่อกินหลายแถว/คอลัมน์" SpreadsheetLLM ทำ table detection ที่ EoB-0 ได้ F1 **0.759–0.789** ด้วย fine-tuned GPT-4 บน compressed encoding เทียบ TableSense-CNN 0.666 โดยบีบอัดได้ 24.79× (1,548,577 → 62,469 token) ([SpreadsheetLLM](https://arxiv.org/html/2407.09025v2)) แต่ header recognition บน 237 ตารางได้ F1 ≈ 0.80–0.85 เฉพาะโมเดล 405B ส่วน 7B ได้ 0.06–0.30 และความผิดใหญ่สุดอยู่ที่ hierarchical headers และ merged cells แม้ในโมเดลใหญ่ ([TaDA25_14](https://tabular-data-analysis.github.io/tada2025/papers/TaDA25_14.pdf)) agent ปี 2025–26 จึงลงเอยที่ pre-structuring เชิงกำหนดก่อน: SQUARE ให้คะแนนความซับซ้อนจากความลึกของหัวและจำนวน merge แล้ว route ([arXiv 2512.04292](https://arxiv.org/pdf/2512.04292)), SpreadsheetAgent มีขั้น structure-extraction ที่มองหา hierarchical headers/merged cells/multi-sheet ก่อน reasoning ([ACL 2026](https://aclanthology.org/2026.acl-long.86.pdf)) ไม่มีใครวัด "subtotal row detection" หรือ "multi-sheet linkage" เป็น sub-task — การที่ FORMA ทำ `TableSpec.section_column` เป็นกฎใน profiler (แถวที่มีเซลล์ข้อความเดียวใต้หัว ≥2 แถว = heading แล้ว fill-down) และวัดบนคอร์ปัสของตัวเองจึงเป็นแนวทางเดียวที่มี และผลก็ชัด: HAND r1 จาก 0 รายการเป็น 12 รายการตั้งแต่ครั้งแรกเมื่อโมเดลเห็นคอลัมน์ `section` ที่ profiler สร้างให้

## ความมั่นใจที่โมเดลพูดออกมาแคลิเบรตแย่ — กฎเชิงกำหนดจึงอยู่เหนือคะแนนเสมอ

วรรณกรรมเกือบทั้งหมดใช้ verbalized confidence (ขอให้โมเดลให้ 0–100 หรือ 0.00–1.00 ต่อผู้สมัคร) และไม่มีบทความ schema matching ใดวัด calibration เลย Matchmaker ตั้งเป็น MCQ ที่มี "NONE of the above" และให้ 0–100 ต่อตัวเลือก โดย prompt เขียนว่า "Your scores will be calibrated" แต่ไม่มีวิธี calibrate ใด ๆ และพบความล้มเหลวที่ตัวเลือกซ้ำ (`note_text` สองตัว) ได้ 90 ทั้งคู่; สิ่งที่มันใช้ได้จริงคือ **entropy ของ vector ความมั่นใจ** เพื่อเลือกว่าคู่ใดส่งคน ซึ่งชนะ random deferral ที่ทุกอัตรา 0–50% ([Matchmaker](https://arxiv.org/html/2410.24105v1)) ส่วนงานวัด calibration โดยตรง (Xiong et al., ICLR 2024) พบว่า LLM "tend to be highly overconfident when verbalizing their confidence": ECE ของ GPT-3/3.5/Vicuna **> 0.377** โดยเฉลี่ย, AUROC ของ GPT-4 **62.7%** "still close to a random guess", consistency-based ชนะ verbalized และ hybrid (verbalized + consistency) ดีที่สุดใน 13/20 กรณี ([arXiv 2306.13063](https://arxiv.org/abs/2306.13063)) Parciak วัด "decisiveness" เป็นตัวแทน: GPT-4 N-to-1 ตอบชัด 0.992 แต่ N-to-M เหลือ 0.029 ([Parciak](https://arxiv.org/html/2407.11852v1)) KcMF พบว่าเมื่อไม่มี pseudo-code rules ความผิดแบบ over-matching พุ่งจาก 13 เป็น 60 — ตัวเลือก "no match" ที่ชัดแจ้งคือกลไกความมั่นใจเดียวที่ทุกระบบแข็งใช้ร่วมกัน ([KcMF](https://arxiv.org/html/2410.12480v2))

ผู้ขายที่โตแล้วจึงเลิกเชื่อคำพูดของโมเดลและสร้างคะแนนจากหลักฐาน Microsoft Content Understanding เป็นรายเดียวที่อธิบายวิธี: "The score is not the LLM's self-reported certainty. A separate confidence model produces it" จาก "where and how the value appears, grounding evidence, field type and schema position, predicted value shape, comparison with labeled examples... extraction diagnostics such as ambiguity"; ฝึกบน "Microsoft-curated data, not customer data"; refresh ล่าสุดเพิ่ม AUROC "up to 14%"; และย้ำให้ถือเป็น "a risk-ranking signal rather than a calibrated probability" ([Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)) สูตรตั้ง threshold ของ Microsoft เป็นสูตรที่ยกไปใช้ได้ตรงที่สุด: รวบรวมเอกสารที่คนตรวจแล้ว → วัดความถูกต้องและ separability ต่อฟิลด์/ชนิดเอกสาร → ตั้งเป้าธุรกิจ (เช่น "catching at least 80% of known errors") → เลือก cutoff ที่ถึงเป้าด้วยจำนวนรีวิวน้อยสุด → validate บน held-out; "If no cutoff meets the target, the field stays in review"; **ฟิลด์ว่างต้องมี policy แยก** เพราะคะแนน "didn't reliably distinguish 'missed' from 'truly empty'"; และ 0.8 ถูกยกเป็นตัวอย่างของ rule of thumb ที่ *ไม่มีเหตุผลรองรับ* ผลบน >22,000 ค่า จาก >1,000 เอกสาร: ส่งรีวิว **น้อยลง 41%** ขณะยังจับ **>80%** ของความผิดที่รู้ แต่ lab สาธารณะบน CORD v2 1,000 ใบเสร็จที่เป้า 80% error coverage อนุมัติเองได้แค่ **~14%** ของค่าที่มีและ ~13% ของค่าว่าง เหลือ 73% ให้คน ([Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)) Hyperscience ไปไกลกว่าด้วยการซ่อนคะแนนดิบ: ความมั่นใจ "an internal, non-configurable value that is meaningful only inside its model" ผู้ใช้ตั้ง *accuracy target* แล้วระบบ auto-threshold จาก QA records (ต้องมีอย่างน้อย 5,000 ฟิลด์สำหรับ structured text, 2,000 สำหรับ semi-structured); เป้า 99.5% อาจเริ่มที่ automation 75% แล้วไต่เป็น 94% เมื่อ QA ฝึกโมเดล ([Hyperscience v42](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)) Rossum ที่ขาย "calibrated score" ก็ยังเตือนในเอกสาร API ว่า "Note that the threshold does not correspond to the accuracy of the fields passing the threshold!" โดยค่าเริ่มต้น `score_threshold` 0.8 ใน API แต่ 0.975 ใน UI preset "Confident" ([Rossum API](https://rossum.app/api/docs/openapi/guides/automation/); [Rossum KB](https://knowledge-base.rossum.ai/docs/using-ai-confidence-thresholds-for-automation-in-rossum)) Snowflake รายงานว่า fine-tune Arctic-Extract "widens the gap between confidence scores for correct and incorrect responses, from 0.130 to 0.249" ซึ่งคือการทำให้ *separability* ดีขึ้น ไม่ใช่ความถูกต้อง ([Snowflake](https://snowflake.com/en/blog/engineering/arctic-extract-fine-tuning/)) ในหมู่ importer ความมั่นใจเป็น *คุณสมบัติของชั้นที่ยิง* มากกว่าตัวเลข: Flatfile automap ต้องการ `strong` (>90%) หรือ `absolute` (100%) ทุกฟิลด์แบบ "all-or-nothing" คอลัมน์ต่ำหนึ่งคอลัมน์ล้มทั้ง job ([Flatfile automap](https://flatfile.com/docs/plugins/automap.md)); Ingestro ใช้ threshold 0.6 บน similarity ([Ingestro](https://docs.ingestro.com/sdk/settings)); Dromo headless ให้ `NEEDS_REVIEW` พร้อม `review_url` ถ้า map อัตโนมัติไม่ได้ ([Dromo headless](https://developer.dromo.io/getting-started/headless.md)) — ไม่มีสิ่งใดบางส่วนถูก commit

หลักการที่ทุกค่ายใช้ร่วมกันคือ **กฎอยู่เหนือคะแนน**: Rossum "never exports a document that contains validation errors" และฟิลด์ที่ตก built-in check จะไม่ automate "even when its confidence score meets the threshold" ([Rossum automation rules](https://knowledge-base.rossum.ai/docs/automation-rules-overview)); ABBYY ส่งเอกสารเข้ารีวิวเมื่อฟิลด์ใดตกกฎ และเมื่อคนแก้ค่า "it will be checked again using any applicable rules" — คำตอบของคนก็ไม่ถูกเชื่อแบบไม่ตรวจ ([ABBYY](https://docs.abbyy.com/vantage/documentation/skill-designer/process/manual-review)); UiPath ยก "synthetic consistency checks (for example, confirming line items sum to a total or that an ID checksum is valid)" เป็นสิ่งที่ทำให้ข้ามคนได้ ([UiPath](https://docs.uipath.com/document-understanding/automation-suite/2022.10/classic-user-guide/data-extraction-validation-overview)); Databricks นิยามคุณภาพเป็น "deterministic checks (schemas, required fields, totals)" + model confidence + business rules เช่น "flagging a document where tax paid is greater than salary" และ quarantine เอกสารที่ตกไว้ตารางแยก ([Databricks](https://docs.databricks.com/aws/en/large-language-models/genie-code-document-processing)) คลังศัพท์ของการตรวจมาจากโลก data quality: Deequ มี `isComplete`, `isUnique`, `isContainedIn`, `isNonNegative`, `hasApproxQuantile`, `hasSize` และ tolerance แบบ `containsURL(col, _ >= 0.5)` บวก anomaly detection บน metric ตามเวลา ([Deequ](https://github.com/awslabs/deequ)); dbt มี `unique`/`not_null`/`accepted_values`/`relationships` กับ `severity: warn|error` และ `store_failures` ([dbt](https://docs.getdbt.com/docs/build/data-tests)); Soda ทำ anomaly detection บน `row_count`, `missing_count`, `invalid_count` ด้วย Prophet แต่ต้องการ **อย่างน้อยสี่การวัดที่ cadence สม่ำเสมอ** ก่อนจะประเมินได้ ([Soda](https://docs.soda.io/soda-cl/anomaly-detection)) — สำหรับไฟล์ทุก 14 วันคือราวสองเดือนต่อลูกค้า ทุกเจ้ายังเก็บผลเป็น **สามแถบบวกตัวอย่าง**: auto / review / block และสุ่มตรวจงานที่ผ่านเอง — A2I มี `Sampling` ที่ "always send low confidence... and sample high confidence at a specified rate" (เช่น <60 ส่งเสมอ, >90 สุ่ม 5%) และ sampling เป็น deterministic ต่อ input ([AWS A2I](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-json-humantaskactivationconditions-textract-example.html)); Microsoft ทำ "outer loop" สุ่มตรวจผลที่ *ไม่ถูกธง* เพื่อจับ drift ([Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/))

ด้าน UX ของการรีวิว HCI ให้คำตอบที่ไม่คลุมเครือ: Buçinca, Malaya & Gajos (N=199) พบว่า "Adding explanations to the AI decisions does not appear to reduce the overreliance and some studies suggest that it might even increase it" คนพัฒนา heuristic ทั่วไปแทนการคิดทีละข้อ ส่วน cognitive forcing functions "significantly reduced overreliance" แต่ได้คะแนนความพอใจต่ำสุด ([To Trust or to Think](https://kgajos.seas.harvard.edu/papers/bucinca21trust.pdf)) การถาม "ยืนยัน?" จึงเสื่อมเป็นตรายางตามธรรมชาติ ขณะที่คำถามแบบ "คอลัมน์ไหนในสองนี้" เป็น forcing function อ่อน ๆ ที่ให้ labelled decision กลับมาด้วย Tamr จัดคิวตาม learning value — "high-impact pairs" ที่ระบบไม่แน่ใจที่สุดและ "have the biggest effect on what Tamr Core learns" ขึ้นบนสุด ให้ label "confident but wrong" ก่อน และอนุญาต "don't guess" ข้ามพร้อมคอมเมนต์ ([Tamr](https://docs.tamr.com/new/docs/record-pairs-reviewer)); UiPath ตั้งคะแนนฟิลด์ที่คนแก้เป็น 100% เพื่อเอาออกจากกลุ่ม "requires attention" ([UiPath forum](https://forum.uipath.com/t/document-understanding-2022-5-community-preview/442187)); และ Microsoft แสดงโหมดเริ่มต้นที่ปลอดภัยสำหรับทีมที่ยังไม่เชื่อโมเดล: ลูกค้าประกันใช้ความมั่นใจเป็น *priority label* เท่านั้น "the labels directed attention and did not authorize automatic processing" ([Microsoft Foundry blog](https://devblogs.microsoft.com/foundry/content-understanding-confidence-grounding-hitl/)) ส่วนตัวเลข STP ที่น่าเชื่อถือจากภายนอกมีแค่ค่าเฉลี่ยอุตสาหกรรม AP touchless 32.6% (Ardent Partners 2025, n=212, อ้างผ่าน Hypatos) ([Hypatos](https://www.hypatos.ai/knowledge-base/what-is-touchless-rate-ap-automation)) — ไม่มีตัวเลข STP สำหรับ schema mapping เลย FORMA ควรตั้ง baseline "รอบที่ส่งออกโดยคนไม่แตะ mapping" ของตนเองก่อนตั้งเป้า

## การเรียนรู้จากการแก้ของคนคือสองลูปที่ความเร็วต่างกัน และไม่มีใครฝึกโมเดลจากการแก้ครั้งเดียว

ไม่มีผู้ขายที่โตแล้วรายใด retrain โมเดลจากการแก้หนึ่งครั้ง สิ่งที่มีผลทันทีคือ **หน่วยความจำเชิงกำหนด** และสิ่งที่เรียนรู้เชิงสถิติถูก **batch และ gate** ABBYY Vantage Online Learning เป็นตัวอย่างที่เขียนตัวเลขครบที่สุด: เริ่มเก็บจากเอกสารแรกที่คนแก้, training set สูงสุด 10,000 / test set 1,000, session แรกเริ่มเมื่อชุดข้อมูลโตขึ้น **10%** (ลดเป็น 5% หลัง session ที่ล้มเหลว), และ "the skill is updated only if Online Learning yields at least a **1% accuracy increase**" — ที่สำคัญ online learning "does not create a new skill version" เวอร์ชันเปลี่ยนเฉพาะเมื่อ publish ([ABBYY](https://docs.abbyy.com/vantage/documentation/runtime/online-learning/online-learning)) Hyperscience auto-thresholding "runs nightly" บน QA records หลายพันรายการ ([Hyperscience](https://help.hyperscience.ai/v42/docs/transcription-accuracy-and-automation)); Tamr ต้องกด job "Apply Feedback and Update Results" และแนะให้ label "at least 50 pairs" ก่อนฝึกครั้งแรก ([Tamr](https://docs.tamr.com/new/docs/record-pairs)); แม้ผลิตภัณฑ์นอก IDP อย่าง Norman Finance ก็ auto-book pattern ที่จำได้ก็ต่อเมื่อ "confirmed at least twice" ([Norman Finance](https://norman.finance/de/en/blog/categorization-learns-from-corrections)) และ Super.AI แนะอย่างน้อย 30 data points ต่อฟิลด์ก่อนเลือก threshold ([Super.AI](https://docs.super.ai/docs/confidence-score)) ส่วน "instant learning" ที่ Rossum ทำตลาดถูก hedge ในเอกสารตนเองว่า "depending on your version of the AI engine, changes may affect predictions either immediately or after an agreed-upon period" ([rossum.university mirror](https://mrtnzlml.github.io/rossum.university/docs/learn/ai-learning))

ลูปที่เร็วมีสามรูปแบบ: (1) **fingerprint ของชุดคอลัมน์** — Ingestro ผูก mapping ที่บันทึกกับ "scenario identifier, a fingerprint of the source columns and target structure" และถ้าหัว/key/isMultiSelect/ค่า dropdown ต่างไปแม้ตัวเดียว "automatic mapping is not triggered" โดยมีโหมด `gapFill` ที่ใช้ของเดิมเท่าที่ยังตรงแล้วให้ AI เติมเฉพาะคอลัมน์ใหม่ ([Ingestro](https://docs.ingestro.com/sdk/settings)); (2) **ตัวระบุผู้ส่ง** — Dromo `autoMapHeaders` จำการ map ต่อ `importIdentifier` และเก็บเฉพาะ mapping + unique values ของ select field ในโหมด `MAPPINGS_ONLY` ([Dromo](https://developer.dromo.io/reference/settings/settings.md)); (3) **alias ที่สะสมจากคน** — CSVbox "User Keywords" ที่ดู/ลบได้ ([CSVbox](https://help.csvbox.io/dashboard-settings/sheet-options)) ลูปที่ช้าคือการเรียนรู้ข้าม tenant: Informatica CLAIRE ใช้ "anonymous metadata" ข้าม IDMC organizations แบบ opt-in และอ้าง "40 petabytes of enterprise data patterns" (แหล่งอื่นบอก 14 PB — ขัดกัน) ([Informatica](https://onlinehelp.informatica.com/IICS/prod/CDI/en/hh-cloud-mappings/CLAIRE_recommendations.html); [VentureBeat](https://venturebeat.com/ai/enterprise-data-fragmentation-isnt-going-away-how-informatica-has-evolved-its-ai-capabilities-to-solve-real-challenges)); Oracle Gen-2 publish ทุก integration บน instance เข้า recommendations engine โดยค่าเริ่มต้น ([Oracle](https://docs.oracle.com/en/cloud/paas/integration-cloud/mapper-user/accepting-mapping-recommendations-recommendations-engine.html)) ข้อสังเกตที่ย้อนแย้งคือผลิตภัณฑ์ยุค LLM (Fabric Copilot "doesn't understand previous inputs", Glue Q, BigQuery data prep ที่ "Your example change to the data isn't saved") มีการเรียนรู้ถาวร *น้อยกว่า* ผลิตภัณฑ์ยุค ML (Trifacta 2016, Tamr 2019, CLAIRE 2018) — การเรียนรู้ย้ายไปอยู่ในชั้น metadata ที่ LLM อ่านเป็นบริบท (Databricks ใช้ "Unity Catalog metadata, table descriptions, lineage, popularity, and example queries") แทนน้ำหนักโมเดล ([Microsoft Learn](https://learn.microsoft.com/en-us/fabric/data-factory/copilot-fabric-data-factory); [Google](https://docs.cloud.google.com/bigquery/docs/data-prep-get-suggestions); [Databricks](https://www.databricks.com/blog/announcing-public-preview-lakeflow-designer)) ไม่มีผู้ขายใดบันทึกการใช้ *ข้อเสนอที่ถูกปฏิเสธ* เป็นสัญญาณลบ และไม่มีใครทำ few-shot จาก mapping ของลูกค้าเดิมเข้า prompt อย่างเป็นเอกสาร

การ capture การแก้ก็มีรูปแบบร่วม: **ชี้ไปที่หลักฐาน ไม่ใช่พิมพ์คำตอบ** ABBYY ให้ reviewer "select the correct region on the document image" แล้วระบบอ่านใหม่จากตรงนั้น ([ABBYY online learning](https://docs.abbyy.com/vantage/documentation/runtime/manual-review/online-learning)); A2I ในกรณี `MissingImportantFormKey` ขอให้คน *หา* key และ value ([AWS A2I](https://docs.aws.amazon.com/sagemaker/latest/dg/a2i-json-humantaskactivationconditions-textract-example.html)); Tamr ให้ label คู่พร้อม highlight ฟิลด์ที่ตรง ([Tamr](https://docs.tamr.com/new/docs/record-pairs-reviewer)) สำหรับ schema mapping การเทียบเคียงคือให้ reviewer เลือก *คอลัมน์ต้นทาง* ที่ควรป้อนฟิลด์ ซึ่งให้กฎที่ใช้ซ้ำได้ ส่วนการพิมพ์ค่าให้แค่ override หนึ่งแถว ส่วนเรื่องเวอร์ชันและ drift Hyperscience วาง pattern ที่ชัดที่สุด: layout มี working version และ committed version, และ "the system can only match submission pages to Live versions" — เอกสารที่ไม่ match เวอร์ชัน Live คือสัญญาณ drift ในตัวมันเอง ([Hyperscience](https://help.hyperscience.ai/v40/docs/what-is-a-layout-version)) ส่วน drift ที่ไม่พึ่งความมั่นใจของโมเดลถูกตรวจจากสามสัญญาณอิสระ — schema/header change, volume (row count เทียบประวัติ), และ distribution ของค่าต่อฟิลด์ (KS test) — ซึ่งทั้ง Soda/Monte Carlo และบทความ IDP ใช้ร่วมกัน ([Soda](https://docs.soda.io/soda-cl/anomaly-detection); [Monte Carlo](https://docs.getmontecarlo.com/docs/monitors-overview); [The Neural Base](https://theneuralbase.com/document-ai/learn/advanced/monitoring-extraction-accuracy/)) ไม่มีผู้ขายรายใดเปิดเผยว่า *ตรวจจับ* การเปลี่ยน layout ของผู้ส่งอย่างไรนอกจาก "match ไม่ได้" และไม่มี benchmark วิชาการสำหรับไฟล์ซ้ำทุก 14 วันจากแหล่งเดิม — ลูปหลักของ FORMA ไม่มี benchmark สาธารณะรองรับ

ผลวัดของ FORMA เองยืนยันวรรณกรรมในสองจุดที่น่าสนใจเป็นพิเศษ หนึ่ง — self-check ทำงาน 3 ใน 12 ครั้งที่เรียกโมเดล และทุกครั้งแก้ในรอบเดียว โดยกติกา "เก็บ mapping ที่ดีที่สุด" ไม่เคยถูกใช้ นี่คือ Self-Debugging "typically one debugging turn is sufficient" และยืนยันว่า `FORMA_LLM_SELF_CHECK_ROUNDS = 2` เพียงพอ ไม่มีเหตุให้เพิ่ม สิ่งที่มันจับได้ (SAPTH อ้าง `MTSTB` จาก frame ผิด, ACCTH แถวท้ายไม่มี sku, DYN r3 อ้างคอลัมน์จากชีตเดิม) ล้วนเป็น "source column not found" และ "null identity key" — ความผิดชนิด schema linking ที่ Spider 2.0 นับเป็น 27.6% และที่ oracle แบบ "รันผ่านไหม" ตรวจไม่ได้แต่ oracle ของ FORMA ตรวจได้ สอง — deepseek-v4-pro ให้ความถูกต้องเท่าเดิม 10 จาก 12 รอบ แย่กว่า 1 รอบ (DYN r1 0.764 vs 0.842 เพราะเลือกชีต Sales Price 5 แถวเป็นแหล่งราคา *เดียว* และ "เห็นเองและเขียนไว้ในคำถามอิสระ... แต่ไม่แก้") ช้ากว่า 2–3 เท่า (241–542 วินาที) — ตรงกับ Snell/Monkeys ที่ว่าเครื่องจักรรอบโมเดลให้ผลมากกว่าขนาดโมเดลเมื่อโมเดลเล็กทำได้ไม่เลวอยู่แล้ว และตรงกับ Olausson ที่ GPT-4 "never expressed uncertainty" แต่ v4-pro กลับเห็นปัญหาแล้วไม่ลงมือ ซึ่งคือเหตุผลว่าทำไมกฎ "สินค้า N จาก M ไม่มีราคาทั้งที่รายการอื่นมี" ต้องเป็น oracle เชิงกำหนดที่ *ส่งกลับให้แก้* ไม่ใช่รอให้โมเดลสังเกตเอง

สิ่งที่หลักฐานบอกชัดว่า **ไม่ควรทำ** มีสี่ข้อ อย่าเพิ่มรอบ self-check เกิน 2 — Self-Debugging บน Spider เปลี่ยน <0.1% หลังรอบแรก, LitE-SQL และ Self-Refine ลู่เข้าภายใน 1–3 รอบ และ FORMA ก็ไม่เคยต้องใช้รอบที่สอง อย่าเพิ่ม "ให้โมเดลอ่าน mapping ตัวเองแล้วทบทวน" โดยไม่มีข้อมูลใหม่ — Huang et al., Olausson (32/80 feedback ผิดชัด), SQLens ("breaks the most correct queries") และ Matchmaker (57.1 vs 57.9) ชี้ทางเดียวกัน อย่าเพิ่ม LLM critic ตัวที่สองเป็น gate — self-preference มีความเชื่อมโยงเชิงสาเหตุกับ self-recognition ([Panickssery et al.](https://arxiv.org/abs/2404.13076)), CriticGPT แม้ชนะคน 63% ก็ยัง hallucinate "still quite high" ([CriticGPT](https://arxiv.org/abs/2407.00215)), และ Agent-as-a-Judge ที่ทำได้ 86.6–92.1% ก็เพราะมัน *รันของจริงใน workspace* ไม่ใช่เพราะมันเป็น LLM ([arXiv 2410.10934](https://arxiv.org/abs/2410.10934)) — oracle เชิงกำหนดของ FORMA คือ "agent judge" อยู่แล้ว และอย่าเปลี่ยนโมเดลด้วยความหวังว่าจะแก้เรื่องตัดสิน (category รหัส/ชื่อ, หน่วย) — v4-pro ตัดสินเหมือน flash ทุกข้อ และสิ่งเหล่านี้คือ *นโยบาย* ที่ควรอยู่ใน schema registry/กฎ ไม่ใช่ใน prompt

## สรุป

ภาพที่ออกมาจากทั้งห้าสายหลักฐานคือ FORMA ไม่ได้ตามหลังเจ้าใหญ่ในเรื่องการตรวจงานของโมเดล — มันอยู่ในกลุ่มเล็กมาก (Databricks Genie Code, Palantir AIP Evals, งานวิจัยสาย execution-feedback) ที่ปิดลูปด้วย oracle เชิงกำหนดโดยอัตโนมัติ ขณะที่ importer เชิงพาณิชย์ส่วนใหญ่ยังปิดลูปผ่านคนและไม่ให้โมเดลเห็นค่าเลย สิ่งที่เปลี่ยนไปจากการอ่านวรรณกรรมคือ *ตำแหน่งของกำไรที่เหลือ*: ไม่ได้อยู่ที่การตรวจ (ซึ่งทำครบและวัดแล้วว่าลู่เข้ารอบเดียว) แต่อยู่ที่ **สิ่งที่โมเดลเห็นก่อนเขียน** — ค่าในคอลัมน์ที่ถูกบังคับให้เห็น และ mapping ที่คนเคยอนุมัติจากลูกค้าอีก 299 รายที่วันนี้ลูกค้าใหม่ไม่ได้ประโยชน์เลย ทั้งสองอย่างเป็นคันโยกที่วรรณกรรมวัดได้ใหญ่ที่สุด (+20 จุดจาก anchor, 40 → 90% จาก grounding) และทั้งสองไม่ต้องแตะโมเดลหรือเพิ่มรอบ

ข้อสังเกตที่ควรจดไว้สำหรับไฟล์ลูกค้าจริง: benchmark ไฟล์จริงทุกชุดต่ำกว่าไฟล์สะอาดเป็นสิบเท่า และ Microsoft ที่มี confidence model ที่สร้างมาเฉพาะทางก็ยังอนุมัติเองได้แค่ ~14% ของค่าบนใบเสร็จสาธารณะที่เป้า 80% error coverage ความสำเร็จของระบบแบบนี้จึงไม่ได้วัดจาก auto-approve rate แต่วัดจากว่า **คิวรีวิวจับความผิดได้กี่เปอร์เซ็นต์ด้วยคำถามน้อยที่สุด** — ตัวเลข 58 → 21 คำถามของ FORMA คือ metric ที่ถูกต้องแล้ว และตัวเลขถัดไปที่ควรเริ่มเก็บตั้งแต่ลูกค้าจริงรายแรกคือ error rate บนตัวอย่างสุ่มของรอบที่ผ่านเอง เพราะนั่นคือค่าความถูกต้องเดียวที่ซื่อตรงพอจะใช้ตั้ง threshold ใน `policies/approval.yaml` แทนตัวเลขที่โมเดลพูดเอง
