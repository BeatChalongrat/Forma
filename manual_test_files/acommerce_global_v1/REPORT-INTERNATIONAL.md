# ผลทดสอบ FORMA กับไฟล์จำลองหลายประเทศ และผู้ประเมินบริบทใหม่

ทดสอบ 2–3 พฤศจิกายน 2026 (Asia/Bangkok), run `intl-20261102-a` บน stack Docker จริง ด้วย model ID `deepseek-flash` ไม่ใช่ mock LLM

## ข้อสรุป

FORMA อ่านและจับคู่ข้อมูลที่มีหลักฐานชัดได้ดีในชุดเล็กนี้ รวมถึงหลายภาษา รูปแบบตัวเลขต่างประเทศ การรวมหลายไฟล์/หลายคลัง และ JSON Schema ที่ต่างจาก product เดิม แต่ **ยังไม่ผ่านเกณฑ์ปล่อยทำงานอัตโนมัติสำหรับไฟล์ใหม่ทั่วไป** จุดอ่อนที่ยืนยันได้คือการเปลี่ยนคำถามของ AI ให้เป็นคำตอบที่นำไปใช้ได้ถูกต้องและมีขอบเขต ไม่ใช่แค่เลือกโมเดลที่ฉลาดขึ้น

ผู้ประเมินอิสระทำ field ที่คาดหวังถูกครบในกรณีที่ข้อมูลพอ และแก้ทั้ง 4 กรณีกำกวมได้หลังรับคำตอบที่ควบคุมไว้ ส่วน FORMA ตรวจพบประเด็นกำกวม แต่เส้นทางตอบคำถามปัจจุบันยังปิดงานทั้ง 4 กรณีนี้ไม่ได้อย่างถูกต้องโดยตรง จึงไม่ควรอ้างว่าประสบการณ์เทียบเท่าการให้ผู้ช่วยอ่านไฟล์และถามกลับแล้ว

ผลนี้เป็น **synthetic pilot** ไม่ใช่การรับรองไฟล์ของลูกค้า aCommerce จริง ไม่ใช่คะแนน overall ของระบบ และไม่ใช่หลักฐานว่าโมเดลหนึ่งเหนือกว่าอีกโมเดลหนึ่ง

## สิ่งที่ทำในรอบนี้

1. เพิ่ม scorer ที่นับข้อมูลซ้ำจริง ไม่ทับ SKU/price key เป็น dictionary; ราคาใช้ key รวมวันเริ่มใช้; ไม่เพิ่มคะแนนจาก null ที่ไม่มีหลักฐาน เก็บ missing/extra rows และ extra collection members
2. เพิ่ม runner ที่ checkpoint/resume ได้ แยก customer/schema ของการทดลอง เก็บ prediction ก่อนอ่าน oracle และไม่กดตอบคำถามทุกข้อหรือส่งออกอัตโนมัติ
3. พบว่าโจทย์ `task.md` เดิมไม่มีเส้นทางเข้า context ของ mapper จึงเพิ่ม `RoundIn.instructions` เก็บใน `ImportRound.notes` ส่งให้ schema/mapping/adaptation agents และเก็บ SHA256 เป็นหลักฐาน เมื่อโจทย์เปลี่ยนห้าม reuse mapping เดิมตรง ๆ แม้ header เหมือนเดิม
4. รันไฟล์จริงผ่าน API, worker, parser, model, DSL engine และ preview ของ FORMA ไม่มีการฉีด expected JSON เป็น mapping
5. ใช้ผู้ประเมินในบริบทใหม่ตามที่ผู้ใช้อนุญาต ให้เฉพาะ inputs/task/schema; เก็บ prediction ก่อนตอบกลับ แล้วให้คำตอบเรื่องวันที่ สกุลเงิน หน่วย และราคาขัดแย้งตามสคริปต์เดียวกัน

ไม่ได้แก้กฎตัวเลข/หน่วยหรือระบบ clarification ระหว่างการวัดเพื่อไล่คะแนน และไม่ได้ commit

## ขอบเขตและความยุติธรรมของการเทียบ

- ชุดหลัก 16 กรณี / 20 รอบ และอีก 1 งานที่เปลี่ยน JSON Schema รวม 21 งาน งานละ 12 SKU
- 22 ไฟล์ต้นทาง: Excel 6 ไฟล์ และ CSV/TSV 16 ไฟล์; เป็นข้อมูลสมมติ ไม่ใช่ export จริงของแบรนด์ที่ค้นพบ
- cold ใช้ customer แยกและ target schema แยก ลดการปนกับความจำเก่า
- G02/G03 รอบแรกได้รับ **การตรวจโดยผู้ประเมินก่อนอนุมัติ mapping** เพื่อสร้าง baseline สำหรับ r2/r3 ไม่ใช่อนุมัติแบบเหมา ไม่มี transform/export dataset
- G03 baseline ต้องรับรองโดยผู้ตรวจเป็นพิเศษ: root มี SKU ซ้ำเพราะเป็น SKU × คลัง แต่ตรวจแล้ว inventory ครบทั้ง 24 แถว ภายใต้ 12 สินค้า จึงแยกการยอมรับโดยผู้ตรวจออกจาก `verification.passed=false`
- ผู้ประเมินคู่เทียบเป็น coding agent ที่อ่านไฟล์ด้วยเครื่องมือได้ ไม่ใช่การเปิดหน้า ChatGPT/Claude จริง และไม่ได้ควบคุมให้เป็นโมเดลเดียวกันหรืองบเท่ากัน จึงใช้ค้นหาช่องว่างของ FORMA ไม่ใช้ประกาศชนะ/แพ้ตัวผลิตภัณฑ์
- โฟลเดอร์ที่ให้ agent มีเฉพาะ input/task/schema ไม่มีเฉลย แต่เป็น host ร่วมและอาศัยขอบเขตคำสั่ง ไม่ใช่ filesystem sandbox ที่พิสูจน์การแยกสิทธิ์ได้
- ผู้ประเมินได้รับแพ็กหลายกรณีในบริบทใหม่เดียว ไม่ใช่แชตอิสระใหม่ต่อทุกกรณี; รอบซ้ำของคู่เทียบไม่ได้วัดกลไก approved-memory แบบ FORMA
- ทดสอบหนึ่งครั้งต่อกรณี มีการรันซ้ำเฉพาะปัญหาการตั้งค่าการทดลองที่เก็บหลักฐานไว้ ยังไม่ได้วัดความแกว่งอย่างน้อย 3 runs

## ตัวเลขสรุปจาก run ที่เสร็จแล้ว

- 21/21 งานมี mapping และ preview ครบ งานละ 12 SKU รวม 252 output records; ไม่มี SKU เกิน/ขาดในผลสุดท้าย
- กรณีข้อมูลชัดเจน: 12 cold cases + 4 รอบซ้ำ/เปลี่ยนความหมาย + 1 alternate schema = 17 งาน มี `field_accuracy=100%` สำหรับค่าที่ oracle ระบุ
- ไม่ใช้จำนวนนี้รับรอง 4 กรณีกำกวม: G13 วันที่ตรงแบบ provisional, G14 currency ผิด 12 ค่า, G15 unit ผิด 12 ค่า, G16 มี price item เกิน 1 ตัวที่ยังรอคำตัดสิน
- ถ้ารวมตัวเลข field ทั้งหมดจะได้ 2,280/2,304 = 98.96% แต่ **ห้ามใช้เป็นคะแนน overall** เพราะไม่ได้วัดความครบวงจรของคำถาม, extra facts, สิ่งที่เดาตรงโดยบังเอิญ และภาระคนตรวจ
- รวม 58 การ์ด และข้อความ open_questions 68 ข้อในทุกงานก่อน manual answers; ข้อความบางข้อเป็นข้อมูลแจ้ง ไม่ใช่คำถามที่จำเป็นทั้งหมด
- 3 profile jobs ล้มครั้งแรกแล้ว recover; ผลสุดท้ายไม่มี job failed ค้างในชุดประเมิน แต่ความล้มเหลวครั้งแรกยังนับในรายงาน
- มี `verification.passed=false` ใน G03 r1/r2/r3 และ G16; G01 มีการ์ดเกิน 8; G01/G11 มี disagree อย่างน้อย 8; ไม่พบ LLM fallback ใน 21 ผลที่บันทึก
- cost ตาม agent logs: ชุดหลัก **$1.965625** / 60 model calls; setup attempts ของ G03 เพิ่ม **$0.475737** / 11 calls; รวมที่บันทึก **$2.441362** / 71 calls — เป็นราคาประมาณจาก fallback rate ไม่ใช่ยอดเงินจริง ไม่รวมค่าใช้บริการของผู้ประเมิน Codex

## ผลรอบซ้ำและเปลี่ยนความหมาย

| งาน | วิธีทำงานจริง | Field accuracy | การ์ด | หมายเหตุ |
|---|---|---:|---:|---|
| G02 r2 | memory จาก mapping ที่ตรวจแล้ว | 100% | 0 | auto_approve, ไม่มี model call เพิ่ม |
| G02 r3 | ai_adaptation เมื่อคำสั่งเรื่อง number format เปลี่ยน | 100% | 0 | review; ยังมีข้อความเปิด 1 ข้อ |
| G03 r2 | memory จาก mapping ที่ตรวจแล้ว | 100% | 0 | review เพราะตัวตรวจ root dedupe; ไม่มี model call เพิ่ม |
| G03 r3 | ai_adaptation เมื่อ stock basis เปลี่ยนเป็น cartons × 12 | 100% | 0 | inventory ถูก; verification ยังติด root dedupe |

G03 r3 มี `/unit/pack_size=12` เพิ่มจากข้อมูล carton conversion ขณะที่ oracle ไม่ได้ระบุค่านี้ จึงได้ exact strict 0% แม้ค่าที่คาดหวังตรงทั้งหมด ค่านี้มีต้นทาง แต่ความหมาย “stock carton conversion” เทียบกับ “pack size ของหน่วยขาย PCS” ยังต้องกำหนดใน contract ก่อนตัดสินว่าควรเก็บหรือไม่ ไม่แก้ oracle ย้อนหลังเพื่อเพิ่มคะแนน

## วิธีอ่านคะแนน

`field_accuracy` วัดเฉพาะค่าที่ oracle ระบุ ไม่ใช่คะแนนความปลอดภัย การถามกลับ หรือความพร้อมส่งออก

`exact_record_accuracy` ในตารางเป็นแบบ strict: มีข้อมูลเพิ่มที่ oracle ไม่ระบุจะไม่ถือว่า exact ต้องอ่าน `extra_values` ประกอบ เช่น G04 เก็บ parent style และ G09 เก็บข้อความญี่ปุ่นต้นทางใน attributes ซึ่งมีหลักฐาน ไม่ควรเรียกว่า map ผิดเพียงเพราะ oracle ไม่ใส่ไว้

กรณีกำกวมแยกออกจากคะแนนข้อมูลที่ชัดเจน: การเว้นค่าและถามกลับเป็นพฤติกรรมที่ถูก ขณะที่ค่าที่เดาแล้วบังเอิญตรงเฉลยไม่ได้แปลว่าเข้าใจถูก เช่นวันที่ G13 ก่อนตอบกลับ ส่วน scorer ที่ใช้วันเป็น collection key จะนับ price fields หลายตัว missing เมื่อยังไม่ทราบวัน จึงห้ามเอาคะแนนก่อนตอบของคู่เทียบกรณีนี้มาตัดสินว่าโมเดลอ่านราคาไม่เป็น

ดูตารางทุกกรณี/รอบและตัวเลขประกอบใน [RESULT-TABLE.md](runs/intl-20261102-a/RESULT-TABLE.md) และข้อมูลเครื่องอ่านได้ใน [summary.json](runs/intl-20261102-a/summary.json) ตารางรวมจำนวน/ชนิดการ์ด, ข้อความที่ยังเปิดอยู่, contested, decision, drift, self-check, เวลา, cost และธงแดง

## สิ่งที่พบจริง

### 1. งานที่ข้อมูลชัดเจน

G01–G12 ให้ field ที่ oracle ระบุถูกครบ: ไฟล์สินค้า/ราคา/สต็อกแยกกัน, Bahasa Indonesia และ decimal comma, SKU หลายคลัง, variant รองเท้า, สกุลเงินรายแถว, French spaces/comma, ตัวเลขเยอรมัน, วันที่ US, UTF-16 ภาษาญี่ปุ่น, Excel เกาหลี, เลือกราคาที่ active และภาษีรายแถว

G05 แบบ commercial-offer ให้ field ถูกครบเช่นกัน จึงมีหลักฐานว่าไม่จำเป็นต้องยึด product JSON อย่างเดียวในกรณีนี้ แต่ยังไม่ใช่ข้อพิสูจน์ว่าใช้ได้กับทุก schema

ผลก่อนให้ข้อมูลเพิ่มของคู่เทียบมี field ถูกครบในกรณีข้อมูลชัด และหลังตอบคำถาม 4 กรณีกำกวมก็ถูกครบ โดยยังมีข้อมูลต้นทางเพิ่มเติมใน attributes บางกรณีซึ่งต้องแยกจากความผิดจริง

### 2. ถามได้ แต่คำตอบยังใช้ไม่ถูก/ใช้ไม่ได้

| กรณี | สิ่งที่ FORMA ทำก่อนตอบ | ทดสอบคำตอบแล้วเกิดอะไร | ผลประเมิน |
|---|---|---|---|
| G13 วันที่ `03/04/2026` | ถาม day-first/month-first ถูกเรื่อง แต่ preview ใช้ day-first ไว้ก่อน จึงบังเอิญ field score 100% | เลือก day-first แล้ว expression กลายเป็นข้อความทั้งตัวเลือก `day-first: 3 April 2026 (2026-04-03)` แทน parser/date ISO | ไม่ผ่านวงจรรับคำตอบ; **ไม่ได้ apply** |
| G14 สัญลักษณ์ `$` | ถามสกุลเงิน แต่ใส่ THB เป็น provisional default | คำตอบ SGD ถูกปฏิเสธ HTTP 422 เพราะ enum มีเฉพาะ THB/USD | ถามตรง แต่ไม่มีคำตอบที่ถูกให้กรอกผ่าน API นี้ |
| G15 หน่วย `BT` | engine แปลงเป็น BAG; ข้อความถามให้ยืนยัน canonical unit แต่ไม่มีการ์ดเรื่องหน่วย | ส่ง BOTTLE ถูกปฏิเสธ HTTP 422 ว่า field ไม่ได้รอคำตอบ | เป็นค่าหน่วยผิดจริง 12 สินค้า และไม่มีเส้นทางแก้คำถามนั้นโดยตรง |
| G16 ราคา SKU เดียวขัดแย้ง | ถามว่าราคา 1234.56 หรือ 9999 ถูก แต่เก็บทั้งคู่ใน preview | ไม่มีการ์ด amount/การตัดสินราย SKU; preview probe ถูกปฏิเสธ 422 | การถามและพักตรวจเหมาะสม แต่ยังปิดคำตอบให้จบเฉพาะรายการไม่ได้ |

ทั้งสี่กรณีอยู่ใน review ไม่ได้ส่งออก จึงไม่ใช่หลักฐานว่าระบบเผยแพร่ข้อมูลผิดแล้ว แต่ไม่ผ่านเกณฑ์ “ตอบคำถามแล้วได้ผลที่ถูกครบ” สำหรับการใช้งานทั่วไป

G13 มี nuance สำคัญ: `preview.ok` และ `validation.ok` เป็น true แต่ `stats.invalid_records=12` และ findings แจ้งวันที่ผิดครบ 12 แถว ตัวตรวจข้อมูลทำงาน แต่สถานะสรุปกับการใช้งานของหน้าตอบคำถามไม่สอดคล้องกัน อย่าสรุปว่าตัว engine ไม่ตรวจรูปแบบวันที่เลย

คำตอบของคู่เทียบทั้งสี่กรณีอยู่ใน `blind-predictions/B13_r1` ถึง `B16_r1` แยก before/after พร้อม hash ไม่มีการแก้ผล before ย้อนหลัง

### 3. การ์ดภาษีอาจทำให้ข้อมูลที่ถูกอยู่แล้วผิด

G12 อ่าน tax flag รายแถวถูกทั้ง 12 สินค้าก่อนตอบ แต่ระบบยังสร้างคำถาม boolean เรื่องภาษีทั้งไฟล์จากข้อความ heuristic เก่า เมื่อทดลอง preview `true` หรือ `false` แต่ละแบบกลับเขียนทับ flag ที่เดิมถูกอยู่แล้ว 6 จาก 12 รายการ

นี่เป็น preview regression probe เท่านั้น ไม่ได้ apply และไม่ได้ถือเป็นคำตอบของผู้ใช้จริง ต้องแยก “ยืนยันว่าการอ่านคอลัมน์ถูก” ออกจาก “ตั้งค่าคงที่ให้ทุกแถว”

### 4. ความถูกต้องไม่ได้แปลว่าภาระตรวจน้อย

G01 field score 100% แต่มีการ์ด 10 ข้อ และ G11 มี 8 ข้อ หลายรายการเกิดจาก heuristic กับ AI ให้ expression ต่างกัน หรือถามยืนยัน field ที่ไม่มีในไฟล์/มีค่า explicit อยู่แล้ว

G03 ตัวตรวจ root dedupe แจ้งปัญหาเพราะ SKU ซ้ำต่างคลัง ทั้งที่ output เก็บ inventory ทั้งสองคลังครบ การตรวจควรเข้าใจ grain ของ root/child collections และการรักษาข้อมูล ไม่ใช่เหมารวมว่า root dedupe ทำข้อมูลหาย

### 5. ระบบงานและ harness มีปัญหาที่ต้องแยกจาก AI

- G02/G04/G06 profile ครั้งแรก failed เพราะ worker ยังไม่รับ schema revision ใหม่ในช่วง TTL 5 วินาที ไม่มี mapping call ในครั้งที่ล้ม เก็บ `initial-profile-failure.json` ไว้ แล้วรัน profile job เดิมใหม่
- API retry ทำสถานะ DB เป็น queued แต่ ARQ ยังเก็บผลของ job ID เดิม ทำให้สาม retry ไม่ทำงานตามคิว ในการทดสอบนี้เรียก `run_job` ของ ID เดิมภายใน worker container เพื่อดำเนินต่อ ไม่ได้สร้างผลลัพธ์เทียม ต้องแก้กลไก retry จริงก่อนอาศัยมันใน production
- schema ID ของงาน alternate ยาวจน audit_log เก็บไม่ได้ ใช้ชื่อสั้นใน harness เพื่อทดสอบต่อ ไม่ได้แก้ข้อจำกัด DB
- การย่อชื่อ schema ใน harness เคยทำให้ G03 warm สองรอบได้ reference ต่างจาก baseline จึงเก็บเป็น `setup-attempts` และรัน warm ใหม่ด้วย reference เดิม ผลรอบที่ปนนี้ **ไม่นับเป็นผล reuse** แต่รวมต้นทุนแยกไว้ ไม่เลือกผลที่คะแนนดีกว่า

## ควรทำต่อในข้อ 4 ตามลำดับ

1. **ทำ clarification เป็นคำสั่งที่มีชนิดและขอบเขต**: แยก label กับ value; คำตอบวันที่ต้องเปลี่ยน parser locale/format ไม่ใช่ const string; ระบุ SKU/source/collection ที่เกี่ยวข้อง; free text/other สำหรับคำตอบที่ตัวเลือกไม่ครอบคลุม; แปลง open question ที่ actionable เป็นคำถามตอบได้
2. **ตรวจคำตอบก่อนบันทึกและก่อนอนุมัติ**: ใช้ invalid_records/findings ร่วมกับความถูกต้อง DSL; ข้อมูลที่ถูกอยู่แล้วต้องไม่แย่ลง; ถ้าคำถามเป็น row-scoped ห้ามเปลี่ยนค่าทั้งไฟล์ ตรวจ publish gate แยกจาก UI ด้วย
3. **แก้การอนุมานหน่วย/สกุลเงิน**: `BT` ต้องเป็น unresolved จนมีหลักฐานหรือตารางแปลของลูกค้า/ต้นทาง; `$` ไม่เท่ากับ USD และค่า default ไม่เท่ากับข้อมูลยืนยัน; เก็บคำตอบเป็น rule ที่มี provenance และ scope
4. **แก้ verifier ให้เข้าใจ grain และลดคำถามลวง**: เช็กว่า root dedupe ยังรักษา child items ครบหรือไม่; เปรียบเทียบความหมาย/ผลของ expression ไม่ลงโทษเพียงโครงสร้างต่าง; metadata ที่ไม่มีใน source ไม่ควรกลายเป็นคำถาม business decision ทุกครั้ง
5. **แก้ schema propagation และ job retry**: ก่อนเริ่มงาน worker ต้องเห็น target revision ที่ round อ้างถึง; retry ต้อง enqueue ได้จริงแม้มี result key เดิม; ทดสอบ recovery โดยไม่ต้องสั่ง CLI ช่วย
6. **ทำ cost accounting ตาม provider/model จริง**: แสดง unknown rate เมื่อไม่รู้ราคา แยก estimates จาก billed usage และไม่ใช้เรตสำรองโดยไม่ติดป้าย
7. หลังแก้ เพิ่ม regression สำหรับหลักฐานเหล่านี้ แล้วรันทั้งชุดซ้ำอย่างน้อย 3 seeds/runs; ต่อด้วย held-out anonymized exports จริง, JSON schema ใหม่, ไฟล์ใหญ่และโหลดพร้อมกัน เกณฑ์ขั้นต่ำคือ critical errors เป็นศูนย์ และ 4 ambiguity cases ต้องถามและรับคำตอบสำเร็จโดยไม่ทำลายข้อมูลอื่น

## ก่อน–หลังงานรอบนี้

| ก่อน | หลัง |
|---|---|
| scorer อาจซ่อนราคาซ้ำ/เพิ่มคะแนนจากช่องว่าง | เห็น extra price items และคะแนนจากค่าที่มีหลักฐานเท่านั้น |
| ผล AI กับคำตอบจากคนปนกันได้ | มี before, controlled-reply preview และผลของคู่เทียบ before/after แยกกัน |
| task ของการทดลองไม่ได้ส่งเข้า mapper อย่างพิสูจน์ได้ | มี instructions bridge และ hash ใน agent_log |
| เปลี่ยนคำสั่งแต่ header เดิมอาจเข้าเส้นทาง reuse ตรง ๆ | ตรวจ requirement changes ก่อนเลือก reuse |
| รู้เพียงว่าโมเดลตอบ JSON ได้ | เห็นช่องว่างการถามกลับ, preview, verifier, retry และต้นทุนจากหลักฐานที่ทำซ้ำได้ |

งานรอบนี้ทำให้ **การวัดผลและการส่งโจทย์ถูกต้องขึ้น** ไม่ได้อ้างว่าแก้จุดบกพร่อง production ที่พบครบแล้ว
