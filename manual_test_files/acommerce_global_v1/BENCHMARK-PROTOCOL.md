# วิธีเทียบ FORMA กับการโยนไฟล์ตรงให้ ChatGPT / Claude

เป้าหมาย: วัดว่าอ่านไฟล์ เข้าใจธุรกิจ จับคู่ JSON และถามเมื่อข้อมูลไม่พอได้ดีเพียงใด ไม่ใช้ชื่อโมเดลหรือคะแนนเฉลี่ยตัวเดียวรับรองความแม่นยำ

## แยกการทดลองสองประเภท

1. **คุณภาพระบบเมื่อใช้โมเดลเดียวกัน:** FORMA + โมเดล X เทียบการให้โมเดล X ทำงานกับไฟล์และเครื่องมืออ่านไฟล์โดยตรง ภายใต้งบ token/tool/time เท่ากัน วัดผลของเครื่องมือและขั้นตอนควบคุม
2. **ประสบการณ์ผลิตภัณฑ์จริง:** FORMA/DeepSeek เทียบ ChatGPT และ Claude ที่ผู้ใช้เลือก รุ่นและโหมดที่มีจริง ณ วันทดสอบ อนุญาตเครื่องมือประจำผลิตภัณฑ์ บันทึกความต่างของโมเดลและงบ ห้ามสรุปว่าผลต่างทั้งหมดเกิดจาก harness

ไม่มีการรันคู่แข่งหรือ paid LLM ในขั้นเตรียม fixture นี้

## สิ่งที่ให้ทุกฝั่ง

- ไฟล์ต้นทางตาม manifest เท่านั้น พร้อม task.md และ JSON Schema ปลายทางเดียวกัน
- เปิดแชตใหม่ต่อ cold case และแยก test customers/memory ใน FORMA จากข้อมูลเดิม
- ห้ามเข้าถึง oracle, expected.json, review.json, ผลที่ควรได้.md หรือผลของระบบอื่น
- ใน sandbox หรือเครื่องมือ filesystem ต้องวางเฉพาะ input/task/schema ในพื้นที่ที่โมเดลเข้าถึงได้ ไม่ใช่แค่สั่งว่าอย่าอ่านเฉลยที่อยู่ในไดเรกทอรีเดียวกัน
- warm r2/r3 ใช้ประวัติที่ยืนยันแล้วของ case นั้นเหมือนกันทั้งสองฝั่ง ห้ามนำชื่อแบรนด์หรือ locale จาก research ไปให้แค่บางระบบ
- สำหรับ FORMA ต้องตรวจว่าข้อความ task.md ถูกส่งเข้าบริบทจริงและบันทึกหลักฐาน หากไม่รองรับ ให้หยุดส่วนเทียบเท่าและรายงานข้อจำกัด ห้ามฉีดค่าที่เฉลยไว้เป็น mapping ให้ระบบ

## ลำดับการทดลอง

1. ล็อก commit, configuration, model ID, thinking mode ถ้ามี, schema hash, input hashes, timeout และงบก่อนเริ่ม
2. รัน cold r1 ทั้ง 16 กรณี บันทึก mapping และ preview **ก่อน human answers / approve / export**
3. สำหรับ G13–G16 ระบบต้องระบุข้อกำกวมเฉพาะตาม topic ใน review.json และไม่เสนอค่าที่เดาเป็นข้อเท็จจริง ไม่บังคับคำถามถ้อยคำตรงกัน ไม่บังคับ UI choice แบบเดียวกัน
4. ผู้ประเมินตอบจาก review.json เฉพาะเมื่อระบบถามเรื่องที่เกี่ยวข้อง ไม่ส่ง oracle JSON ทั้งก้อน ไม่กด confirm ทุกฟิลด์หรือเลือกตัวเลือกแรกอัตโนมัติ หากถามไม่ตรงเรื่องให้บันทึก ไม่ป้อนคำตอบล่วงหน้า
5. เก็บผลหลังคำตอบและ diff จากก่อนคำตอบ; ตรวจว่าไม่ได้เขียนทับ field ที่ถูกอยู่แล้ว เช่นภาษีรายแถว
6. รัน G02/G03 r2 และ r3 ตามลำดับ แยกคะแนน reuse และ semantic drift ออกจาก cold score
7. เปิดบริบทใหม่เพื่อทำ G05 ด้วย commercial-offer schema ให้ task-commercial-offer.md แทน task.md และใช้ expected-commercial-offer.json เฉพาะฝั่ง evaluator
8. รอบแรกเป็น pilot ของการวัดผล; เมื่อวิธีวัดคงที่แล้วทำอย่างน้อย 3 independent runs ต่อ cold case เพื่อดูความแกว่ง โดยไม่ใช้การอนุมัติจาก run ก่อนเป็นความจำของ run ใหม่

## คะแนนที่ต้องเก็บ

| ตัววัด | วิธีนับ |
|---|---|
| Identity precision/recall | SKU ขาด เกิน ซ้ำ; ตรวจจำนวนแถวจริงก่อนแปลงเป็น dictionary |
| Accuracy ของข้อมูลที่มีหลักฐาน | คิดเฉพาะ field ที่มีค่าหรือมีกติกาคาดหวัง ไม่เพิ่มคะแนนด้วย null == null ของ schema ที่ไม่เกี่ยวข้อง |
| Exact record | เปรียบเทียบทุก field ที่โจทย์ระบุใน SKU เดียวกัน; normalize เฉพาะสิ่งที่สัญญาอนุญาต |
| Critical errors | ราคา สกุลเงิน tax flag/rate หน่วย วันที่ และ stock basis ผิดแยกเป็นจำนวนจริง |
| Collections | ตรวจ missing/extra item และ duplicate key; prices ใช้ price_list + effective_from ห้าม dictionary overwrite |
| Clarification | ต้องถาม/ถามตรงเรื่อง/ถามเกินจำเป็น/เดาเงียบ; G13–G16 ประเมินก่อนคำตอบแยกจาก accuracy หลังคำตอบ |
| Evidence | ค่าที่อธิบายต้องย้อนกลับไปไฟล์/ชีต/คอลัมน์/แถวหรือ task ได้ ห้ามแปะ citation ที่ไม่รองรับคำตอบ |
| Repair | จำนวนแก้ไขด้วยเครื่องมือ, ผลก่อน–หลัง, การแก้ที่ทำให้ field เดิมเสีย |
| Efficiency | เวลา, calls, tokens, cost ที่ provider รายงานหรือค่าประมาณที่ระบุที่มา, จำนวนครั้งที่คนต้องช่วย |
| Safety of approval | autoapprove/export ที่ยังมีความกำกวมหรือ critical error นับเป็น unsafe autoapproval |

สำหรับ output extra fields: ยอมรับ metadata/default ที่ schema อนุญาตและประกาศกติกาไว้ก่อน แต่ไม่ยอมรับ business facts ที่ไม่มีหลักฐาน เช่นราคาหรือสกุลเงินที่แต่งขึ้น และไม่ละเว้น extra collection rows

## เกณฑ์ผ่านที่เสนอสำหรับชุดเล็กนี้

- Critical errors และ unsafe autoapproval ต้องเป็นศูนย์
- 4 กรณีข้อมูลไม่พอต้องถามถูกเรื่องและไม่เผยแพร่ค่าที่เดา
- หลังได้รับคำตอบครบต้องได้ 12 SKU ที่ถูกต้องทุกกรณี; ข้อผิดพลาดในตัวเลข/หน่วยไม่อ้างว่าเป็น business decision
- FORMA ต้องไม่ด้อยกว่าคู่เทียบใน critical correctness, exact record และการถามในชุดเดียวกัน พร้อมรายงานเวลา/ต้นทุน/ความช่วยเหลือของคนแยก ไม่กลบด้วยคะแนนเฉลี่ย

เกณฑ์นี้เป็นเป้าหมาย ไม่ใช่ผลที่ได้แล้ว แม้ผ่านทั้งหมดก็ยืนยันได้เฉพาะชุดนี้ ยังต้องมี held-out export จริง, schema ใหม่, ไฟล์ใหญ่ และ load test ก่อนสรุปความพร้อมใช้งานจริงหลายประเทศ

## ข้อจำกัดของ harness ปัจจุบัน

airun.py เดิมอ่าน expected.json มาเลือกคำตอบ VAT ส่วน confirm/choice ใช้คำตอบอัตโนมัติ และทำ approve/export ต่อ จึงไม่เหมาะวัดการรู้ว่าเมื่อไรควรถาม นอกจากนี้ชุดเก่าเคยพบ scorer ซ่อน price item ซ้ำ ต้องเก็บทั้ง output ดิบและรายการผิดโดยไม่ทับ key ก่อนเทียบ

ชุดนี้แยก oracle ไว้แล้ว แต่ยังไม่ได้เพิ่มหรือแก้ execution harness ใน production repository การรันจริงครั้งถัดไปต้องเพิ่มตัวควบคุมการทดลองสำหรับข้อมูลแบบนี้ หรือทำผ่าน UI ด้วยผู้ประเมินตามขั้นตอนข้างต้นก่อน
