## ไฟล์อยู่ที่ไหนและลองด้วยมืออย่างไร

1. เลือกกรณีจาก `inputs/<case>/r1/` อ่าน `task.md` ก่อน
2. นำ JSON Schema จาก `schemas-neutral/T01.json` ถึง `T12.json` เข้าเป็นรูปแบบปลายทางใหม่สำหรับลูกค้าทดสอบ เลข T ตรงกับเลข R ของโฟลเดอร์ input
3. ใช้ลูกค้าทดสอบแยกแต่ละกรณี เพื่อไม่ใช้คำตอบจากกรณีอื่น
4. R01 ต้องนำเข้าไฟล์ 3 ไฟล์รวมเป็นงานของลูกค้ารายเดียวกัน ส่วนกรณีอื่นมี 1 workbook หลายชีต
5. ป้อนโจทย์จาก task.md ผ่านช่อง instructions ที่ระบบรองรับ หาก UI ไม่มีช่องนี้ ผลจะไม่เทียบเท่ารอบ API ที่รันไว้ ห้ามเดาว่าระบบได้รับโจทย์แล้ว
6. เก็บผลและคำถามก่อนตอบ แล้วจึงเปิด `oracle/<case>/` เฉพาะสำหรับคนตรวจ ห้ามอัปโหลด oracle ให้ AI
7. ตอบเฉพาะข้อที่ระบบถามตรงกับข้อมูลที่คนตรวจรู้ อย่ากดอนุมัติทุกข้อเพื่อให้คะแนนผ่าน

**R06–R08 เป็นไฟล์ใส่ความผิดปกติโดยตั้งใจ ห้ามเปิดแล้ว Save ด้วย Excel ก่อนอัปโหลด** เพราะ Excel อาจคำนวณใหม่หรือแก้ลิงก์ ทำให้กับดักหายไป ใช้สำเนาเมื่อต้องการเปิดดู สูตรลิงก์ภายนอกใน R08 เป็น OOXML fixture สังเคราะห์ ไม่ได้แนบ workbook ภายนอกจริง

## วิธีประเมิน

- รันผ่าน API/worker/PostgreSQL/S3/queue ของ stack จริงที่ localhost และ DeepSeek ที่ตั้งค่าไว้
- สร้างลูกค้าและ schema แยกต่อกรณี ไม่ approve ไม่ export ไม่แก้ mapping ก่อนเก็บผล
- ส่งเฉพาะไฟล์ใน manifest, task และ schema ให้ mapper ตรวจ hash และหลักฐานส่ง instructions
- oracle ถูกอ่านโดยตัวประเมินหลังเก็บ before.json แล้วเท่านั้น
- จำนวนสินค้า คีย์ซ้ำ แถวเกิน และสมาชิกคลังเกินถูกนับ ไม่ใช้ dictionary ทับข้อมูลซ้ำ
- inventory ไม่มีข้อกำหนดเรื่องลำดับ จึงเทียบด้วย warehouse_code โดยยังเก็บความซ้ำไว้ สกอร์ฉบับตรวจแล้วคือ score-reviewed.json; score-before.json เก็บผล harness เดิมไว้ตรวจย้อนหลัง รอบยืนยัน B ใช้ identity_keys ของ collection ที่ถูกต้องตั้งแต่เริ่ม
- แยกคะแนนการ map ที่มีหลักฐานครบ ออกจากความปลอดภัยและการถามในกรณีกำกวม ผลหลังตอบแยกจากก่อนตอบ
- นี่เป็นหนึ่งรอบทดลองต่อกรณี ขนาดเล็ก ไม่ใช่ load test หรือหลักฐานว่าไฟล์จริงทุกรูปแบบผ่าน
