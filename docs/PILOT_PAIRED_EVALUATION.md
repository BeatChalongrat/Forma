# ชุดคู่เทียบและการลองใช้งานก่อนรับ ERP จริง

ชุดนี้ใช้ข้อมูลจำลองเท่านั้น ไม่ใช่คะแนนความแม่นยำของ DeepSeek หรือหลักฐานว่าพร้อมเปิดส่งออกอัตโนมัติ
ไม่ได้เปลี่ยนกฎ mapping, knowledge ใน dev, คีย์โมเดล หรือค่าของ production

## สิ่งที่เตรียม

`backend/tests/fixtures/pilot_pair/` มี CSV 8 กรณี พร้อม JSON Schema, เฉลยข้อมูล และเฉลยหัวข้อที่ต้องถาม
เฉลยเขียนจากโจทย์โดยตรง ไม่ได้เอา JSON ที่ FORMA ส่งออกมาเป็นคำตอบของตัวเอง
เป็น synthetic hand-authored gold ยังไม่มีผู้เชี่ยวชาญเจ้าของ ERP ตรวจ ไม่ใช่ข้อมูลส่งออกจริงของลูกค้า

| กรณี | หลักฐาน/สิ่งที่ต้องตรวจ | พฤติกรรมที่คาดหวัง |
|---|---|---|
| P01 | รหัส `001`, ราคา, จำนวน | รักษาเลขศูนย์และค่าทั้งหมด |
| P02 | เปลี่ยนลำดับแถวและคอลัมน์ | ได้ข้อมูลเท่า P01 โดยไม่จำตำแหน่ง |
| P03 | ชื่อคอลัมน์ใหม่ที่ไม่ได้เพิ่ม alias ให้กฎ | อ่านความหมายและค่าประกอบ; เปิดเผยหากจับคู่ไม่ได้ |
| P04 | `02/03/2026` มี `22/09/2026` ในคอลัมน์เดียวกัน | ใช้หลักฐาน day-first อ่านเป็น 2 มีนาคม |
| P05 | ทุกวันและเดือนมีค่าไม่เกิน 12 | ถามรูปแบบวันที่; ยังไม่มี gold วันที่สุดท้ายจนเจ้าของข้อมูลตอบ |
| P06 | สกุลเงินสองช่องขัดกัน ไม่มีลำดับความสำคัญในสัญญาข้อมูล | ถามว่าจะใช้สกุลเงินไหน |
| P07 | `1.234,50` และค่ารูปแบบเดียวกันหลายแถว | อ่านทศนิยมเป็น 1234.50 |
| P08 | จำนวนปัจจุบัน/ปีก่อน และราคา/ต้นทุนอยู่ด้วยกัน | ไม่สลับคอลัมน์ที่ตัวเลขดูคล้ายกัน |

ชุดนี้เสริมชุดทดสอบหลายชีตและ relationship เดิม ไม่แทน corpus ทั้งหมด
การลอง staging ใช้ Excel 3 ชีต 12 สินค้า 24 รายการคลังและโปรโมชั่นหนึ่งรายการ
คำถาม VAT กับจำนวนต่อแพ็กใน UI fixture ถูกสร้างโดยเจตนาเพื่อทดสอบ flow
ไม่ใช้จำนวนคำถามใน fixture นี้เป็นผลประเมินโมเดลจริง

## รันฟรี

รันจาก repo root ด้วย virtualenv เดิม ไม่มีการอ่านคีย์หรือเลือก provider จริง

```powershell
backend\.venv\Scripts\python -m forma.eval.pilot backend/tests/fixtures/pilot_pair/manifest.json --out test-results/pilot-pair-run1
```

คำสั่งปฏิเสธโฟลเดอร์ผลที่มีอยู่แล้ว และปฏิเสธการเขียนทับ corpus
ไฟล์ผลทุกชุดเก็บ hash ของ source/schema/gold/manifest, prompt version, Git revision และ hash ของ harness
หากไฟล์ต่างกันจะไม่ยอมคำนวณผลต่างคู่เทียบ

| ผลลัพธ์ | ใช้ทำอะไร |
|---|---|
| `rules.json` | กฎเดิมผ่าน profiler → mapper → engine พร้อมผลลัพธ์จริง |
| `mock_echo.json` | เรียก schema/mapping agent ด้วย provider จำลองที่คืน draft เดิม ไม่แก้คำตอบตามเฉลย |
| `comparison.json` | เปรียบเทียบรายกรณี รายฟิลด์ รายการตกหล่น/ซ้ำ validation และเวลา พร้อมแสดง fallback |
| `blind-inputs/<case>/` | เฉพาะ source, schema และโจทย์ ไม่มีเฉลย/ประเภทกับดัก สำหรับผู้ทำ mapping แยก |
| `corpus-lock.json` | ลายนิ้วมือไฟล์เพื่อใช้ตรวจว่าคู่เทียบใช้โจทย์เดียวกัน |
| `question-review.json` | คำถามจริงจาก component ที่เรียก พร้อมช่องให้จัดประเภทหลังตรวจหลักฐาน |
| `reviewer-sessions.json` | แบบเก็บเวลาคนตรวจ การแก้ไข ความชัดเจน และข้อผิดพลาดหลังอนุมัติ |

Mock echo ไม่ใช่ AI ที่คิดและไม่ใช่การเทียบความเก่งกับกฎ ผลเท่ากันเป็นสิ่งที่คาดหวัง
เส้นทาง component นี้ยังไม่รวม routing/graph/policy/UI ทั้งระบบ
flow จริงตรวจแยกบน staging ด้วยคำสั่งด้านล่าง ค่าต้นทุนเป็น 0 เพราะไม่เรียกบริการโมเดลภายนอก

## ลอง flow บน staging แยก

ใช้ instance `pilot-nov14` ที่มีอยู่ หรือสร้าง pilot ชื่อใหม่ตาม `deploy/repro/PILOT.md`
ห้ามชี้ไป localhost ของ dev สคริปต์อ่าน ownership marker และตรวจ mock lock/pilot mode ก่อนทำงาน

```powershell
backend\.venv\Scripts\python deploy/repro/pilot_qualification.py --name pilot-nov14
```

รันตามลำดับ ไม่เปิด browser suite พร้อมขั้น restart

1. ชุดคู่เทียบกฎกับ mock พร้อมเฉลย
2. อัปโหลด → คำถาม → ร่าง → preview → ยืนยัน → อนุมัติ → ดาวน์โหลด
3. แก้ข้อมูลสองคำขอพร้อมกัน → ป้องกันทับเวอร์ชัน → ประวัติ → ดาวน์โหลด → restart → backup/restore
4. สร้าง fixture ใหม่สำหรับ browser → ตอบ → refresh → Back → preview → อนุมัติ → ดาวน์โหลด
5. ตรวจรหัสสินค้า ราคา หน่วย ความสัมพันธ์คลัง และโปรโมชั่นครบ 12 รายการจาก JSON ที่ดาวน์โหลด
6. เก็บ ledger คำถามเฉพาะ round ที่รันครั้งนี้ ไม่รวมตัวเลขจากการลองครั้งเก่า

ผลอยู่ `test-results/pilot-qualification/<timestamp>/result.json` พร้อม log แต่ละขั้น
หากขั้นใดล้ม คำสั่งหยุดและไม่เขียนผลว่า passed
เพิ่มเฉพาะข้อมูล synthetic ในฐาน staging เดิม ไม่ลบข้อมูลเก่า ไม่เปิด/หยุด dev
ขั้น recovery restart เฉพาะ API/worker ของ instance นี้ และ restore ในฐานกับ bucket ทดลองใหม่
trace และภาพหน้าจอ browser ล่าสุดอยู่ `test-results/pilot-browser/`

## วัดคำถามและเวลาคนให้ตรงความจริง

ช่องที่มีหลักฐานเพียงพอใช้ `answerable_field_accuracy` ส่วนช่องที่ต้องให้คนตัดสินใจแยกเป็น `decision_fields`
`field_accuracy` ดิบยังเก็บไว้ตรวจค่า draft แต่ไม่ใช้ตัดสินว่าการถามเป็นข้อผิดพลาด
P05/P06 ต้องดูทั้งคำถามที่จำเป็น การอนุมัติ และผลหลังคนตอบ ไม่ใช่ดูแค่ JSON ก่อนตอบ
ถ้าไม่ถามหัวข้อจำเป็นต้องนับ missed question แม้ schema validation ผ่าน

ผู้ตรวจใส่ `target`, `category`, `reviewer`, `evidence_location` ในสำเนาของ `question-review.json`
ประเภทมี `missing_information`, `conflicting_evidence`, `evidence_in_file`, `not_assessed`
ช่องหลักฐานของ missing-information ให้ระบุขอบเขตที่ตรวจแล้วและสิ่งที่ยังขาด
อย่าลบคำถามที่ไม่ชอบจากรายการ เพราะจะทำให้คะแนนสูงปลอม

```powershell
backend\.venv\Scripts\python -m forma.eval.pilot backend/tests/fixtures/pilot_pair/manifest.json --out test-results/pilot-pair-run1 --review test-results/reviewed-questions.json
```

สคริปต์ตรวจ hash และรายการคำถามเดิมก่อนสร้าง `question-scores.json`
ยังไม่จัดประเภทจะแสดง pending/null ไม่ตีเป็นคำถามที่ถูกต้อง
แสดง recall ของหัวข้อจำเป็น, precision ของคำถามจำเป็น, จำนวนถามเกินและหัวข้อถามซ้ำแยกกัน
คำถาม component ยังไม่ใช่คำถามทั้งหมดที่ผู้ใช้เห็น ให้เก็บ `/api/pilot/questions` จาก staging และตรวจ UI ประกอบ

ใช้ `reviewer-sessions.json` เก็บการทำด้วยมือ เทียบกับกฎช่วยและ AI ช่วย
ให้ผู้ตรวจต่างคนหรือสลับลำดับ/ใช้ไฟล์คู่ที่เทียบกันได้ เพื่อลดการจำคำตอบจากการลองรอบแรก
จับเวลาที่ทำงานจริง แยกเวลารอโมเดล แยกบันทึกพักงาน และให้ผู้ตรวจอีกคนสุ่มตรวจผลหลังอนุมัติ
ให้คะแนนความเข้าใจคำถาม 1–5 และบันทึกว่าเสร็จโดยไม่ต้องมีคนช่วยหรือไม่
เวลารัน Playwright เป็นเวลา automation เท่านั้น ไม่แทนเวลาคนหรือคำรับรองว่า UX ใช้ง่าย

## ตรวจหลักฐานเมื่อชื่อคอลัมน์ใหม่หรือสกุลเงินมีหลายความหมาย

`source_candidates` ส่งตัวเลือกของฟิลด์ที่ยังจับคู่ไม่ได้ให้ทั้ง mapper และ Evidence Analyst
ใช้ชนิดค่า ชื่อ/คำอธิบายใน schema ค่าตัวอย่าง และตำแหน่งไฟล์/ชีต เป็นสมมติฐานให้สำรวจต่อ
ไม่เลือกคอลัมน์อัตโนมัติจากรูปแบบตัวเลขหรือเพราะเหลือเพียงคอลัมน์เดียว
จำกัด 32 ฟิลด์ / 3 ตัวเลือกต่อฟิลด์ และตรวจเพิ่มเริ่มต้นไม่เกิน 8 คอลัมน์
จำนวนตัวเลือกจริงและป้าย complete แสดงข้อจำกัด; agent ใช้ inspection tools ขยายการตรวจได้
ข้อกำหนด วันที่ หน่วย การเชื่อมชีต และการเทียบ candidate ใช้ harness เดิมร่วมด้วย

ตัวตรวจสกุลเงินทำงานทั้ง full verifier และ service ก่อนอนุมัติ ไม่เชื่อคะแนน confidence ของโมเดลแทนหลักฐาน
รองรับ semantic `currency`, ชื่อ currency และคำอธิบาย currency code / ISO 4217 ใน schema
ถ้า source มีหลายสกุลเงินที่ยังไม่รู้ว่าใช้กับราคาใด ระบบถามเลือกคอลัมน์ โดยคงค่ารายแถวไว้
สอง currency fields ที่ระบุคนละแหล่งไว้แล้วถือเป็นคนละขอบเขต ไม่สรุปว่าข้อมูลผิดเพราะต่างสกุลเงิน
schema ไม่มี default จะไม่เติม THB ให้เอง; constant จากโมเดลที่ไม่มีหลักฐานต้องยืนยัน

หากเจ้าของข้อมูลระบุความหมายแหล่งที่มาแน่นอน สามารถใส่ใน schema ที่ตรวจแล้ว:

```json
{
  "x-forma": {
    "currency_sources": {
      "/settlement_currency": {
        "columns": ["Local Currency", "Invoice Currency"],
        "authoritative": "Invoice Currency"
      }
    }
  }
}
```

target ต้องเป็นฟิลด์สกุลเงินจริงและ authoritative ต้องอยู่ใน columns
ไม่ใส่ authoritative หากยังไม่มีข้อกำหนดจากเจ้าของข้อมูล; ไม่ให้โมเดลตั้งค่าใน DSL เพื่อข้ามคำถาม
column names เป็น configuration ของสัญญาข้อมูลนั้น ไม่ใช่ alias ของไฟล์ benchmark ใน production code
ถ้าคอลัมน์เปลี่ยนชื่อ ให้ปรับสัญญาหรือยืนยันใหม่ ไม่ถือว่าชื่อใหม่มีความหมายเดิมเสมอ

คำตอบที่ยืนยันเก็บผู้ตอบ target, expression และ hash ของ schema/หลักฐาน/source selector/record scope/collection joins/ไฟล์
คำตอบไม่เท่ากับอนุมัติส่งออก และการแก้ expression หรือไฟล์ใหม่ต้องตรวจใหม่
receipt นี้ใช้ในสายเวอร์ชันของงานเดิม ไม่ใช่สิทธิ์ข้ามข้อขัดแย้งทุกไฟล์ในอนาคต
ความรู้ข้ามรอบยังต้องผ่านกลไก scope/compatibility เดิม ไม่คัดลอก receipt ไปใช้อัตโนมัติ
ตัวตรวจสกุลเงินใช้ profile samples และ unique counts จึงไม่ใช่หลักฐานว่าเทียบสกุลเงินทุกแถวหรืออ่านภาษาทุกแบบแล้ว
ผล execute ตรวจจำนวน/ชนิด/ข้อผิดพลาดทั้งไฟล์แยกจากขอบเขตหลักฐานทางความหมาย

```powershell
backend\.venv\Scripts\python deploy/repro/source_evidence_smoke.py --name pilot-nov14
```

คำสั่งนี้ทดสอบ 3 กรณี: ชื่อคอลัมน์ปกติ, เปลี่ยนชื่อ/ลำดับ/source target และข้อกำหนดที่ระบุคอลัมน์ authoritative บน mock pilot:
อัปโหลด → เกิดคำถามจริงจากตัวตรวจ → preview → บันทึก → ไม่ถามซ้ำ → ตรวจ → อนุมัติ → ดาวน์โหลด
ตรวจค่ารายแถว 12 รายการ, คำขอบันทึกซ้ำต้องไม่สร้างเวอร์ชันซ้ำ และต้องอนุมัติก่อนส่งออก
กรณี authoritative ปฏิเสธคำตอบเลือกคอลัมน์อื่นด้วย แม้ข้อมูลคอลัมน์นั้นจะผ่านชนิดตาม schema
ผลอยู่ `deploy/repro/generated/<name>/source-evidence-result.json`
ไม่มีคำสั่งลบข้อมูล dev หรือเรียก API เสียเงิน

## เมื่อได้รับไฟล์ ERP จริง (ขั้นดำเนินการ)

1. รับไฟล์ที่ปกปิดแล้วและได้รับอนุญาต พร้อม JSON Schema ปลายทางและความหมายของฟิลด์
2. เก็บใน `data/real/` ซึ่งถูก ignore ห้าม copy เข้า synthetic fixture ที่จะเข้า Git
3. ให้เจ้าของข้อมูล/ผู้ตรวจอิสระทำเฉลยจาก source ก่อนดูผล FORMA ระบุ cell/sheet/กฎความหมาย
4. ข้อที่ยังไม่ทราบให้คงเป็นเรื่องตัดสิน ไม่เติมค่าเองให้เฉลยครบ ดูตัวอย่าง P05/P06
5. ตรึงไฟล์/schema/เฉลย แยก blind packet จากเฉลยและฐานความรู้ ไม่มีการเอาเฉลยส่งเข้า agent
6. ใช้ staging สำหรับข้อมูลจริงแยกจาก mock pilot และ dev ตั้ง provider/version/schema เดียวกันในคู่เทียบ
7. วัดกฎและโมเดลจริงบนไฟล์เดียวกันผ่าน stack เต็ม ทั้งก่อนคนตอบและหลังตอบ เก็บ fallback และ failed job ทุกครั้ง
8. เก็บคะแนนข้อมูล คำถาม เวลาคนตรวจ ต้นทุน และ downstream acceptance แยกตามไฟล์/format
9. ทดลองใช้งานแบบให้คนยืนยันก่อนส่งออกจนมีหลักฐานจริง ไม่มีการตัดสิน production จากค่าเฉลี่ย synthetic

ยังไม่เปิด live-provider runner ในคำสั่ง rehearsal นี้ รอไฟล์จริงและการอนุญาตก่อนรอบเสียเงิน
