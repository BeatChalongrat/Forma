## 2. AI เข้าใจไฟล์จริงไหม — สิ่งที่โมเดลทำได้โดยไม่มีใครบอก

- อ่านชีต **Info** ของ SAP แล้วเปลี่ยน `vat_included` จากที่ heuristic เดา (true ตามธรรมเนียมค้าปลีก) เป็น **false** พร้อมอ้างประโยค
  "KBETR is the net price excluding VAT 7%" และใส่ `vat_rate = 0.07`
- เห็นว่าชีต **T141T** ไม่ใช่ตารางสินค้า (heuristic ให้ role products) เปลี่ยนเป็นตาราง legend แล้ว **join** MARA.MSTAE ↔ T141T
  เพื่อแปล 01/02 เป็นข้อความสถานะ; ใน r3 แปล 01 → inactive, 02 → discontinued ถูก
- Odoo: อ่าน "Customer Taxes = VAT 7%" → ราคาก่อนภาษี, regex ดึง 7 แล้วหาร 100 เป็น vat_rate, ยก `product.pricelist.item`
  ที่ heuristic ทิ้งไว้ขึ้นเป็น collection โปรโมชั่น (Percentage → percent_off, Fixed Price → fixed_price), เชื่อม 3 ไฟล์ด้วย
  Internal Reference
- POS: รู้ว่า heuristic เอา "Promo Price" มาเป็นราคาขาย (ผิด) แล้วย้ายไป "UP"; `vat_included` อ่านจากคอลัมน์ Tax Incl แทนค่าคงที่;
  แปลงสต็อกกว้าง Qty OH Main / Br2 เป็น inventory 2 แถวด้วย `unpivot`; สร้างโปรจากแถวสินค้าพร้อมกรอง Promo ID ไม่ว่าง;
  สถานะ A/I/D → enum
- Business Central: ไม่เลือกชีตราคาที่สองเอง แต่ประกาศ source ไว้แล้วถามว่า WHOLESALE คืออะไร; status จาก Lifecycle Stage
  ก่อนแล้วค่อย Blocked (conditional); ลบ /description ที่ heuristic map จาก "Item Category Description" เพราะไม่ใช่คำบรรยายสินค้า
- ปรับโครงสร้าง (adaptation) อธิบายทุกการเปลี่ยนเป็นรายการ บางรายอธิบายเป็นภาษาไทยเอง และ **ไม่เปลี่ยนคำตัดสินทางธุรกิจ** ที่คน
  เคยยืนยัน (VAT, warehouse = WERKS) — ตรงตามที่ prompt สั่ง
- ข้อความสั่ง AI ในเซลล์หมายเหตุ (HAND) ไม่มีผล: ราคาทุกตัวคงเดิม ไม่มีคำถามหรือ evidence ที่อ้างถึงข้อความนั้น

คำถามที่ AI ตั้งเป็นคำถามของคนทำงานจริง เช่น "DATBI มี 31.12.9999 คือไม่มีวันสิ้นสุด ควรออกเป็น null ไหม",
"warehouse_code ควรเป็น WERKS หรือ LGORT หรือรวมกัน", "category ควรเป็นรหัส MATKL หรือชื่อ WGBEZ"

## 3. สิ่งที่ต้องแก้ (เรียงตามความสำคัญ)

### 3.1 โมเดลเขียน DSL ไม่ผ่าน validator แล้วระบบถอยไป heuristic เงียบ ๆ (2 ใน 6 ลูกค้าใหม่)
SAPTH (ครั้งที่ 2) และ HAND: mapping agent ตอบไม่ผ่าน `MappingDocument` 3 ครั้ง (1 + retry 2) ทั้งที่ครั้งแรกของ SAPTH ผ่านในรอบที่ 2
ความผิดเป็นรูปทรง expression (ใส่ `args` ให้ op ที่รับ `params`, `const` ไม่มี `value`, nested `conditional`) ไม่ใช่ความเข้าใจไฟล์
ผลคือได้ mapping ที่แย่กว่า (0.86 / 0.67) และคนต้องแก้มือ ทั้งที่ AI "เข้าใจ" แล้ว
- deepseek ผ่าน `response_format: json_object` ไม่บังคับ schema; prompt บอกชื่อ op แต่ **ไม่บอกชื่อ param และ arity**
  (`_ops_list()` ส่งแค่ชื่อ)
- แก้: ส่งตาราง op → arity + params (จาก `docs/MAPPING_DSL.md` เดียวกัน) เข้า prompt; เมื่อ validation ตก ส่งเฉพาะ node ที่ผิด
  พร้อมตัวอย่างรูปที่ถูกให้แก้เฉพาะจุด แทนการให้เขียนทั้งเอกสารใหม่; เพิ่ม repair แบบ deterministic สำหรับความผิดซ้ำ ๆ
  (`{"op":"const"}` ไม่มี value, params ที่สะกดผิดอย่าง `day_first`); และเมื่อถอยไป heuristic ให้บอกบนการ์ดว่า AI เสนออะไรไว้
  (เก็บ output ที่ตกไว้ให้คนดู)

### 3.2 ค่าที่ผิดเงียบ ๆ จาก param ที่ไม่มีใครตรวจ — วันที่อเมริกันกลายเป็น 10 มกราคม
POS: โมเดลใส่ `parse_date_th(..., day_first=false)` (ชื่อจริงคือ `dayfirst`) validator ไม่รู้จัก param จึงปล่อย engine ไม่รู้จักจึง
ใช้ค่า default → `10/1/2026` ออกเป็น **2026-01-10** ทั้งที่โมเดลเขียน evidence ว่า "10/31/2026 proves month/day/year"
และ profiler ก็ติด hint `month_first` ไว้แล้ว (ADR-055) เป็นความผิดเงียบระดับ critical (promo.start_date)
- แก้: `validate_mapping` ต้องรู้ชุด param ของทุก op และ **error** เมื่อพบ param แปลก (ตอนนี้ตรวจแค่ param ที่ขาด);
  heuristic/AI ควรรับ hint `month_first` จาก profile เป็นค่าเริ่ม

### 3.3 drift มองไม่เห็นคอลัมน์ที่ย้ายชีต
DYN r3: Unit Price ย้ายจากชีต Item ไปชีต Sales Price `compare()` ใช้ **union ของหัวทุกชีต** จึงเห็นว่าชุดหัวเท่าเดิม → "header_moved"
→ ใช้ mapping เดิมจาก memory → 12 รายการไม่มีราคา → review ด้วย engine errors (ปลอดภัย แต่ AI ไม่ถูกเรียกมาปรับ และข้อความบอกคน
ว่า "หัวตารางเลื่อน" ซึ่งไม่จริง)
- แก้: เทียบหัวต่อตาราง (ต่อชีต) ก่อนแล้วค่อยรวม; คอลัมน์ที่หายจากตารางหนึ่งและโผล่ในอีกตารางคือ `column_moved` ที่ต้องปรับ mapping

### 3.4 ปี 9999 ของ SAP กลายเป็น 9456
`31.12.9999` (เปิดไม่สิ้นสุด) ถูก `assume_year=auto` ตีว่าเป็นปีพุทธศักราชแล้วลบ 543 → `effective_to: 9456-12-31` ค่าผิดเงียบ ๆ
ทั้งที่โมเดลถามเรื่องนี้ไว้แล้ว
- แก้: ปี ≥ 9000 คือ sentinel → null (หรือ param `open_ended_values`); การตีว่าเป็น พ.ศ. ควรจำกัดช่วง 2400–2700

### 3.5 API ตอบก่อน commit — client ที่เร็วอ่านไม่เจอสิ่งที่เพิ่งสร้าง
วัดจริง: สร้างรอบแล้วอ่านทันที 25 ครั้ง ได้ 404 **3 ครั้ง**; ตัวรันชนสองครั้ง (ACCTH r1 อัปโหลดไฟล์เข้ารอบที่ "ไม่มี", ODOO r3 อ่าน
mapping ใหม่หลัง answers/apply ไม่เจอจึงอนุมัติเวอร์ชันที่ superseded → 409) `get_session` commit หลัง `yield` ซึ่ง FastAPI 0.162
รันหลังส่ง response แล้ว หน้าเว็บที่ยิง request ต่อเนื่อง (apply แล้ว refresh) จะโดนเหมือนกันเป็นครั้งคราว
- แก้: commit ก่อนคืน response (ใน handler ที่เขียน หรือ middleware ที่ commit session ของ request ก่อนส่ง body)

### 3.6 การ์ดคำถามถาม "ยืนยัน" มากเกินและไม่มีทางเลือก
ลูกค้าใหม่ได้ 9–13 คำถาม ส่วนใหญ่ชนิด `confirm` ที่ตอบได้อย่างเดียวคือ "ยืนยัน" (เช่น "/promotions/*/end_date — date part is the
validity end") คำถามที่มีทางเลือกจริง (category = MATKL หรือ WGBEZ, warehouse = WERKS หรือ LGORT) กลับตอบบนการ์ดไม่ได้ ต้องไป
mapping editor นอกจากนี้คำถาม VAT ของ heuristic ("assumed VAT-inclusive (Thai retail convention)") ยังค้างอยู่แม้ AI เปลี่ยนเป็น
false จากหลักฐานแล้ว (SAPTH ครั้งที่ 1 มีทั้งสองคำถามพร้อมกัน)
- แก้: คำถามชนิด `choice` ที่ให้เลือกคอลัมน์/ค่าได้บนการ์ด; ถามเฉพาะฟิลด์ที่ความมั่นใจต่ำกว่าเกณฑ์ **และ** มีทางเลือก;
  เมื่อ AI ตอบคำถามของ heuristic แล้วให้ตัดคำถามเดิมทิ้ง

### 3.7 เรื่องเล็กที่เห็น
- หน่วย: รหัส SAP (FL, KAR, KI) และ "Dozens" ของ Odoo ไม่ถูก normalize (`unit_normalize` มี param `synonyms` แต่โมเดลไม่ใช้) →
  ให้ `enum_hint` + ตัวอย่างค่าจริงเข้า prompt และให้ `unit_normalize` รู้จักรหัส SAP/Odoo/POS ที่พบบ่อย
- category: AI เลือกรหัส (BEV01, BEV) แทนชื่อเมื่อมีทั้งคู่ และตั้งเป็นคำถาม — ควรมีกฎ: เมื่อมีทั้งรหัสและชื่อ ให้ชื่อเป็นค่าและรหัสเป็น attribute
- HAND: แถวหมวด (เซลล์เดียว) กลายเป็นสินค้า 2 แถว และ `category` ไม่ได้ fill-down — ต้องมีกฎ "แถวที่มีค่าเฉพาะคอลัมน์แรกใต้หัวตาราง =
  section" ใน profiler (ปัญหาที่รู้แล้ว P13)
- ACCTH: `/prices: 1 items reference unknown root records` — แถวท้ายรายงานหลุดเข้า collection ราคาแต่ไม่เข้าสินค้า (filter คนละชุด)
- ตารางราคา LLM ของ FORMA ไม่มี deepseek → ตัวเลขค่าใช้จ่ายบนหน้า Settings ไม่ตรงบิล

## 4. flow ตั้งแต่ไฟล์เข้าจนส่งออก และการแก้ข้อมูล

ลูกค้าใหม่ (คนทำ): อัปโหลด → กดรัน → อ่านการ์ด (เหตุผล + คำถาม + ตัวอย่าง) → ตอบคำถาม (preview แล้ว apply = 1 คลิก ได้ mapping
เวอร์ชันใหม่) → อนุมัติ mapping → แปลง → ดูข้อมูล → อนุมัติข้อมูล → ส่งออก รวม ~7 การกระทำ ส่วนที่ยังสะดุด: หลังอนุมัติ mapping
ต้องกด "แปลง" เองอีกครั้ง (อัตโนมัติเฉพาะรอบจาก bulk upload) และคำถามชนิด confirm ที่ไม่มีอะไรให้ตัดสิน (§3.6)

ลูกค้าเดิมโครงสร้างเดิม: 0 การกระทำ — 3 วินาที ผ่านเอง เผยแพร่เอง และยังตรวจค่าสำคัญกับรอบก่อน (POS r3 จับ VAT หายได้)

ลูกค้าเดิมโครงสร้างเปลี่ยน: AI อธิบายว่าเปลี่ยนอะไรทำไมเป็นข้อ ๆ คนอ่านแล้วกดอนุมัติ (ACCTH r3 ได้ `rename_only` →
ปุ่มยอมรับคลิกเดียว)

การแก้ข้อมูล (ทดสอบบน dataset ของ ODOO ที่เผยแพร่แล้ว, 11 ขั้นผ่านหมด): แก้ 1 ช่อง = preview (เห็น before/after) + apply →
เวอร์ชันใหม่ (v2 draft, v1 ยังเป็น published); กฎถาวร ("SKU นี้ inactive เสมอ") = เหมือนกันและไปอยู่ที่ลูกค้าเป็น override;
rollback = 1 คลิกได้ v4 ที่ชี้ parent ครบ; lineage/trace ของรายการบอก mapping, ไฟล์, แถว, และ edit 1 ครั้ง ถือว่า **ง่ายและย้อนได้**
สิ่งที่ยังไม่มี: แก้ mapping "ใช้คอลัมน์อื่น" จากการ์ดคำถาม (ต้องไป editor) และกฎถาวรยังอยู่ระดับ dataset ไม่ได้สอน mapping
(ADR-038 learning ครอบคลุมเฉพาะ header alias)

## 5. คำตอบของคำถาม "AI เข้าใจไฟล์ format และสิ่งที่เราอยากได้ แทน manual ไหม"

ใช่ในส่วนความหมาย: ทุกครั้งที่โมเดลตอบเป็น DSL ที่ถูกต้อง มันอ่านโน้ต legend ภาษี และความสัมพันธ์ข้ามชีตได้ดีกว่ากฎ และตั้งคำถาม
ตรงจุด ความผิดที่เหลือเป็นเรื่อง **กลไกรอบ ๆ โมเดล**: (1) รูปทรง DSL ที่โมเดลเขียนพลาดแล้วไม่มีใครช่วยซ่อม (2) param ที่สะกดผิด
แล้วไม่มีใครเตือน (3) drift ที่มองข้ามการย้ายชีต (4) sentinel ปี 9999 (5) API commit ช้ากว่า response ห้าเรื่องนี้แก้ได้ที่โค้ด
FORMA ไม่ต้องเปลี่ยนโมเดล และควรแก้ก่อนเอาไฟล์ลูกค้าจริงเข้า

สิ่งที่ยังไม่ได้วัด: โมเดลตัวอื่น (gpt-4.1 / claude ที่บังคับ schema ได้จริงจะลด §3.1 ไปมาก), ไฟล์ขนาดหลายพันแถว (ตัวอย่าง 5 แถว
ต่อคอลัมน์อาจไม่พอเห็นค่าแปลก), และความสม่ำเสมอเมื่อส่งไฟล์เดิมซ้ำหลายครั้ง (รันครั้งเดียว)

## 9. รันครั้งที่สี่ — ความมั่นใจจากหลักฐาน (ADR-059, ลูกค้าใหม่ `AI-*-E` / `AI-*-F` / `AI-HAND-G`, deepseek-flash)

สิ่งที่เปลี่ยนก่อนรอบนี้ (7 ข้อจากรายงานสำรวจเจ้าใหญ่): การ์ดคอลัมน์ส่ง 10 ค่าถ่วงความถี่ + สัดส่วนว่าง + distinct + min/max;
FORMA ดูค่าเต็มของคอลัมน์ที่ draft ไม่มั่นใจและคอลัมน์ทางเลือกให้ก่อนโมเดลเริ่ม (grounding); anchor จาก mapping ที่อนุมัติของลูกค้ารายอื่น
(≥2 รายกลายเป็น alias, 1 รายส่งให้โมเดล); ความเห็นตรงกันของ matcher กับโมเดลคุมความมั่นใจและทำให้ฟิลด์ที่เห็นต่างเป็น `choice`;
plausibility เทียบรอบที่อนุมัติ; threshold เสนอจากผลรีวิว; สุ่มตรวจ 5% ของงานอัตโนมัติ; คำถามเดียวกันข้ามไฟล์ตอบครั้งเดียว

รอบ `-E` (18 รอบ) เผยข้อผิดสองข้อที่แก้ก่อนรอบ `-F`: agreement เทียบข้อความ expression จึงบอกว่า "เห็นต่าง" ทั้งที่อ่านคอลัมน์
เดียวกัน (คำถามบนการ์ดพุ่งเป็น 7–13 ข้อต่อราย ทุกข้อ "contested") และ `enum_hint` ของหน่วยในไฟล์ schema ไม่มี BOTTLE/BAG/CAN
โมเดลจึงเขียน synonyms ทับตารางของ engine (FL, Bottle → PCS) รอบ `-F` (r1+r3) เผยอีกสองข้อ: `questions()` ล้มเมื่อฟิลด์ที่เห็นต่างเป็น

### ก่อน → หลัง (เทียบ §7 ซึ่งวัดด้วย scorer และเฉลยชุดเดียวกัน)
- **ความถูกต้อง** SAPTH 0.908 → **0.938** (หน่วย FL → BOTTLE ถูกแล้ว เหลือ category รหัส/ชื่อ 12 ฟิลด์), ODOO 0.995 → **1.000** (Bottle →
  BOTTLE), ACCTH/POS 1.000, DYN 0.842/0.944 และ HAND 0.995 เท่าเดิม — ที่เหลือทั้งหมดเป็นเรื่องตัดสินที่ §7 ระบุไว้ (category รหัสหรือชื่อ
  SAP 12 + DYN 12, ชีตราคาที่สองของ DYN, HAND สถานะจากหมายเหตุ 1)
- **คำถามบนการ์ด r1 ของลูกค้าใหม่ 6 ราย** 58 (§6) → 21 (§7) → **16** และใน 16 ข้อ 5 ข้อเป็น "contested" คือ matcher กับโมเดลอ่านต่างกันจริง
  (SAPTH/ACCTH/POS/DYN: VAT รวมหรือไม่ — matcher ตั้งสมมติ true โมเดลอ่านจากไฟล์ว่า false; ODOO: ราคากับชื่อคอลัมน์ที่มีสองตัวเลือก)
  คำถามที่เหลือเป็น confirm ของฟิลด์ critical ที่ไม่มีทางเลือก (วันเริ่ม/จบโปร) และ `choice` ที่โมเดลไม่มั่นใจเอง
- **grounding แทน inspect** FORMA ดูให้ 0–4 คอลัมน์ต่อรอบ โมเดลไม่เคยขอ inspect เองเลย (0/12 — §7 คือ 1/12) และ self-check ยังจับได้ 3 รอบ
  (SAPTH r1 อ้าง MTSTB ผิด frame อีกครั้ง, ODOO r1, DYN r1) แก้สำเร็จในรอบเดียวทุกครั้ง `problems_left` ว่างทุกรอบ
- **anchor** ลูกค้าใหม่แต่ละรายได้ alias 12–25 ฟิลด์จาก mapping ที่อนุมัติของลูกค้าทดสอบรุ่นก่อน (`AI-*`, `-B`, `-C`, `-D` ซึ่ง
  เป็น flavour เดียวกัน) โดยมี evidence "learned: N other customers map this header here (anchor, ADR-059)" — นี่คือภาพที่ลูกค้า SAP
  รายที่ 5 จะเห็นในระบบจริง ไม่ใช่ลูกค้ารายแรก; ความมั่นใจของฟิลด์เหล่านั้นเป็น 1.0 และ `confidence_basis.raised` ยก /status, /category,
  /unit/pack_size, /inventory/*/warehouse_code ที่โมเดลให้ต่ำแต่ matcher เห็นตรงกัน
- **ข้อจำกัดของ matcher** HAND มี 15 ฟิลด์ที่โมเดล map แต่ heuristic ไม่ (inventory แบบ unpivot, โปรโมชั่น) ฟิลด์เหล่านั้นยังอยู่บนคำของโมเดล
  (`model_only`) เพราะ FORMA ไม่มีผู้อ่านที่สองให้เทียบ
- **สุ่มตรวจและกลุ่มคำถาม** ไม่มีรอบ auto_approve ของลูกค้าใหม่ในชุดนี้ (r2 ที่ auto_approve ไม่ถูกสุ่ม — 5% ของ 4 รอบ) และ harness ตอบ
  คำถามทีละไฟล์ จึงไม่ได้วัดสองข้อนี้กับโมเดลจริง เทสครอบคลุมทั้งสองทาง

ต้นทุนรอบ `-F` + SAPTH ซ้ำ + HAND `-G`: 25 เรียก ≈ $1.2 สำหรับ 12 รอบที่เรียกโมเดล (ลูกค้าใหม่ ~$0.10–0.20 เท่า §7; prompt ใหญ่ขึ้น
~5k token จาก top_values และ grounding) harness แก้ให้ตอบ VAT ตามเฉลยของรอบนั้น ไม่ใช่ของลูกค้า (ข้อบกพร่องที่ §8 บันทึก)
