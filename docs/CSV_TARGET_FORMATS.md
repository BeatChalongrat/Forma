# รูปแบบปลายทางจาก JSON Schema หรือ CSV ตัวอย่าง

หน้า Settings → Target formats → New format มีสองทางเลือก:

- **JSON Schema**: ใช้สัญญาข้อมูลเดิม รวมถึงข้อมูลซ้อน กฎตรวจค่า และ `x-forma` เหมือนเดิม
- **CSV ตัวอย่าง**: ใช้ตารางตัวอย่างของผลลัพธ์ปลายทาง ไม่ใช่ไฟล์ต้นทางที่จะนำมาประมวลผล

## ใช้ CSV

1. เลือก CSV ตัวอย่าง (UTF-8, Windows-874/TIS-620 หรือ UTF-16 LE) และตัวคั่น
2. กดอ่านแม่แบบ ระบบอ่านทุกแถวในแม่แบบ ไม่สุ่มบางแถว ไม่เรียกโมเดล
3. ตั้งชื่อและรหัสรูปแบบ ตรวจตัวอย่างของแต่ละคอลัมน์ เลือกชนิดข้อมูล ความหมายหรือคำอธิบาย และช่องห้ามว่าง เพิ่มชื่อเรียกอื่นได้ถ้าทราบ เช่น Product Name กับ ชื่อสินค้า
4. เลือกคอลัมน์ที่ใช้ระบุแต่ละรายการ หากรหัสสินค้าซ้ำข้ามคลัง ให้เลือกทั้งรหัสสินค้าและคลังร่วมกัน
5. ยืนยันแต่ละคอลัมน์ แล้วกดตรวจรูปแบบที่ยืนยันแล้ว ก่อนบันทึกรูปแบบ
6. เลือกรูปแบบนี้ให้ลูกค้า หรือกำหนดเป็นค่าเริ่มต้น แล้วอัปโหลดและตรวจงานตาม flow เดิม
7. หลังอนุมัติ สามารถดาวน์โหลด CSV หรือ JSON โดย CSV รักษาหัวคอลัมน์ ลำดับ และตัวคั่นที่ยืนยันไว้

การอ่านและตรวจแม่แบบไม่เปลี่ยนค่าเริ่มต้นของระบบหรือรูปแบบของลูกค้า การบันทึกเพิ่มเวอร์ชัน ไม่เขียนทับเวอร์ชันเก่า ใช้สิทธิ์ผู้อนุมัติที่เข้าถึงลูกค้าทั้งหมดและบันทึก audit ผ่านเส้นทางเดียวกับ JSON

## สิ่งที่ต้องยืนยัน

- ตัวอย่างอย่างเดียวพิสูจน์ไม่ได้ว่าช่องใดห้ามว่าง เป็นรหัส หน่วยอะไร หรือรวม VAT หรือไม่ จึงไม่เติมค่าเริ่มต้นทางธุรกิจจากตัวอย่าง
- `00123` และรหัสตัวเลขยาวแนะนำเป็นข้อความเพื่อรักษาค่า ไม่แปลงเป็นตัวเลขเงียบ ๆ
- วันที่แบบ `02/03/2026` ไม่ถูกเดาว่าเดือนหรือวันก่อน ชนิดวันที่ปลายทางใช้ `YYYY-MM-DD` และตรวจวันที่จริง หากต้องการคงข้อความเดิม ให้เลือกข้อความและอธิบายรูปแบบ (ไม่มีการรับประกันการจัดรูปวันที่จากคำอธิบายอย่างเดียว)
- ตัวเลขปลายทางใช้เลขมาตรฐาน เช่น `1234.50` ตัวอย่างที่มีตัวคั่นกำกวมต้องแก้ตัวอย่างหรือเลือกเป็นข้อความ; ค่า boolean ใช้ `true`/`false`
- คำอธิบายถูกส่งเป็นบริบทของ schema ให้ mapper แต่ไม่ใช่กฎคำนวณอัตโนมัติ หากต้องการกฎบังคับเพิ่มเติม ใช้ JSON Schema
- แก้การตั้งค่าคอลัมน์หลังยืนยัน จะต้องยืนยันและตรวจใหม่ ผลตรวจเก่าหรือ response ที่มาช้าไม่เปิดสิทธิ์บันทึกข้อมูลใหม่

## ค่าคงที่และคำถามสกุลเงิน

คอลัมน์ข้อความเลือก **ใช้ค่านี้ทุกแถว** แล้วกรอกค่าที่ต้องการและยืนยันคอลัมน์อีกครั้งได้ ระบบสร้าง `const` และ `default` ใน JSON Schema เดียวกัน ไม่อนุมานค่าคงที่จากแถวตัวอย่างหรือคำอธิบาย หากตัวอย่างมีค่าขัดกันจะไม่ให้บันทึก การเปลี่ยนค่าหรือชนิดข้อมูลต้องตรวจและยืนยันใหม่

กฎตรวจสกุลเงินใช้ค่าที่กำหนดชัดเจนในรูปแบบ (`const`, `enum` ที่มีค่าเดียว หรือ `default`) ได้ทั้ง CSV และ JSON หาก mapping ใช้ค่าตรงตามสัญญาและไม่พบหลักฐานขัดกัน จะไม่ถามยืนยันค่าซ้ำ ข้อความในคำอธิบายหรือคำกล่าวอ้างของโมเดลไม่ถือเป็นการยืนยัน

คำตอบสกุลเงินที่เลือกให้จำและผ่านการอนุมัติแล้ว ใช้ซ้ำได้เมื่อผ่านเงื่อนไขความจำเดิม เช่น ลูกค้า รูปแบบ และสัญญาปลายทาง ระบบบันทึกแหล่งความจำที่ใช้กับหลักฐานของไฟล์รอบใหม่ หากถอนความจำ เปลี่ยนเงื่อนไข หรือพบแหล่งสกุลเงินที่ขัดกัน จะกลับมาให้ตรวจ ไม่ใช้คำตอบเดิมปิดข้อสงสัยอัตโนมัติ ทั้งนี้การตรวจจากตัวอย่างข้อมูลไม่ใช่หลักประกันว่าทุกแถวของไฟล์จริงมีความหมายถูกต้อง ยังต้องผ่านกฎตรวจผลลัพธ์และการอนุมัติเดิม

## สัญญาข้อมูลภายในและขอบเขต

CSV ถูกแปลงเป็น JSON Schema ผ่าน registry เดิม จึงใช้การตรวจ mapping, schema gate, การอนุมัติ และการส่งออกเดิม ไม่เพิ่ม mapper แยก CSV ตัวอย่างไม่ใช่การเรียนรู้ความจำอัตโนมัติ

รองรับตารางแบน 1–100 คอลัมน์, ไม่เกิน 1 MiB หลังถอดรหัสเป็น UTF-8, และ 2,000 แถวตัวอย่าง ใช้เฉพาะหัวคอลัมน์ได้แต่ต้องยืนยันชนิดและความหมายเอง ข้อจำกัดนี้ใช้เฉพาะแม่แบบ ไม่ใช่จำนวนแถวของไฟล์ ERP ที่นำเข้าตามปกติ

รองรับ comma, semicolon, tab และ pipe; quoted cells, multiline values, Unicode/BOM ตรวจชื่อซ้ำ จำนวนช่องไม่ตรง ตัวอักษรเสีย และตัวอย่างที่ขัดกับชนิด/ช่องบังคับก่อนบันทึก

ชื่อหัว CSV ที่มี `/`, `~`, `*`, `.` หรือชนกับชื่อภายใน ใช้ชื่อฟิลด์ภายในที่ปลอดภัยและ synonyms ของหัวเดิม โดยส่งออก CSV ด้วยหัวเดิมทุกตัว การส่งออก JSON ใช้ชื่อฟิลด์ภายในเหล่านี้ เห็นได้ในตารางตรวจรูปแบบก่อนบันทึก

คอลัมน์ไม่บังคับยังปรากฏใน CSV แม้ทุกแถวว่างหรือไม่มีรายการ ส่งออก UTF-8 พร้อม BOM เพื่อให้ Excel อ่านภาษาไทยได้; encoding ที่เลือกตอนอ่านแม่แบบไม่ได้เปลี่ยน encoding ของผลลัพธ์

ข้อมูลซ้อนและหลายรายการในช่องเดียวให้ใช้ JSON Schema และ output variants เดิม การรองรับ CSV แม่แบบไม่ได้รับประกันความแม่นของโมเดลกับไฟล์ ERP ที่ไม่เคยทดสอบ และยังต้องมีคนตรวจตามนโยบายเดิม

## ทดสอบแบบไม่เสีย API และไม่แตะ dev

Backend tests ใช้ `isolated_env` สร้างฐาน SQLite และ storage ชั่วคราว พร้อมโมเดลจำลอง:

```powershell
cd backend
$env:FORMA_TEST_BLOCK_EXTERNAL='1'
$env:FORMA_LLM_PROVIDER='mock'
.\.venv\Scripts\python -m pytest tests/test_csv_target.py tests/test_config.py tests/test_custom_schema.py tests/test_schema_registry.py tests/test_schema_gate.py tests/test_export_stream.py --no-cov
```

Frontend tests ใช้หน้าจอจริงและ mock ที่ API boundary พร้อมบล็อก network:

```powershell
cd frontend
npm run test -- tests/TargetFormats.page.test.tsx
npm run test:typecheck
npm run build
```

เส้นทางใหม่ `POST /api/schemas/csv/analyze` และ `POST /api/schemas/csv/prepare` ไม่เขียนฐานข้อมูล จากนั้นใช้ `POST /api/schemas/preview` และ `POST /api/schemas` เดิม ข้อมูลยืนยันแนบ digest ของ contract เพื่อกันแก้ document แล้วใช้การยืนยันเก่าต่อ
